# 18. 운영 절차

설치부터 종료, 장애 대응, 데이터 삭제 확인까지의 표준 절차다. 시연 당일의 장면 순서와 대체 방법은 부록 E 에 있다.

## 18.1 최초 설치

1. 교실 확인: 카메라 위치, 전원·콘센트(실측 평면도는 만들지 않는다).
2. 네트워크 시험: 카메라 1대로 싸피 Wi-Fi 접속과 노트북 RTSP 수신 확인. 실패 시 공유기 구성(3.5).
3. 카메라 앱 설정: RTSP 계정, fps 25 고정, 워터마크·UPnP·경보·야간 전환·사생활 모드·자동 업데이트 끄기, Tapo 클라우드 외부 접속 차단, 펌웨어 버전 기록.
4. 거치: 네 모서리, 2.6\~2.8m, 아래로 25\~28°, 무게 주머니.
5. 시간 동기화 시험(G0): LED ms 카운터 판을 4대가 동시에 촬영.
6. 실측 정물(안전봉·라바콘 등) 2\~3개를 방의 서로 다른 곳에 세움 → 자동 보정 시작 → 한 명 1\~2분 걷기(키를 미리 잰 팀원. 부족하면 여러 명이 걷고 모두 보정에 씀, 4.3) → 키를 아는 사람이 3\~5곳에 서기 → CALIBRATED 확인 → BEV 평면도 자동 생성·확인. 기준 미달이면 그 자리에서 걷기를 다시 하거나 정물을 더 배치해 재보정한다(설치 일정에 여유를 둔다).
7. 정적 3D 생성 요청 → Scene 커밋 확인.
8. 구역 등록, 정적 객체·작업면 등록(단상·책상 OBB 와 상판 높이, 7.5) → 구성 묶음 발행 → “현장 적용됨” 확인.
9. 시험 알림 확인: 노트북 로컬 시험음, 반장 PWA 시험 푸시(`POST /api/push/test`). 둘 다 “시험” 표시가 나오는지 본다(RiskEvent 는 만들지 않음, 3.10).

**네트워크 보충.**

- 공유기를 쓰면 노트북은 공유기에 유선 LAN 또는 USB 로 연결하고, 노트북 Wi-Fi 는 싸피망에 붙인다. 공유기 DHCP 는 기본 게이트웨이를 주지 않게 설정해 인터넷 트래픽이 싸피 Wi-Fi 로만 나가게 한다.
- 카메라의 Tapo 클라우드 외부 접속은 차단한다.
- 시연장에서는 Direct TCP 와 RunPod HTTPS 프록시를 각각 10분 이상 연속 시험하고, LTE 테더링을 두 번째 업링크로 준비한다(3.12). 실측한 망 이름을 기록한다. SSAFY 개발 망은 나가는 포트가 80·443·8000·8080 만 열려 Direct TCP 가 막혔다(3.12 시연장 망 위험).

**설치 보충.**

- 정적 3D 생성 전에 교실을 비우고 카메라별 프레임을 확보한다(5.3).
- 교실망 NTP 서버로 카메라 시각 기준을 바꾸는 작업은 보류다(3.9). 상태 화면에서 카메라별 촬영 시각 불확실성과 노트북–Pod 시계 차이를 확인한다.
- 반장 휴대폰: Android는 브라우저에서 알림을 허용하고, 갤럭시는 Chrome 을 절전 예외에 넣는다. iPhone은 Safari에서 “홈 화면에 추가”로 PWA를 설치한 뒤 알림을 허용해야 Web Push를 받는다(iOS 16.4 이상, Declarative Web Push 는 18.4 이상). 설치 후 시험 푸시로 확인한다.
- 관제 화면 PC의 소리 출력을 켜고 시험 경보로 확인한다(3.10).
- 노트북 OS: Windows Update 일시 중지, 집중 모드(알림 끄기), 출력 오디오 장치 고정, 노트북 서비스 자동 기동, 시계 오프셋 확인.

## 18.2 일상 시작·종료

- 시작 순서: GPU 인스턴스 기동(GPU 확보, 시작 절차 `simai-bootstrap` 이 GPU 확인·저장 위치·가중치 해시를 확인. TensorRT 엔진은 저장 위치 캐시에서 로드하고, 캐시가 없거나 키가 다르면 첫 기동 때 그 GPU 에서 만든다, 3.12) → Tier 0 엔드포인트 등록 확인(EC2) → 노트북 서비스 기동(재부팅 시 자동 기동 설정) → EC2 상태 화면에서 카메라 4대 OK, CALIBRATED, NOMINAL 확인 → 시험 경보(노트북 시험음·시험 푸시). 분석 워커는 필요할 때만 기동.
- 노트북 설정: 전원 연결 유지, 잠자기·덮개 닫힘 동작 해제, 인터넷 트래픽이 싸피 Wi-Fi로 나가는지 확인.
- 종료: 노트북 서비스 정지 → 결과·기록을 노트북으로 가져옴(컨테이너 디스크면 지우기 전에) → GPU 인스턴스 멈춤 또는 지우기(크레딧 절약) → 당일 이벤트·조치 미결 확인. 시연 저장 위치(재시작에도 남는 디스크)는 지우지 않는다.

**시연 당일.**

- GPU 인스턴스는 아침에 확보해 시연이 끝날 때까지 유지한다(재확보 실패 위험, 3.12).
- T-60분 go/no-go 점검표: GPU 확보, 엔드포인트 등록, 카메라 4대 OK, 노트북 시험음, 시험 푸시. 하나라도 실패하면 부록 E 의 대체 시연으로 간다.

## 18.3 장애 대응

| 증상 | 확인 | 조치 |
|---|---|---|
| 현장 “관제 중단” | 노트북 인터넷 연결, Tier 0 엔드포인트 | Wi-Fi 재연결, 엔드포인트 재조회, RunPod Tier 0·EC2 상태 확인, 막히면 LTE 테더링·443 프록시 |
| “현장 장비 응답 없음” | 노트북 전원·서비스 | 재기동 |
| 카메라 1대 OFF | 카메라 전원·공유기 연결 | 재연결, 구역 감시 저하 해소 확인 |
| DRIFTED | 스탠드 충돌 여부 | 위치 복구 후 한 명 걷기로 재보정 |
| VLM 근거 지연 | RunPod 상태 | 분석 워커만 문제면 근거 없이 경보는 정상. Tier 0 Pod 문제면 관제 정지 상태이므로 즉시 재기동 |
| 시간 동기화 이탈 | health 의 노트북–Pod 시계 오프셋과 카메라별 촬영 시각 불확실성 | 카메라 재부팅, 노트북 시계 확인 |

## 18.4 데이터 삭제 확인

주 1회 EC2 클립 삭제 작업, DB 보관 정책, Tier 0 저장 위치 정리 작업이 동작했는지와 EC2 디스크 사용률(70% 를 넘으면 11.5 의 조치)을 확인하고(삭제 예정일 지난 클립 0건, 클립 14일), 보존 표시된 항목의 사유를 검토한다. 프로젝트 발표 후 30일 안에 보존 표시분을 포함한 모든 데이터를 파기하고 기록을 남긴다(11.5). 참여자 삭제 요청은 해당 세션 데이터를 찾아 삭제하고 기록을 남긴다.

## 18.5 Tier 0 재시작 복구

Tier 0 는 재시작하면 체크포인트와 이벤트 저널로 활성 이벤트를 복구한다(3.2). 복구는 활성 이벤트를 추측하지 않으므로 아래 경우에는 시작하지 않고 노트북에는 “관제 중단”이 표시된다. **어느 경우든 저널을 지워 정상 복구로 삼지 않는다.** 저널을 지우면 활성 이벤트와 EC2 로 보내지 못한 전이(outbox)를 잃는다.

공통 첫 조치: 같은 Tier 0 저장 위치(3.12)의 저널 디렉터리(세그먼트, `acked_offset`, 근거 색인)와 체크포인트 디렉터리를 통째로 보관 위치(날짜·`gateway_id` 를 붙인 디렉터리)에 복사해 원본을 보존하고, 오류 메시지·로그와 함께 Lead 에 알린다.

| 시작 거부 | 원인 | 조치 |
|---|---|---|
| 이전 형식 저널 | 이벤트 상태(`meta.state`)를 남기기 전 코드가 쓴 저널. 상태를 되살릴 수 없다 | 배포 전 시험 데이터면 저널·체크포인트 디렉터리를 보관 위치로 옮기고 새로 시작한다. 운영 데이터면 옮기지 않고 보존한 채 Lead 에 알린다(변환 경로 없음) |
| 체크포인트 불일치 | 저널이 fsync 된 기록을 잃었거나(체크포인트가 앞섬) 다른 저널(같은 offset 의 msg_id 가 다름). 저장 위치(`SIMAI_ROOT`)·마운트 착오가 흔한 원인 | 볼륨·경로 설정을 먼저 확인한다. 같은 Tier 0 의 저널이 맞는데 기록이 없어졌으면 저장소 장애로 보고 보존 뒤 Lead 판단 |
| 정리된 저널(복구 불완전) | 쓸 체크포인트가 없고(모두 손상·형식 불일치) 저널 앞부분이 정리돼 활성 이벤트를 다 알 수 없다 | 보존 뒤 Lead 판단. EC2 의 이벤트 기록(최종 상태)과 대조해 수동으로 판단한다 |
| 저널 재적용 실패 | 기록의 이벤트 상태 손상, payload 와 불일치, 다른 Tier 0·LIVE 가 아닌 기록 | 보존 뒤 Lead 판단(저널 손상) |

시작하지만 알려야 하는 것:

- 버린 체크포인트(손상·부분 쓰기·형식 버전·다른 Tier 0·정리된 구간)와 이유. 로그·health 에 남기고, 파일은 다음 체크포인트 저장 때 정리되므로 필요하면 그 전에 보관 위치로 복사한다.
- 체크포인트 없이 저널 전체로 복구함: 구성 버전을 체크포인트에서 얻지 못하므로 구성 묶음 보관본의 복구 결과만으로 판정한다.
- 저널 이상(빈 번호, 모르는 갱신, 중복, 오래된 기록): 로그로 알린다.
- 복원한 구역 대상 이벤트(R7 형태)는 그 구역의 감시 확보 근거가 해소 유지 시간 동안 이어져야 해소된다(6.4). 카메라를 복구할 수 없거나 구역·R7 을 구성에서 뺐으면 근거가 오지 않아 남는다. 저널·체크포인트를 고쳐 지우지 않고, 확인(ACK)으로 담당자를 남긴 뒤 관리자가 운영자 종료(6.4, `POST /api/events/{id}/close`)로 닫는다. 구역·R7 을 빼기 전에는 그 구역의 활성 R7 이벤트가 없는지 먼저 확인한다.

실행 중 경고:

| 신호 | 의미 | 조치 |
|---|---|---|
| 체크포인트 정지(초기값 5초 동안 성공 없음) | 체크포인트를 못 쓴다(저장 위치 용량·권한·fsync 지연). 이전 세대가 남아 판정은 계속되지만 재시작 때 다시 적용할 구간이 길어지고 저널 정리가 멈춘다 | 저장 위치 용량·쓰기 지연을 확인한다. 용량이 차면 디스크를 늘린다. 저널·체크포인트를 지워 공간을 만들지 않는다 |
| 저널 쓰기 정지·실패 | 이벤트 저널 쓰기가 멈췄거나 실패했다 | 저널 운영 절차를 따른다(3.2 저널 계약) |
| 저널 크기 | 전이 기록에 이벤트 상태 전체를 함께 남겨 이전 형식보다 크다(발생 기록 약 1.7배, 확인 이력이 길면 더 큼) | 저장 위치 용량 감시에 저널 디렉터리를 포함한다 |
