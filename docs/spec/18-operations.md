# 18. 운영 절차

설치부터 종료, 장애 대응, 데이터 삭제 확인까지의 표준 절차다. 시연 당일의 장면 순서와 대체 방법은 부록 E 에 있다.

## 18.1 최초 설치

1. 교실 확인: 카메라 위치, 전원·콘센트(실측 평면도는 만들지 않는다).
2. 네트워크 시험: 카메라 1대로 싸피 Wi-Fi 접속과 노트북 RTSP 수신 확인. 실패 시 공유기 구성(3.5).
3. 카메라 앱 설정: RTSP 계정, fps 25 고정, 워터마크·UPnP·경보·야간 전환·사생활 모드·자동 업데이트 끄기, Tapo 클라우드 외부 접속 차단, 펌웨어 버전 기록.
4. 거치: 네 모서리, 2.6\~2.8m(거치대 기둥은 늘 같은 길이로 펴고 테이프로 표시, 현장 세팅 화면은 직전 세팅 입력값 자동 채움), 아래로 25\~28°, 무게 주머니.
5. 시간 동기화 시험(G0): LED ms 카운터 판을 4대가 동시에 촬영.
6. 세팅 1단계 카메라 각도 확인 및 무보행 현장 세팅 시작: 관제 앱 **현장 세팅 화면 1단계**에서 4대 실시간 미리보기와 **카메라 각도 헬퍼**(`GET /api/cameras/coverage-guides`, 게이트웨이 별도 CPU 프로세스가 `gateway/relay` 로컬 미리보기 키프레임으로 계산, 추가 RTSP 세션 0)로 4대 시야가 하나로 이어지는지(`CONNECTED`)와 회전 방향 안내(`LEFT`·`RIGHT`·`UP`·`DOWN`)를 확인해 필요한 카메라 각도를 다듬고(막지 않음, **“그대로 진행”** 가능; 헬퍼의 `CONNECTED` 는 보정 성공이 아님), 카메라별 바닥~렌즈 실측 높이(직전 세팅 값 자동 채움, 처음이면 입력)를 확인해(정물 배치 단계는 없다. 라바콘·개구부 안내판처럼 원래 놓는 안전 소품이 두 대 이상에 보이면 자동으로 교차 검증에 쓴다, 4.3) **“현장 세팅 시작”**(`POST /api/setup-sessions`, 걷기 보정 없음, 4.3)을 누른다.
7. 무보행 보정·품질 게이트 및 1인 보행 「카메라 확인」 통과 확인: 진행 화면에서 자동 파이프라인(깨끗한 배경 20~30초 누적 → 무마커 내부 파라미터 → 상주 MapAnything 초기 자세·점구름 및 World 자동 정의 → 인접 쌍 배경 특징점 V2 공동 번들 조정·절대 품질 게이트 `quality_gate` 검산 → `CALIBRATED` 발행 + 빠른 3D 미리보기 맵 `preview_scene`·VLM 위험구역 초안 `vlm_zone_draft` 병렬 생성)을 확인하고, 보정 발행 직후 **현장 1명이 작업 영역을 30~60초 걸어 다니며 「카메라 확인」(`camera_check = PASSED`, 6쌍 통과율·LOO 재투영 기준선 확보, 4.3)**과 정밀 맵 완료를 통과하는지 확인한다. 기준 미달(`FAILED`)이면 안내된 원인에 따라 카메라 각도·겹침 물체·보행 범위를 조정한 뒤 **“다시 시도”**(`POST /api/setup-sessions/{id}/retry`)를 누른다.
8. 세팅 구역 검토·VLM 초안 조정 및 구성 묶음 발행: 세팅 구역 확인·실시간 관제 관리자 편집 모드에서 신규 VLM 위험구역·고소 작업면 초안(`vlm_zone_draft`, “AI 초안”)과 이전 세팅 이관 구역(높이 변화 판정 `CHANGE_SUSPECTED` → `UNKNOWN` → `UNCHANGED` 정렬, `UNCHANGED` 만 일괄 확인 가능, `CHANGE_SUSPECTED` 는 VLM 전후 크롭 의견 `KEEP`·`MODIFY`·`REMOVE` 참고, 8.2)을 검토·조정하고, 추가 위험구역(`CRITICAL` 빨강·`HIGH` 주황 2종) 및 고소 작업면(그리면 작업면 OBB + 둘레 `HIGH` 구역 동시 생성, 7.5·8.2) 등록 → `POST /api/zones/commit` 저장·구성 묶음 발행(초안 확정, 카메라 확인 통과 후 허용) → “현장 적용됨” 확인.
9. 시험 알림 확인: 노트북 로컬 시험음. “시험” 표시가 나오는지 본다(RiskEvent 는 만들지 않음, 3.10).

**네트워크 보충.**

- 공유기를 쓰면 노트북은 공유기에 유선 LAN 또는 USB 로 연결하고, 노트북 Wi-Fi 는 싸피망에 붙인다. 공유기 DHCP 는 기본 게이트웨이를 주지 않게 설정해 인터넷 트래픽이 싸피 Wi-Fi 로만 나가게 한다.
- 카메라의 Tapo 클라우드 외부 접속은 차단한다.
- 시연장(SSAFY 망)에서는 기본 경로인 EC2(`simai.live:22`) SSH 경유 + Pod 공개 포트 Direct TCP(EC2 보안 그룹 인바운드 22 허용 확인 포함)를 10분 이상 연속 시험하고, LTE 테더링을 두 번째 업링크로, RunPod HTTPS 프록시(443 + wstunnel)를 최후 예비로 준비한다(3.12). 실측한 망 이름과 바깥 IP 를 기록한다. SSAFY 망은 일반 외부로 나가는 포트가 80·443·8000·8080 만 열려 직접 Direct TCP 는 막히지만 팀 EC2(`simai.live:22`)는 열려(노트북→EC2 약 5 ms, EC2→일본 Pod 약 41 ms) EC2 경유를 기본으로 쓰고, LIVE·GPU 세션 중에는 EC2 CPU(`t3.xlarge` 4 vCPU, 버스트형)를 나누는 CI 빌드를 피한다(3.12 시연장 망 위험).

**설치 보충.**

- 현장 세팅(정적 배경 수집) 때 교실이 비어 있으면 즉시 조기 수렴하며, 사람이 지나가더라도 `CleanBackgroundAccumulator` 가 사람 영역을 지우고 시간 중앙값으로 깨끗한 배경을 자동 누적한다(4.3, 5.3).
- 교실망 NTP 서버로 카메라 시각 기준을 바꾸는 작업은 보류다(3.9). 상태 화면에서 카메라별 촬영 시각 불확실성과 노트북–Pod 시계 차이를 확인한다.
- 관제 화면 PC의 소리 출력을 켜고 시험 경보로 확인한다(3.10).
- 노트북 OS: Windows Update 일시 중지, 집중 모드(알림 끄기), 출력 오디오 장치 고정, 노트북 서비스 자동 기동, 시계 오프셋 확인.

## 18.2 일상 시작·종료

- 시작 순서: GPU 인스턴스 기동(GPU 확보, 시작 절차 `simai-bootstrap` 이 GPU 확인·저장 위치·가중치 해시를 확인. TensorRT 엔진은 저장 위치 캐시에서 로드하고, 캐시가 없거나 키가 다르면 첫 기동 때 그 GPU 에서 만든다, 3.12) → Tier 0 엔드포인트 등록 확인(EC2) → 노트북 서비스 기동(재부팅 시 자동 기동 설정) → EC2 상태 화면에서 카메라 4대 OK, CALIBRATED, NOMINAL 확인 → 시험 경보(노트북 시험음). 분석 워커는 필요할 때만 기동.
- 노트북 설정: 전원 연결 유지, 잠자기·덮개 닫힘 동작 해제, 인터넷 트래픽이 싸피 Wi-Fi로 나가는지 확인.
- 종료: 웹 작업 종료 → 게이트웨이가 기존 기기 REST를 반복 조회하여 종료 구간의 닫힌 파일 업로드 시작(관제 유지 가능, 진행 상태는 다시 보기 표시) → 노트북 서비스 정지(`simai-gateway.ps1 stop` 실행 시 백그라운드 `simai-recorder upload` 가 로컬 녹화본에서 완료된 작업 구간만 mp4 조각으로 잘라 S3 에 자동 업로드, 5.1·11.5) → 결과·기록을 노트북으로 가져옴(컨테이너 디스크면 지우기 전에) → GPU 인스턴스 멈춤 또는 지우기(크레딧 절약) → 당일 이벤트·조치 미결 확인. 시연 저장 위치(재시작에도 남는 디스크)는 지우지 않는다.

**시연 당일.**

- GPU 인스턴스는 아침에 확보해 시연이 끝날 때까지 유지한다(재확보 실패 위험, 3.12).
- T-60분 go/no-go 점검표: GPU 확보, 엔드포인트 등록, 카메라 4대 OK, 노트북 시험음. 하나라도 실패하면 부록 E 의 대체 시연으로 간다.

## 18.3 장애 대응

| 증상 | 확인 | 조치 |
|---|---|---|
| 현장 “관제 중단” | 노트북 인터넷 연결, EC2 SSH 로컬 포워드(`simai-ec2`), Tier 0 엔드포인트 | Wi-Fi·EC2 SSH 포워드 재연결, 엔드포인트 재조회, RunPod Tier 0·EC2 상태 확인(EC2 경유 시 EC2 호스트가 멈추면 현장 경보도 함께 멈춤), EC2·망이 막히면 LTE 테더링(두 번째 업링크)·443 프록시(최후 예비)로 전환 |
| “현장 장비 응답 없음” | 노트북 전원·서비스(`simai-gateway.ps1` `Test-ModeTreeAlive` 가 자식 프로세스 생존까지 확인해 5분 주기 자동 복구하되 30분 내 3회 초과 반복 시 `notify-mode-flapping` 중단, 3.10) | 원인 확인 후 재기동 |
| 카메라 1대 OFF | 카메라 전원·공유기 연결 | 재연결, 구역 감시 저하 해소 확인 |
| DRIFTED | 스탠드 충돌·회전 여부 | 미세 회전은 배경 비교 기반 중심 고정 회전 자동 복구(`rotfix`)가 2회 연속 확인·60초 감시를 거쳐 자동 반영하고, 세팅 기준선이 있는 보정에서 재투영 급등으로 일시 제외된 카메라는 배경 `< 0.5°` 3회 연속 정상 확인 시 자동 복귀(보정당 최대 2회, 4.4). 스탠드 위치 이동이나 큰 회전으로 복구되지 않으면 위치·각도 점검 후 현장 세팅(`POST /api/setup-sessions`) 재실행 |
| VLM 근거 지연 | RunPod 상태 | 분석 워커만 문제면 근거 없이 경보는 정상. Tier 0 프로세스 비정상 종료 시 `simai-bootstrap` 이 사이드카를 유지한 채 Tier 0 만 백오프(1~5초) 자동 재기동하며(3.12), Pod 자체 장애면 즉시 재기동 |
| 시간 동기화 이탈 | health 의 노트북–Pod 시계 오프셋과 카메라별 촬영 시각 불확실성 | 카메라 재부팅, 노트북 시계 확인 |

## 18.4 데이터 삭제 확인

주 1회 EC2 클립·작업 구간 녹화 조각 삭제 작업, DB 보관 정책, Tier 0 저장 위치 정리 작업이 동작했는지와 EC2 디스크 사용률(70% 를 넘으면 11.5 의 조치)을 확인하고(삭제 예정일 지난 클립·녹화 조각 0건, 클립·작업 구간 녹화 조각 모두 14일), 보존 표시된 클립 항목의 사유를 검토한다. 프로젝트 발표 후 30일 안에 보존 표시분과 TBM 전자서명·관제 운영 표시 이름 이력을 포함한 모든 데이터를 파기하고 기록을 남긴다(11.5). 참여자 삭제 요청은 해당 세션 데이터를 찾아 삭제하고 기록을 남긴다.

## 18.5 Tier 0 재시작 복구

Tier 0 는 재시작하면 체크포인트와 이벤트 저널로 활성 이벤트를 복구한다(3.2). 복구는 활성 이벤트를 추측하지 않으므로 아래 경우에는 시작하지 않고 노트북에는 “관제 중단”이 표시된다. **어느 경우든 저널을 지워 정상 복구로 삼지 않는다.** 저널을 지우면 활성 이벤트와 EC2 로 보내지 못한 전이(outbox)를 잃는다.

공통 첫 조치: 같은 Tier 0 저장 위치(3.12)의 저널 디렉터리(세그먼트, `acked_offset`, 근거 색인)와 체크포인트 디렉터리를 통째로 보관 위치(날짜·`gateway_id` 를 붙인 디렉터리)에 복사해 원본을 보존하고, 오류 메시지·로그와 함께 Lead 에 알린다.

| 시작 거부 | 원인 | 조치 |
|---|---|---|
| 이전 형식 저널 | 이벤트 상태(`meta.state`)를 남기기 전 코드가 쓴 저널. 상태를 되살릴 수 없다 | 배포 전 시험 데이터면 저널·체크포인트 디렉터리를 보관 위치로 옮기고 새로 시작한다. 운영 데이터면 옮기지 않고 보존한 채 Lead 에 알린다(변환 경로 없음) |
| 체크포인트 불일치 | 저널이 fsync 된 기록을 잃었거나(체크포인트가 앞섬) 다른 저널(같은 offset 의 msg_id 가 다름). 저장 위치(`SIMAI_ROOT`)·마운트 착오가 흔한 원인 | 볼륨·경로 설정을 먼저 확인한다. 같은 Tier 0 의 저널이 맞는데 기록이 없어졌으면 저장소 장애로 보고 보존 뒤 Lead 판단 |
| 정리된 저널(복구 불완전) | 쓸 체크포인트가 없고(모두 손상·형식 불일치) 저널 앞부분이 정리돼 활성 이벤트를 다 알 수 없다 | 보존 뒤 Lead 판단. EC2 의 이벤트 기록(최종 상태)과 대조해 수동으로 판단한다 |
| 저널 재적용 실패 | 기록의 이벤트 상태 손상, payload 와 불일치, 다른 Tier 0·LIVE 가 아닌 기록 | 보존 뒤 Lead 판단(저널 손상) |

시작하지만 알려야 하는 것:

- 버린 체크포인트(손상·부분 쓰기·형식 버전·다른 Tier 0·정리된 구간)와 이유. 로그·health 에 남기고, 파일은 다음 체크포인트 저장 때 정리되므로 필요하면 그 전에 보관 위치로 복사한다.
- 체크포인트 없이 저널 전체로 복구함: 구성 버전을 체크포인트에서 얻지 못하므로 구성 묶음 보관본의 복구 결과만으로 판정한다.
- 저널 이상(빈 번호, 모르는 갱신, 중복, 오래된 기록): 로그로 알린다.
- 복원한 구역 대상 이벤트(R7 형태)는 그 구역의 감시 확보 근거가 해소 유지 시간 동안 이어져야 해소된다(6.4). 카메라를 복구할 수 없거나 구역·R7 을 구성에서 뺐으면 근거가 오지 않아 남는다. 저널·체크포인트를 고쳐 지우지 않고, 확인(ACK)으로 담당자를 남긴 뒤 관리자가 운영자 종료(6.4, `POST /api/events/{id}/close`)로 닫는다. 구역·R7 을 빼기 전에는 그 구역의 활성 R7 이벤트가 없는지 먼저 확인한다.

실행 중 경고:

| 신호 | 의미 | 조치 |
|---|---|---|
| 체크포인트 정지(초기값 5초 동안 성공 없음) | 체크포인트를 못 쓴다(저장 위치 용량·권한·fsync 지연). 이전 세대가 남아 판정은 계속되지만 재시작 때 다시 적용할 구간이 길어지고 저널 정리가 멈춘다 | 저장 위치 용량·쓰기 지연을 확인한다. 용량이 차면 디스크를 늘린다. 저널·체크포인트를 지워 공간을 만들지 않는다 |
| 저널 쓰기 정지·실패 | 이벤트 저널 쓰기가 멈췄거나 실패했다 | 저널 운영 절차를 따른다(3.2 저널 계약) |
