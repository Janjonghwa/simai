# 5. 처리 계층

실시간 경로는 Tier 0(검출·추적·keypoint·삼각측량·LIVE 판정)이며 RunPod Tier 0 서비스에서 관제 중 상시 동작한다. 나머지는 같은 GPU Pod 안의 분석 워커 프로세스에서 비동기로 처리하며, 3.2의 자원 규칙으로 Tier 0의 큐와 GPU 메모리를 침범하지 않는다.

**계층(Tier) 명칭.** simai는 처리를 지연 요구와 안전 판단 권한에 따라 Tier로 나눈다. 번호가 작을수록 실시간성과 안전 판단 권한이 높다.

| Tier | 이름 | 내용 | 실행 | 안전 판단 권한 |
|---|---|---|---|---|
| Tier 0 | 실시간 안전 경로 | 관측 → YOLO26x-pose 검출·추적·2D keypoint → 카메라 간 연결 → 시간 보간·삼각측량 → World 상태 → LIVE 판정 | RunPod Tier 0 서비스, 실시간 | 있음. 위험 판단의 유일한 위치 근거 |
| Tier 1 | 3D 인체 강화·아바타 | Fast SAM 3D Body(HMR)로 MHR 리깅 메시·포즈 스트림과 관측 기반 외형 보강, 빠진 관절·체형·손 보강 | RunPod 분석 워커, 비동기(아바타 스트림은 상시 루프) | 없음. 표시·보조용(inferred), Tier 0 위치·ID 를 덮어쓰거나 위험 판정에 넣지 않음 |

구 Pipeline 문서의 Tier 2(LHM++·PEAR 기반 사실적 아바타)는 폐지했다(16장). EXP-02의 MHR 리깅 메시·포즈 스트림과 관측 기반 외형 갱신은 시연 범위(2026-10-23 결정: 1단계 MHR 리깅 메시 + 포즈 스트림(상·하의 대표색), 2단계 관측 픽셀 UV 텍스처 누적, 3DGS 미사용)이며 계속 Tier 1(안전 판단 권한 없음, 관절은 inferred, root 위치는 Tier 0 `world_state` 가 정본, 위험 판정에 쓰지 않음)에 둔다. 정적 3D, VLM, PPE 워커는 Tier 번호 없이 각자의 주기로 도는 비동기 처리이며, 결과는 상태(Scene 버전, 근거 문장, PPEState)로만 위험 판단에 들어간다. 아래 표에서 5.1·5.2가 Tier 0, 5.6이 Tier 1이다.

| 계층 | 실행 위치 | 주기 | 단계 |
|---|---|---|---|
| 5.1 Tier 0 관측 | RunPod Tier 0 | 카메라당 12 FPS 이상 | MVP |
| 5.2 3D 골격·World 상태 | RunPod Tier 0 | 10 Hz | MVP |
| 5.3 정적 3D | RunPod 분석 워커 | 설치 시 1회 | MVP |
| 5.4 VLM·LLM | RunPod 분석 워커(VLM), 외부 API(LLM) | 이벤트 발생 시, 보고서 요청 시 | MVP |
| 5.5 PPE 검출 | RunPod Tier 0 와 같은 GPU 인스턴스의 PPE 프로세스 | 1\~2 Hz | MVP(M3) |
| 5.6 SAM 3D Body 강화·메시 아바타(EXP-02) | 분석 워커·상시 아바타 프로세스(`services/avatar`) | 아바타 포즈 스트림 사람별 2\~5 Hz(body 모드 기본, LIVE 중 지연 감시 예외 3.2), 손 포함(full)은 표시용 저주기 | 시연 범위(1단계 메시·포즈 스트림, 2단계 UV 텍스처 누적 CUDA 기본 `auto`) |
| 5.7 정적 공간 갱신 | RunPod 분석 워커 | 저주기 | 확장(부록 C) |
| 5.8 Unreal 배경 빌드 | 빌드 워커 | Scene 커밋 시 | 확장(부록 C) |

## 5.1 Tier 0 관측

- 입력: 노트북이 중계한 카메라 4대 영상(RTSP over TCP)과 촬영 시각 메타데이터(3.9)
- 모델: YOLO26x-pose 하나로 사람 검출과 2D keypoint를 한 번의 추론으로 낸다. **기준선은 YOLO26x-pose, TensorRT FP16, imgsz 1280, E2E(NMS-free) 출력**이다. H100 80GB 에서 카메라 4대 동시 입력 38 ms(카메라당 약 26 FPS)로 목표를 넘고, 크기별 정확도는 공식 벤치마크와 COCO 측정 모두 x 가 가장 높다. 크기 비교를 다시 하지 않는다. E2E 를 기본으로 하는 근거는 공식 COCO 지표가 E2E 71.6, NMS 71.7 로 같다는 것이며, 교실 밀집 장면의 재현율은 A0 녹화에서 기록만 한다.
- 관절: COCO 17관절에 발 6점(COCO-WholeBody 의 좌우 엄지발가락·새끼발가락·발뒤꿈치)을 더한 23점으로 미세조정해 Tier 0 단일 추론을 유지한다(15.4 A1). 미세조정 모델이 채택되기 전에는 COCO 17관절이다.
- 추적: 카메라별로 독립된 TrackTrack 상태(추적기 설정은 명시 지정, 카메라 움직임 보정 `gmc_method: none`). 추론 모델은 공유해 묶음 추론하되 ID 공간·시간 기록·추적 상태는 카메라마다 분리한다. 카메라 간 통합은 5.2의 추적 3계층이 맡는다
- 검출 클래스: 사람(MVP). 확장: 장비 대체물(카트), 책상·의자, 방향 마커(부록 C)
- 출력: 카메라별 `observation_2d`(bbox, 카메라 내 트랙 ID, keypoint 배열과 신뢰도). 원본은 Tier 0 저장 위치(3.12)에 보관하고 EC2 로 보내지 않는다(11.2)
- 2D keypoint는 카메라 간 연결, 삼각측량, 자동 보정, SAM 3D Body 프롬프트, PPE 사람 연결(그리고 확장의 워치 움직임 대조)의 공통 입력이라 단일 실패점이다. 가림 시 신뢰도 동작을 G0·G2에서 검증하고 bbox와 트랙 이력을 독립 근거로 함께 쓴다. Tier 0 실시간 안전 경로에서는 분할 마스크를 추론하지 않는 대신, 이미 만든 원본 해상도 BGR 프레임과 사람 검출 상자를 비동기 스레드(`tier0-clean-background`)로 넘겨 사람 없는 정적 배경을 시간 중앙값으로 누적한다(5.3, `docs/design/clean-background-accumulator.md`). 정적 3D 복원(`static_reconstruct`)의 단일 프레임(`FRAME`) 입력과 상시 아바타 루프(`services/avatar`, 5.6)에서는 `YOLO26x-seg` 사람 분할 마스크를 쓴다.

**입력 추상화.** Tier 0 서비스는 노트북 중계 스트림, 녹화 파일(시나리오 데이터셋), 시뮬레이터 출력을 같은 형식(카메라 ID + 촬영 시각 + 프레임)으로 받는다. 시뮬레이터는 2D keypoint 단계부터 바로 넣을 수도 있다. 장비 없이 개발하고 같은 데이터로 반복 검증하기 위한 장치다.

**프레임 최신성 정책.** 처리 속도가 입력(카메라당 25 fps)보다 낮아도 늘 최신 영상을 판정한다.

- 디코딩과 추론을 분리한다. 디코더는 프레임 의존성 때문에 모든 압축 프레임을 받지만(기본은 CPU 디코딩, GPU 하드웨어 디코더(NVDEC)는 설정으로 고른다. 어느 쪽이든 BGR 색 변환은 CPU 에서 한다), 추론은 카메라별 최신 디코딩 프레임만 고른다(latest-frame-wins).
- 카메라별 추론 대기열은 최대 1\~2장, 최대 대기 시간(queue_wait_ms 기준, 초기값 150ms)을 넘긴 프레임은 추론하지 않고 버린다.
- 정책상 건너뛴 프레임은 `SKIPPED_BY_POLICY`, 전송 중 사라진 프레임은 `NETWORK_LOSS`로 따로 기록한다. G0의 손실률에는 NETWORK_LOSS만 넣는다. 노트북 송신 큐가 넘쳐 버린 프레임은 노트북 쪽에서 따로 센다(12.7).
- 오래된 프레임을 뒤늦게 추론한 결과로 LIVE 상태를 갱신하지 않는다. 결과는 촬영 시각 기준으로 시간 모델(6.1)에 들어가고, 이미 반영된 최신 결과보다 오래되면 버린다.
- 카메라당 12 FPS는 평균값이므로, 최대 결과 간격과 촬영부터 추론 시점까지의 전체 경과 시간인 프레임 연령(`frame_age_ms`)을 함께 잰다.
- GPU가 포화되면 Tier 0 포즈 추론을 지키고 분석 워커 작업과 PPE 프레임부터 건너뛴다(3.2 접수 규칙).

**이벤트 클립 링 버퍼와 CRITICAL 이벤트 프레임.** Tier 0 서비스는 카메라별 최근 영상(예: 60초)을 압축 상태로 메모리에만 보관한다. LIVE 의 CRITICAL·HIGH 이벤트가 발생하거나 해소 후 재개되면 앞뒤 구간(예: 각 20초)을 키프레임부터 디코딩 없이 잘라 객체 저장소에 올리고 `media_clip`에 기록한다(얼굴 흐림 없음, 11.5). 같은 위험 구간이 HIGH 에서 CRITICAL 로 오르면 새 클립을 만들지 않고 보존 표시만 붙인다. 또한 LIVE 의 R1\~R4 가 처음 CRITICAL 로 발생할 때(병합된 이벤트당 1회)는 판정 스레드와 분리된 비동기 스레드에서 같은 60초 압축 링 버퍼로부터 대상 관측 카메라 우선 최대 2대 × 2시점(이벤트 0\~500 ms 전, 3\~5초 전, 사후 프레임 제외)을 디코딩·JPEG 인코딩해 객체 저장소에 올리고(`EVENT_FRAME`) I1 `event_frame_ready` 를 보낸다(5.4, 12.3, `docs/design/vlm-rationale.md`). 버퍼에 구간이 다 없거나 구간 안에 빈칸이 있으면 지어내지 않고 기록에 남긴다. EC2 가 끊겨 업로드 주소를 받을 수 없으면 클립을 Tier 0 저장 위치(3.12)에 먼저 저장하고, 복구 후 업로드한다. 링 버퍼의 나머지 영상은 덮어써진다.

**상시 영상 조각.** Tier 0 서비스는 받은 영상을 카메라별로 일정 길이(초기값 1분) 조각으로 키프레임부터 디코딩 없이 잘라, 업로드 주소(`POST /api/uploads/sign`, 목적 `VIDEO_SEGMENT`)를 받아 객체 저장소에 올리고 I1 `video_segment` 로 기록을 보낸다(얼굴 흐림 없음, 삭제 예정일 = 자른 시각 + 14일, 11.5). 이벤트와 묶이지 않고 보존 표시가 없다. 구간 안 빈칸은 지어내지 않고 기록에 남긴다. 관리자는 `GET /api/videos` 로 구간을 찾아 조각마다 재생 주소를 받는다(12.6). 사고 구간을 오래 남기려면 이벤트 클립의 보존 표시를 쓴다(v1.3 수정 36, 팀 결정 2026-10-29).

## 5.2 3D 골격과 World 상태

- 카메라 간 연결: 바닥 투영 위치 + 다시점 기하 일관성으로 같은 사람을 묶고, 전체 1:1 배정으로 World ID를 유지한다(MV3DT 방식). 참조 알고리즘은 Chen et al. CVPR 2020(기존 3D 에 2D 를 직접 매칭하며 반복 추적)과 RapidPoseTriangulation(학습 없음, 이전 프레임 3D 를 재투영해 후보를 거름)이다. 한 시각의 카메라 간 묶기는 카메라를 차례로 배정하지 않고, 같은 카메라 금지·완전 연결(기하가 반대하는 쌍이 하나라도 있으면 합치지 않음) 제약을 둔 최선 우선 병합으로 한다(앞 카메라의 약한 연결이 먼저 굳어 뒤 카메라의 반대 근거를 가리는 오병합을 막는다). 1:1 배정(헝가리안)은 시각 사이 클러스터를 잇는 데 쓴다. 학습형 다시점 3D pose(VoxelPose·MvP·TEMPO 류)는 새 카메라 배치에 일반화가 약하다는 보고(MVGFormer, CVPR 2024)가 있어 쓰지 않는다(16장).
- 삼각측량: 2대 이상에서 보인 관절만 삼각측량한다. 1대 이하인 관절은 `joint_visibility = false`로 표시하고 지어내지 않는다.
- World 위치: 골반 관절의 삼각측량 결과를 우선 쓰고, 발 접지점이 보이면 함께 쓴다. 2대 이상 유효 관측이 없을 때 바닥 투영(발점)은 발의 접지 표면이 검증된 경우(바닥 또는 등록된 작업면)에만 쓴다. 지지 표면을 모르면 Z를 0으로 가정하지 않고 z_validity = UNAVAILABLE로 두며, 높이 규칙(R2·R3)은 “확인 필요”로 처리한다. 고소 위치였던 사람이 가려지면 마지막 유효 높이와 커지는 불확실성을 유지하고, 바닥 위치로 바꾸지 않는다. 바닥 투영은 일반적인 3D 관측 실패의 대안이 아니다.
- 출력: `world_track_state`(XYZ, 불확실성, 속도, 관측 상태, 시간 필드, 기여 카메라)와 `skeleton_3d`
- root 위치의 정본은 이 계층이다. HMR 모델 결과가 이 위치를 덮어쓰지 않는다.

**접지 추정(ContactEstimator).** 발목 위치(`ankle_position`)를 접지점(`ground_contact_point`)으로 취급하지 않는다. ContactEstimator가 발뒤꿈치·발끝 keypoint(23점 모델, 5.1), 발목 높이와 정지 여부, 다시점 발목 Z, 등록된 작업면 높이(7.5)를 근거로 접지 여부와 지지 표면을 추정하고, 근거가 부족하면 `support_surface = UNKNOWN`으로 둔다. 23점 모델 채택 전(COCO 17관절)에는 발목까지만 있으므로 발목 근거만 쓴다. 바닥 투영과 높이 규칙(R2·R3)은 이 결과를 쓴다. 발목이 자주 가려지면 UNKNOWN 이 많아질 수 있으므로 그 비율을 G2 에서 잰다(부록 D).

- 근거는 관절 유효성 게이트가 VALID 로 낸 발목뿐이다(UNCERTAIN·UNAVAILABLE 발목, HMR·정적 3D·VLM 결과는 쓰지 않는다). 접지점 Z 는 발목 Z 에서 빼서 만들지 않고 등록된 상판 높이(바닥은 0)를 쓴다.
- 새 지지 표면(처음 잡는 표면 포함)은 접촉 확인(디딤발 정지 또는 두 발목이 같은 표면 높이)이 이어져야(초기값 2번) VALID 가 된다. 발목 하나의 오연결로 단상 위 사람을 바닥으로 바꾸지 않게 한다. 높이가 맞는 표면이 둘 이상이면 애매로 보고 접지점을 비운다.
- **접지 추정 분해능.** 발목만으로는 약 8 cm 이하 미등록 상판을 바닥과 구별하지 못한다(발목 높이 개인차와 삼각측량 오차 안). 바닥 접지점의 높이 불확실성(σz 초기값 3 cm)은 그 대부분을 2σ 로 덮는 값이다. 10 cm 이상 미등록 상판 위의 발목은 바닥 높이 띠 밖이라 UNKNOWN 이다. 그래서 높이 규칙에 쓸 상판은 등록해야 한다(7.5).
- **가림 동안 유지.** 발목 근거가 없으면(골격 없음, VALID 발목 없음, 보인 발목 하나가 표면보다 높음) 마지막 유효 지지 표면과 접지점을 유지한다. 이때 지지 표면 출처는 inferred, `z_validity`·`contact_validity` 는 UNCERTAIN 이고 접지점 불확실성이 시간에 따라 커진다. 바닥으로 바꾸지 않는다. 마지막 발목 근거 뒤 3초(초기값)가 지나거나, 발목·골반이 유지 중인 표면과 모순되거나(표면 높이 띠보다 낮은 발목, 골반이 작업면 범위 밖, 골반 높이가 접촉 확인 때보다 크게 바뀜), 그 작업면이 구성에서 빠지거나 높이가 바뀌거나, ID 교정이 있으면 유지를 끊고 UNKNOWN(접지점 비움)으로 둔다. 무기한 유지하지 않는다.
- 임계값은 모두 초기값이고 G2 에서 조정한다.

**추적 3계층.** 하나의 Tier 0 서비스 안에서 중앙 집중형으로 동작한다.

| 계층 | 담당 | 구현 |
|---|---|---|
| Local Tracker | 같은 카메라 안에서 프레임 간 사람 연결 | 카메라별 독립 TrackTrack(기본). 설정 전환: ByteTrack(단순 기준), BoT-SORT + ReID(가림·재등장 개선용). 고정 카메라라 어느 설정이든 카메라 움직임 보정을 끈다(`gmc_method: none`) |
| Cross-view Association | 네 카메라의 트랙이 같은 사람인지 판단 | MV3DT 원칙의 Python 구현. 근거: World 위치(유효 접지·다시점 관절), 1\~2초 궤적·속도, 관절 재투영·에피폴라 오차, 필요 시 ReID, 가림·불확실성 |
| World Track Manager | 최종 World ID, XYZ, 속도, 가림·재관측 | World 칼만 필터, tracklet 이력, 늦은 재연결(late re-association), ID 교정 |

- 같은 카메라의 서로 다른 두 검출을 한 World ID에 동시에 묶지 않는다. World XY가 가깝다는 이유만으로 합치지 않는다.
- 매칭이 애매하면 합치지 않고 새 ID를 만들거나 `IDENTITY_UNCERTAIN`을 표시한다. 잘못 합친 ID보다 갈라진 ID가 덜 위험하다.
- Track 생명주기 TENTATIVE → CONFIRMED → OCCLUDED → LOST는 관리용 속성이며, 위험 판단용 관측 상태(OBSERVED/PREDICTED/UNKNOWN)와 별도다. ID 확신과 위치 확신도 별도로 관리한다.
- Local Tracker 선택 근거: TrackTrack(CVPR 2025)은 추적 관점 연결(TPA)과 추적 인지 초기화(TAI)로 혼잡·가림에서 중복 ID 와 잘못된 연결을 줄였다고 MOT17·MOT20·DanceTrack 에서 보고됐다. 공식 벤치마크로 답이 있으므로 크기 비교처럼 별도 비교 실험은 하지 않고, 교실 ID 전환·IDF1 은 G2·A0 측정으로 확인한다. G2 ID 유지가 실패하면 A2 에서 BoT-SORT + ReID 로 넘어간다.
- ReID는 보조 근거다. 비슷한 복장이 많으면 외형만으로 구분할 수 없으므로 기하와 궤적이 주 근거다.
- DeepStream MV3DT를 직접 붙이지 않고 원칙(공유 World 좌표, tracklet 연결, 가림 상태 관리, 늦은 재연결)을 Python으로 구현한다.
- Pod를 여러 개로 늘리면 World Association 상태가 나뉘므로, 확장 시 카메라·시간 단위 분할과 상태 소유권을 따로 설계한다.

**계산 순서.** 카메라 간 연결과 삼각측량, 접지 추정이 서로를 기다리지 않도록 순서를 고정한다.

1. 카메라별 Local Tracklet(2D keypoint, 공통 시각으로 시간 보간)
2. 연결 후보 생성: 에피폴라 오차, 시간, 기존 World Track 궤적(이전 프레임 3D 재투영), 임시 바닥 가설(두 시점의 발목 시선이 높이 0\~1.0 m 수평면과 만나는 점 사이 최소 거리. 단상·책상 위 사람을 담으려고 바닥만 보지 않는다. 비용에만 쓰고 탈락 근거로는 쓰지 않는다)
3. 후보별 삼각측량과 검증: 재투영 오차, 시선각, 관절 일관성(관절 유효성 게이트)
4. ContactEstimator: 지지 표면과 접지 신뢰도
5. 최종 연결과 World Track 갱신

카메라 간 묶기(2·3단계)의 쌍별 기하 호환성 검사에서는 손목·발목·엉덩이 등 말단·하체 관절의 검출 흔들림이 쌍 전체를 기각시키지 않도록, 쌍 기하 오차를 관절 잡음 배율(`KEYPOINT_NOISE_SCALE`)의 역수를 정규화 가중치로 쓴 가중 평균(에피폴라 거리)과 가중 중앙값(2-view 삼각측량 잔차)으로 모은다(픽셀 문턱과 완전 연결·경계 보류 규칙은 그대로 둔다). 임시 바닥 가설은 후보 생성에만 쓰고 안전용 접지나 Z로 쓰지 않는다. 4단계에서 접지가 검증되지 않으면 `z_validity`와 `support_surface`를 UNKNOWN으로 둔다.

**ID 교정 기록.** World ID를 조용히 덮어쓰지 않는다. 병합·분할·교정마다 `identity_revision`을 올리고 별칭(alias)과 교정 이력을 남기며, 이벤트에는 발생 당시의 원본 World ID를 보존한다. ID 교정은 이력과 리플레이를 고칠 수 있지만 진행 중인 위험을 자동 해소하지 않는다.

**늦은 재연결과 ID 교정.** 지금 Tier 0 는 같은 ID 로 다시 잇기, 병합, 자동 분할을 한다. 운영자 수동 교정은 아직 없다(19.1).

- **2대 근거.** 근거는 카메라 안 로컬 트래커가 이어 온 로컬 트랙 연결 이력과 위치뿐이다. 외형·얼굴·재식별은 쓰지 않는다(2장). 로컬 트래커는 옆 사람에게 옛 ID 를 넘기는 ID 전환을 막지 못하므로 카메라 한 대의 옛 로컬 트랙은 같은 사람의 근거가 아니다. 서로 다른 카메라 2대 이상의 로컬 트래커가 같은 옛 Track 의 로컬 트랙을 이어 왔을 때만 근거로 센다. 위치만으로는 잇지 않는다.
- **같은 ID 로 다시 잇기.** CONFIRMED 였다가 LOST 가 된 Track 은 마지막 측정부터 10초(초기값) 소실 후보로 남는다(`world_state` 에는 내지 않는다). 새로 생길 Track 의 옛 로컬 트랙이 모두 한 소실·가림 Track 의 것이고, 2대 근거, 도달 거리(마지막 위치에서 0.5 m + 2 m/s × 공백, 6.1 속도 상한), 그 마지막 위치 1.5 m 안에 다른 소실·가림 Track 없음(교차로 로컬 트랙이 넘어갔을 수 있음) 등을 모두 채우면 새 ID 대신 그 Track 에 붙인다. ID 가 바뀌지 않으므로 `identity_revision` 은 그대로다.
- **근거가 모자라면** 새 ID 를 주고, 옛 Track 이 소실 후보로 남아 있는 동안 새 ID 에 `IDENTITY_UNCERTAIN` 을 붙인다. 옛 Track 의 위험 이벤트는 관측되지 않으므로 UNVERIFIABLE 로 남고 해소되지 않는다.
- **병합.** 이미 새 ID 를 받은 Track 에 붙은 클러스터에서 옛 Track 의 로컬 트랙이 2대 이상 보이는 시각이 3번(초기값) 쌓이면 먼저 만든 ID 로 합친다. 직전 근거가 2초 넘게 끊기거나 반대 근거가 나오면 처음부터 센다.
- **병합 금지 반증.** 같은 시각 같은 카메라의 서로 다른 두 검출이 가리키는 두 Track 은 한 사람일 수 없으므로 병합 금지 쌍으로 기록하고 다시 합치지 않는다(위치 갱신과 상관없이 기록한다). 병합하면 사라지는 ID 의 금지 쌍은 남는 ID 로 이어진다.
- **첫 관측부터 도달 거리.** 병합의 도달 거리는 새 ID 의 위치 측정 전부(옛 Track 의 마지막 관측 뒤 첫 관측부터)와 이번 시각으로 잰다. 지금 시각만으로 재면 시간이 지나기만 해도 거리 조건을 통과하기 때문이다. 한 번이라도 갈 수 없는 곳에서 관측됐으면 병합 금지 쌍이 된다.
- **교정 결과.** 남는 ID 는 먼저 만든 ID 이고 `identity_revision` 은 두 ID 중 큰 값 + 1, 사라지는 ID 는 별칭(`aliases`)에 뒤로 붙고 Track 이 살아 있는 동안 빠지지 않는다. 진행 중 이벤트는 남는 ID 로 다시 키를 달되 원본 World ID 를 보존하고 해소하지 않는다(교정은 그 시각 판정보다 먼저 적용한다). 잇거나 합친 Track 은 자기 로컬 트랙만으로(2대 이상) 위치가 갱신된 시각이 3번 쌓일 때까지 `IDENTITY_UNCERTAIN` 이고, 가려져 갱신이 없으면 시간만으로 풀지 않는다.
- **잔여 위험.** 2대 기준은 한 카메라의 우연한 ID 전환은 막지만 독립 근거는 아니다. 두 카메라의 로컬 트래커가 같은 상황에서 함께 사라진 사람의 옛 ID 를 다른 사람에게 붙이면 잘못 이을 수 있고, 옛 사람의 진행 중 경보가 새 사람의 관측으로 해소될 수 있다. 두 카메라가 로컬 트랙을 World LOST(3초)보다 오래 함께 유지하고 같은 다른 사람에게 붙여야 하므로 드물다. 근거가 모자란 새 ID 의 `IDENTITY_UNCERTAIN` 은 정상 해소를 최대 약 11초 늦출 수 있다(신규 발생·현장 경보는 늦지 않는다).
- **분할.** 한 World ID 의 로컬 트랙이 서로 다른 카메라 2대 이상에서 **같은 시각 같은 카메라의 두 검출로** 갈라지면(병합 금지 반증과 같은 근거: 한 사람일 수 없다) 그 ID 는 두 사람을 묶고 있었다. 갈라진 쪽은 사람을 빠뜨리지 않도록 곧바로 새 ID 로 추적하고 분할 후보로 둔다. 두 골반이 0.35 m(같은 사람 두 ID 기준과 같은 경계) 넘게 떨어진 근거 시각이 3번(병합과 같음) 쌓이면 분할한다. 한 카메라만 갈라짐(로컬 ID 전환과 구별 불가), Cross-view 가 불확실로 표시한 클러스터, 0.35 m 안(같은 사람일 수 있음)은 분할 근거가 아니다. 한쪽이 가려진 시각은 세지도 버리지도 않고, 근거가 2초 넘게 끊기면 분할하지 않는다(모르면 그대로). 원래 ID 는 갈라짐을 처음 본 시각에 예측 위치에 가까운 쪽에 남고, 두 ID 의 `identity_revision` 을 둘 중 큰 값 + 1 로 함께 올린다. 별칭은 바꾸지 않는다. 갈라져 나간 새 ID 에만 원래 ID 를 `split_from` 으로 싣는다(`world_state` 2.1.0, 분할을 확정한 시각부터 그 ID 가 살아 있는 동안 같은 값, 병합으로 사라지면 함께 사라짐). 체크포인트에는 넣지 않는다(재시작하면 모두 새 ID). 두 ID 는 병합 금지 쌍이 되어 다시 합치지 않고, 후보인 동안과 분할 뒤 일관성 확인(자기 로컬 트랙만으로 2대 이상 3번 갱신)까지 둘 다 `IDENTITY_UNCERTAIN` 이다.
- **분할과 진행 중 이벤트.** 분할 전 이벤트가 둘 중 누구의 것인지 모르므로 둘 중 하나로 지어내지 않는다. 이벤트는 원래 ID 에 그대로 두고(원본 World ID 보존, `identity_revision` 증가로 ID 교정 갱신이 나간다) 갈라져 나간 ID 를 분할 상대로 기억해, 두 ID 가 모두 유효하게 관측되고 같은 규칙의 판정이 어느 쪽에도 없을 때만 해소를 센다. 분할 상대는 분할 계보 전체다: 상대가 다시 갈라지면 새로 갈라져 나간 ID 도 상대가 되고, 상대가 병합되면 남는 ID 로 잇는다. 갈라져 나간 ID 에 같은 위험이 판정되면 새 이벤트다. 계보 안의 ID 하나라도 관측되지 않으면(소실 포함) 그 이벤트는 확인 불가로 남는다.
- **분할 잔여 위험.** 두 사람이 서로 다른 카메라에만 보이다 한 ID 로 합쳐진 뒤 다시 서로 다른 카메라 쌍으로 갈라지면 같은 카메라의 두 검출이 없어, Cross-view 가 한 사람을 두 클러스터로 가른 경우와 위치로만 구별해야 한다. 이때는 분할하지 않고 지금처럼 새 ID 만 만든다(교정 기록 없음).
- 수치(10초, 1.5 m, 2대, 3번, 2초, 0.35 m)는 초기값이고 G2·A0 녹화로 조정한다.

**World 위치의 정의.** 사람의 위치는 하나의 `position`으로 뭉뚱그리지 않고 아래처럼 나눈다.

| 필드 | 의미 | 없을 때 |
|---|---|---|
| `pelvis_xyz` | 삼각측량한 골반 관절 위치 | 2대 이상 유효 관측이 없으면 비움 |
| `position_xy` | 구역 판정용 수평 위치. 기본은 골반 XY | 골반이 없으면 검증된 접지점 XY, 둘 다 없으면 예측값(PREDICTED): 마지막 유효 측정 시각(t_last_valid)의 필터 위치를 그대로 두고 불확실성만 공백만큼 키운다(2.0 m/s × 공백). 속도로 옮기지 않는다(현재 위치 예측은 Risk Engine 시간 모델이 한 번만 한다, 6.1) |
| `ground_anchor_xyz` | 검증된 지지 표면 위의 위치(ContactEstimator) | 접지 미확인이면 비움. Z=0으로 채우지 않음 |
| `surface_source` | 지지 표면(접지점)의 출처: observed(이번 시각 발목 근거), inferred(가려진 동안 마지막 유효 지지 표면 유지) | 접지점이 없으면 싣지 않음. 메시 표면 출처와 이름만 같은 다른 필드(부록 A) |
| `support_surface_id`, `support_surface_validity` | 서 있는 면(바닥, 등록 작업면)과 그 유효성 | UNKNOWN |
| `head_z` | 머리 꼭대기 높이 추정. COCO 17관절에는 머리 꼭대기가 없으므로 삼각측량한 양쪽 귀·눈 중점의 높이에 고정 오프셋(초기값, G2 에서 조정)을 더한다. 관절 유효성 게이트가 VALID 나 UNCERTAIN 으로 낸 값을 싣고(접지점과 `z_validity` 의 관계와 같음), 값이 있어도 `head_z_validity` 를 함께 읽는다. Tier 0 관측(observed) 귀·눈으로만 만든다 | `head_z_validity` 가 UNAVAILABLE 이면 비움 |
| `head_z_validity` | 게이트가 낸 `head_z` 유효성. VALID(VALID 귀·눈으로 만든 값), UNCERTAIN(VALID 귀·눈이 없어 UNCERTAIN 귀·눈으로만 만든 값, 확정 근거 아님), UNAVAILABLE(좌표 있는 귀·눈 없음, 이번 시각 관측 없음, 값 비움) | 이전 버전 송신 측은 싣지 않음(그때 `head_z` 가 비면 이유를 모름). `world_state` 1.x 는 UNCERTAIN 값을 싣지 않았다 |

- `head_z` 의 정답은 줄자로 잰 키(신발 신은 상태) + 서 있는 면 높이(바닥 0, 단상 40cm)로 하고, 똑바로 선 프레임에서만 비교한다. G2 머리 높이 오차와 4.4 CALIBRATED 검산이 같은 정의를 쓴다.
- 높이 규칙(R2·R3)은 `ground_anchor_xyz`의 Z(서 있는 면 높이)를 쓰고, 없으면 “확인 필요”로 처리한다. 낙상(R4)은 `head_z` 변화를 쓴다.
- `head_z_validity` 가 UNCERTAIN 인 `head_z` 는 확정 근거가 아니다(아래 관절 유효성 게이트와 같은 규칙). 위험 규칙은 이 값을 쓰면 “확인 필요”(`JOINT_UNCERTAIN`)를 붙이고, 이 값만으로 ‘구역에 들어가지 않았다’·‘낙상이 아니다’ 같은 판정 없음을 확정하지 않는다. 그래서 구역 진입(R1)·진입 예측(R5)은 UNCERTAIN `head_z` 를 위 끝으로 쓰지 않고 모르는 것으로 보며(Z_UNKNOWN), 낙상(R4)만 이 값으로 판정하고 “확인 필요”를 붙인다. 낙상 의심이 난 뒤 머리가 UNCERTAIN 값으로만 높아지면 R4 는 해소하지 않고 유지하며, VALID 머리 근거로 일어나 있는 것이 확인된 뒤에 해소 유지 시간을 센다.
- 구역 진입(R1)은 구역 유형에 따라 판정한다(8.2). GROUND_FOOTPRINT는 `position_xy`와 수평 불확실성으로, VOLUME_3D는 사람이 차지하는 높이 범위(서 있는 면 Z부터 VALID 관절 중 가장 높은 Z까지, 없으면 `head_z`까지)와 구역 높이 범위의 겹침을 3D 불확실성과 함께 본다.
- 아바타는 접지가 확인되면 발을 `ground_anchor_xyz`에 맞추고, 아니면 `pelvis_xyz` 기준으로 배치하며 “접지 미확인”을 표시한다(13.2).

**3D 관절 유효성 게이트.** 두 대에 보인다는 것과 그 관절의 Z가 안전 판단에 충분히 정확하다는 것은 다르다. 관절마다 아래 항목으로 VALID / UNCERTAIN / UNAVAILABLE을 정한다.

- 관측 카메라 수(시간 보간 후 유효한 카메라만)
- 재투영 잔차
- 두 시선 사이 각도(작으면 깊이·높이가 불안정)
- 시간 일관성(속도 상한, 뼈 길이 변화)
- 삼각측량 불확실성
- 2대 관측 경쟁 후보: 관측 카메라가 2대뿐이고 그 관절의 에피폴라선 위에 경쟁 후보(다른 사람의 같은 관절)가 있으면 VALID 로 두지 않는다. UNCERTAIN 으로 두고 그 연결을 `IDENTITY_UNCERTAIN` 후보로 표시한다. 2대 영역 오연결률은 G2 에서 잰다.

위험 규칙은 VALID 관절만 확정 근거로 쓴다. UNCERTAIN이면 등급은 유지하고 “확인 필요”(`JOINT_UNCERTAIN`, 7.1)를 붙인다. `joint_visibility`는 이 게이트의 입력 중 하나이며, I1의 skeleton에 `validity`를 함께 싣는다.

## 5.3 정적 3D (설치 시 1회)

**선행 검증 — EXP-01.** 기존 M3 정적 배경 산출물을 바꾸기 전에 MapAnything Native로 깊이/점군/카메라 정보 → 깊이 정합·표면 복원·glTF → World 스케일·정렬 비교를 하나의 대형 실험으로 검증한다. 비교군은 Depth Anything 3(DA3NESTED-GIANT-LARGE-1.1)를 두 경로로 잰다(20.2, `docs/design/exp01-hybrid-depth.md`).

- (a) MapAnything 자세 고정 + DA3 자세 조건 깊이: MapAnything 자세·K 를 DA3 공식 `inference` 에 넣는다. 공식 `inference` 는 예측 자세를 입력 자세에 Umeyama 로 맞추므로 깊이 단위가 MapAnything 단위를 따른다. 배경 점 밀도를 높이는 용도이고 독립 축척 근거가 아니다. MapAnything 외부 모델 인터페이스(DA3 래퍼)는 입력 자세를 고정하지 않고 예측 자세를 내므로 이 경로에 쓰지 않는다.
- (b) 자세 없이 DA3NESTED 단독(미터 추정): 축척 교차 확인 후보이고 우선순위는 가장 낮다(4.3 스케일 근거의 모델 자체 추정).
- MoGe 단안 경로는 비교 큐에서 뺐다(Lead 결정 2026-10-26: DA3 와 역할이 겹치고, 한 장씩 추정이라 카메라별 축척 정합 부담이 크며, 축척 1순위는 실측 정물이다). G4 미달 때의 대체도 MoGe-3 에서 DA3 혼합 경로로 바꿨다(아래, Lead 결정·사용자 승인 2026-10-26).
- MapAnything 입력 해상도는 공식 기본 518(모델 입력 518×294)·긴 변 1036(1036×588)·1554(1554×868)·원본(2304×1296 → 2296×1288) 네 단계를 같은 입력·가중치로 비교하고, 보정용(바닥 지지 점·rms, 카메라 간 왕복 재투영)과 배경용(원본 px/점, 유효 비율, 점 수, 가장자리 선명도)을 따로 판정한다. 학습 해상도(518) 밖이라 높을수록 낫다고 가정하지 않는다(`docs/design/mapanything-input-resolution.md`).

G4 목표는 개발 교실 줄자 실측 대비 10cm다. Experiment는 재현성·실패 사례·렌더링·VRAM 지표를 함께 제출한다.

- 안전 판단용 Operational Geometry 정본은 보정으로 확정한 바닥 평면과 관리자가 등록한 정적 객체·작업면(보수적 OBB와 상판 높이, 7.5)·위험 구역이다. 정적 3D·BEV 평면도의 벽은 보기용이다.
- 사물(책상, 사물함)과 배경은 분석 워커의 I5 `static_reconstruct` 작업에서 MapAnything Native에 알려진 K·pose를 넣어 복원하고, Open3D TSDF 와 `texrecon` 으로 구운 텍스처 메시(`GLTF_VISUAL`)와 표면 출처 지도(`SURFACE_SOURCE_MAP`)를 객체 저장소에 올린다(2026-10-30 사용자 결정, `docs/design/worker-static-reconstruct.md`, S15P31A101-364).
- 산출물과 폴백: 기본 산출물은 텍스처 메시 glTF(`GLTF_VISUAL`)와 표면 출처 지도(`SURFACE_SOURCE_MAP`, `0` 미관측·`1` 보간·`2` 관측·`3` 추정 평면)이며, `texrecon` 실행 파일이나 `open3d` 가 없는 환경에서는 정점색 단순 메시 glTF 로 폴백한다. 작업 성공 콜백(`scene_output` 2.1.0)은 EC2 에서 `CANDIDATE` Scene 버전으로 저장되고, 관리자가 확인 후 명시적으로 활성화(`commit`)하면 서버 재기동 없이 현재 Scene 에 반영된다(12.5·12.6, `docs/design/scene-version-from-job.md`, S15P31A101-365). 관제가 끝나면 분석 워커가 Tier 0 의 완성 배경 묶음을 자동으로 제출한다(S15P31A101-403, `SIMAI_AUTO_STATIC_RECONSTRUCT`, 기본 켬). 조건은 모두 만족해야 하며 하나라도 모르면 내지 않는다: 묶음이 완성이고 그 보정이 Tier 0 의 지금 활성 보정(PROVISIONAL·CALIBRATED), LIVE 아님(3.2 접수 판단과 같고, 표시 파일이 없으면 정상 종료 기록이 있을 때만 관제 없음), 마지막 LIVE 뒤 300초(초기값), 낸 적 없는 묶음, 자동 제출 작업 중 끝나지 않은 것 없음(한 번에 하나). 사진·보정 문서를 `STATIC_RECONSTRUCT_INPUT` 으로 올린 뒤 `POST /api/worker/scene-jobs/static-reconstruct` 로 등록하고(12.5), 결과는 마찬가지로 `CANDIDATE` 로만 붙는다. 실패는 지수 백오프로 다시 해 보고, FAILED·TIMED_OUT 으로 끝난 묶음은 자동으로 다시 내지 않는다. 운영 흐름은 로비 세션 뒤 `simai-bootstrap after-live`(3.12)다.
- MapAnything이 G4에서 실패하면 DA3 혼합 경로(MapAnything 자세 + 원본 해상도 깊이, 위 (a), S15P31A101-283) + 실측 정물 축척(S15P31A101-100)을 시험하고, 그래도 기준 미달이면 관리자가 등록한 단순 형상(바닥 평면 + 보수적 OBB)을 쓴다. 최종 대체 경로는 관리자 등록 단순 형상이다.
- 안전 판단용 사물 형상은 보수적 OBB로 쓴다. 정적 3D 는 R2·R3 가장자리 판정에 쓰지 않는다(7.5).

**촬영 조건과 사람 지운 배경 누적.** 정적 3D용 입력은 두 경로다. (1) 관제 중 Tier 0 가 이미 디코딩한 원본 해상도 BGR 프레임과 사람 검출 상자를 별도 비동기 스레드(`tier0-clean-background`, 큐 1장·포화 시 버림)로 받아 사람 상자(여유 확장) 바깥 픽셀만 카메라별 표본 버퍼(최소 20장·최대 60장)에 쌓고, 노출된 픽셀의 시간 중앙값으로 사람 지운 정적 배경(`CLEAN_BACKGROUND`, 미노출 비율 < 2% 완료 기준)을 만들어 4대가 모두 준비되면 `$SIMAI_ROOT/state/clean-background/<calibration_version>/bundle-<uuid>/` 와 `status.json` 으로 원자적으로 내보낸다(DRIFTED 귀속 카메라나 보정이 바뀐 카메라는 해당 카메라 버퍼만 비움, `docs/design/clean-background-accumulator.md`, S15P31A101-358·-363). (2) 설치 시 단일 시점 프레임(`FRAME`)을 넣을 때는 분석 워커 `static_reconstruct` 의 `prepare` 단계에서 `YOLO26x-seg` 사람 분할 마스크로 사람 영역을 지우고, `CLEAN_BACKGROUND` 입력이면 분할 추론을 건너뛴다(`docs/design/worker-static-reconstruct.md`).

**복원 후처리(`static_reconstruct`).** 분석 워커는 LIVE 관제가 아닐 때만 `static_reconstruct` 작업을 대여해 별도 자식 프로세스 그룹에서 `download` → `prepare`(왜곡 펴기, `FRAME` 입력만 `YOLO26x-seg` 마스크) → `mapanything`(known-K 점군·신뢰도) → `bake`(Open3D TSDF 표면 복원 → `texrecon` area 1회 텍스처 굽기 → 구멍 규칙·`SURFACE_SOURCE_MAP`, 도구 부재 시 정점색 glTF 폴백) → `measure`(스툴 정물 축척 점검, 4.3) → `upload`(`GLTF_VISUAL`, `SURFACE_SOURCE_MAP`, `metrics.json`, `run_record.json`, 로그) 순서로 실행하고 `scene_output` 2.1.0 을 돌려준다(`docs/design/worker-static-reconstruct.md`). 이 결과는 보기용 Visual Geometry다. 안전 판단용 Operational Geometry는 보정으로 확정한 바닥 평면과 등록 정적 객체 OBB·위험 구역으로 만든다.

## 5.4 VLM·LLM

- 역할: 설명과 제안만 한다. 경보 판단 권한은 없다(원칙 6).
- **VLM 모델:** NVIDIA Cosmos3-Nano(16B)의 Reasoner 모드를 쓴다(OpenMDW 1.1). vLLM 0.21.0 과 플러그인 `vllm-cosmos3`(커밋 고정)의 OpenAI 호환 API 로 서빙한다. vLLM 서버는 Tier 0 와 같은 가상환경(torch 2.11.0, CUDA 13.0, 3.12)의 별도 프로세스이고, Tier 0 와 같은 GPU(48GB 이상, 80GB 권장, 3.12)에 GPU 메모리 예산(3.2) 안에서 올린다. 가중치는 이해(Reasoner) 탑과 비전 인코더 약 31.5GB 만 받는다(생성용 `vae`·`sound_tokenizer` 제외, 빠져도 뜨는지는 다음 GPU 세션에서 확인, 19.1). G7 은 이 모델의 합격 여부만 판정한다. Cosmos3-Super(64B)는 80GB 에 Tier 0 와 함께 올라가지 않아 제외한다(확장 후보, 부록 C).
- **LLM(텍스트 생성):** TBM 보고서 문장, RAG 답변, 운영자 질의응답처럼 텍스트만 다루는 생성은 외부 API “GPT 6.1 sol”(모델 이름 `gpt-6.1-sol`)을 쓴다. SSAFY GMS(OpenAI API 중계, 엔드포인트 `https://gms.ssafy.io/gmsapi/` + OpenAI 경로, 형식은 OpenAI 공식 레퍼런스와 같음)를 거쳐 부른다. 호출 방식은 GMS 공식 방식인 OpenAI Responses API(`POST …/v1/responses`, `store: false` 로 제공사 쪽에 초안을 남기지 않음)가 기본이고, 설정 `SIMAI_LLM_API_STYLE=chat` 이면 Chat Completions 로 부른다(S15P31A101-285).
  - 보내는 것은 텍스트(규칙 계산 결과, 법령 조항, 이벤트 요약, 그리고 개인정보가 아닌 표준 공종 코드·이름 `work_type`)뿐이다. 영상·이미지·얼굴·실명은 보내지 않으며, TBM 작업명(`work_unit.name`)·참석 인원(`planned_people`)·반장/담당 조 이름(`lead_team`)도 실명 혼입 방지를 위해 외부 LLM 에는 보내지 않고 서버가 보고서·회의록 머리말에만 붙인다(계약 반례 `job_request.tbm_report_person_name.json` 원칙 유지, `docs/design/tbm-legal-graph.md`).
  - 호출은 EC2 의 Python 컨테이너(`deploy/risk-engine`) 안에서만 한다(GPU·Pod 없이 언제든 생성 가능, I5 분석 워커 `tbm_report` 작업은 폐기 예정, v1.3 수정 49). 프롬프트와 코드 기반 4단계 생성·검증 파이프라인(1단계 후보 수집: 규칙 태그 `R1`~`R7` + `pg_trgm` 키워드 + `pgvector` cosine 하이브리드 검색 후 참조 엣지 1단계 확장 → 2단계 사전 거름: 허용 조항·지침·사례 ID 목록 확정 → 3단계 초안 작성: 외부 LLM JSON 출력 1회 호출 → 4단계 코드 검증: 인용 ID 허용 목록·본문 미허용 조문 번호·확률/퍼센트 표현·등급 불변성 검사, 다중 LLM 호출 에이전트 아님, `docs/design/tbm-legal-graph.md`)을 한 곳에 둔다.
  - 응답은 섹션·문단별 인용 ID(`citations[]`)를 담은 JSON 으로 받는다. 허용 목록(`allowed_citation_ids`)에 없는 ID 를 인용했거나 본문에 허용 목록 밖의 `제N조`·`KOSHA GUIDE` 번호를 적었거나 정해지지 않은 값(등급 등)을 넣었거나 확률·퍼센트로 표현한 초안은 4단계 코드 검증에서 거부하고, 위반 사유를 붙여 같은 요청 안에서 최대 1회 재작성한다. 재작성본도 검증에 실패하면 보고서 생성은 즉시 실패한다. 위험 등급은 입력값 그대로 결과에 옮겨 LLM 이 바꾸지 못한다.
  - 호출 설정: `temperature` 는 보내지 않는다(이 모델은 기본값만 받는다). 응답 대기 상한(기본 60초)은 작업 시간 제한 안에서 두 번 부를 수 있게 둔다.
  - API 키(`SIMAI_LLM_API_KEY`)는 비밀 값(EC2 `.env`)이다(14장).
  - SSAFY GMS 를 거쳐 OpenAI(국외)로 텍스트만 보낸다(11.5).
- **법령 지식 그래프와 임베딩(RAG):** PostgreSQL 에 건설안전 법령 지식 그래프(`rag_node`·`rag_edge`, 11.3, `docs/design/tbm-legal-graph.md`)를 두고, 노드 텍스트와 질의를 같은 모델로 벡터화해 하이브리드 검색한다(v1.3 수정 49). 모델은 `Qwen/Qwen3-Embedding-0.6B`(Apache-2.0) dense 1024차원, float32, L2 정규화, cosine 이다(이전 `BAAI/bge-m3` 대체). 문서·질의에 같은 고정 revision·설정을 쓰고, 문서 임베딩 입력은 조문 맥락 유실을 막기 위해 `"[법령명 조문(제목)] 본문"` 형식을 쓴다. 법령 조문·지침·사례 노드(`rag_node`, 조 단위 기본·1,000자 초과 시 항·호 분할)와 표준 질의 템플릿(`rag_query_template`)은 시드 적재 때 미리 임베딩해 두고, 비정형 실시간 질의는 EC2 Python 컨테이너 CPU 에서 임베딩한다. 검색은 규칙 태그(`rule_tags`, `R1`~`R7`) + `pg_trgm` 키워드 매칭 + `pgvector` cosine 유사도를 결합한 하이브리드 검색 뒤 `rag_edge`(참조·준용·위임·상하위·별표·방호조치 연결, 종류 값은 `docs/design/db-tables.md`)를 1단계 확장해 상위 근거를 함께 수집하며, 결과 서브그래프(`subgraph`)와 4단계 실행 상태(`steps`)를 보고서와 함께 저장·반환한다. 외부 무거운 그래프 프레임워크(MS GraphRAG, LightRAG, Neo4j, LlamaIndex 등)는 도입하지 않는다. 영상·이미지는 넣지 않는다.
- 용도:
  1. R1\~R4 이벤트 근거 설명(VLM 빠른 경로: 이벤트 시점 프레임 + 직전 3\~5초 + 구조화 상태, G7의 5초 목표 대상). MVP 에서는 CRITICAL 이벤트에만, 병합된 이벤트당 1회 실행한다. Tier 0 가 추론에 이미 사용한 디코딩 프레임을 카메라별 작은 링에 참조로 보관하고, 최대 2대 × 2시점(0\~500 ms 전, 3\~5초 전)을 고정해 판정 lock 밖의 제한 스레드 풀에서 JPEG·서명·업로드한 뒤 I1 `event_frame_ready` 를 보내면(S15P31A101-328·-378, 클립용 60초 압축 링은 유지), EC2 `VlmRationaleIngestor` 가(LIVE·CRITICAL·비감사·관측 시각 5초 이내·중복 없음) `vlm_rationale` 작업(`VLM_FAST`, `timeout_ms=5000`, `max_attempts=2`, `deadline_at = observation_time + 5000 ms`, `face_policy=BLURRED`)을 등록하고 성공 콜백 때 `vlm_assessment`(G7 측정용 `event_observed_at`·`event_to_rationale_ms` 포함) 저장과 `risk_event` 투영·`/topic/events` 발행을 수행한다(S15P31A101-329). 분석 워커는 `proposed_severity` 가 입력 이벤트의 현재 등급보다 높을 때만 남기고 같거나 낮으면 `null` 로 비우며 사유 코드 `NOT_UPWARD` 를 로그에 남긴다(CRITICAL 입력은 더 높은 등급이 없어 늘 `null`, S15P31A101-273, `docs/design/vlm-rationale.md`).
  2. 사고·아차사고 구간 요약(VLM 사후 경로: 이벤트 전후 20초 클립, F-10 리플레이 연계). M3 이다. 관리자가 이벤트 상세·리플레이에서 요청하면(`POST /api/events/{id}/summary`) EC2 가 `incident_summary` 작업을 등록한다(분석 워커 처리기 `services/worker/incident_summary.py`, VLM 설정이 있을 때 등록, S15P31A101-271). 상향 의견은 내지 않고 우선순위는 보고서와 같다(3.2).
  3. TBM 보고서·일일 일지(규칙 계산 결과 + 해당 구역 최근 `risk_event` 이력 요약 + 법령 지식 그래프 하이브리드 검색·1단계 확장 + 외부 LLM 4단계 생성·검증). EC2 가 Python 컨테이너(`deploy/risk-engine`)로 PLANNED 계산과 보고서 생성을 한 번에 처리하고(GPU·Pod 불필요, I5 `tbm_report` 폐기 예정), 보고서 본문·인용과 함께 근거 서브그래프(`subgraph`)·실행 단계(`steps`)를 돌려준다. 일일 일지는 같은 파이프라인의 `report_kind` DAILY 다(8.3, 12.2, 12.6, v1.3 수정 49).
  4. 정적 공간 변화 의견(확장, 부록 C).
  5. 공정 맥락 진단(F-07)과 운영자 질의응답(LLM, 로그 조회 도구 사용). 둘 다 확장(부록 C).
- 맡기지 않는 일: PPE 판정·신호수 구별(YOLO26), 낙상 검출(3D 골격 규칙), 구역 판정(Risk Engine). 전용 모델과 규칙이 더 빠르고 수치로 검증되기 때문이다.
- 권한: 근거 설명과 상향 의견(proposed_severity) 제시만 가능하다. 이벤트 심각도는 규칙 결과로 유지하고, 상향은 검증된 규칙 조건이나 운영자 확인을 거쳐 적용한다. 하향·해소 불가.
- 운영자 확인 상향(M3): 관리자가 관제 화면 이벤트 상세(`EscalationControl`)에서 상향 의견을 승인하거나 거절한다(`POST /api/events/{id}/escalation`, `assessmentId` 는 숫자 ID 또는 `job_id`, S15P31A101-276·-367). 거절은 EC2 `vlm_assessment` 에 기록하고 `risk_event` 투영의 `proposed_severity` 를 비워 `/topic/events` 로 알린다. 승인하면 활성 이벤트이고 상향일 때 `event_escalation` 에 기록한 뒤 I1 `event_escalate` 를 보내고(EC2 는 등급을 직접 바꾸지 않음, 3.2), LIVE 이벤트의 단일 소유자인 Tier 0 가 `event_escalate_result`(`ACCEPTED`, `DUPLICATE`, 또는 `REJECTED` — `NOT_ACTIVE`·`NOT_UPWARD` 는 제안 해제, `JOURNAL_UNAVAILABLE` 은 같은 `escalation_id` 로 재시도 가능)와 같은 `event_id` 의 UPDATED 전이(`escalation`)를 보내면 EC2 가 `risk_event.severity` 와 `escalations[]` 를 갱신·발행한다(12.3, `docs/design/server-event-journal.md`). 올린 등급은 그 이벤트가 관측으로 해소될 때까지 바닥값이라 이후 규칙 판정이 낮추지 않고(규칙이 더 높이면 따른다), 재개(RESUMED)하면 비운다.
- 보고서 인용은 법령 지식 그래프 하이브리드 검색·1단계 확장으로 확정된 허용 목록(`allowed_citation_ids`) 안의 ID 만 허용하고 코드 4단계 파이프라인에서 자동 검사한다. 법령 코퍼스는 국가법령정보센터 Open API 로 수집 가능한 법령(산업안전보건법·시행령·시행규칙, 산업안전보건기준에 관한 규칙, 중대재해처벌법·시행령)을 먼저 적재하고, KOSHA GUIDE 와 중대재해 사이버안전박물관 재해사례는 재배포·API 이용 조건을 확인한 뒤 적재한다(11.3, `docs/design/tbm-legal-graph.md`).
- 큐: 이벤트 근거가 보고서보다 우선한다.

**VLM 입력 프레임과 시각 오버레이.** 이벤트 사진은 같은 GPU 인스턴스 안의 로컬 사본이 있으면 그것을 먼저 읽는다(S15P31A101-408). Tier 0 는 사진을 상태 폴더 `event-frames/<event_id>/` 에 두고 `event_frame_ready` 에 경로·sha256·크기(`local_copy`)를 실어 업로드를 기다리지 않고 알리며, 업로드는 보관용으로 뒤에서 계속한다. 워커는 경로가 상태 폴더의 `event-frames` 안(심볼릭 링크 밖은 거부)이고 크기·sha256 이 맞을 때만 사본을 쓰고, 아니면 객체 저장소에서 받는다(올라오는 중이면 남은 예산 안에서 짧게 다시 시도). 사본이든 객체 저장소든 받은 바이트는 같은 얼굴 처리 관문을 거친다(12.3·12.5). VLM에 넣는 이벤트 클립·프레임은 얼굴 영역을 흐림 처리한 뒤 넣는다(기본값). 근거 판정에 얼굴은 필요 없고, 안전모가 보이도록 머리 윗부분은 남긴다. 처리는 분석 워커가 VLM 작업(`vlm_rationale`·`incident_summary`) 안에서 VLM 호출 직전에 한다. 이벤트 클립은 흐림 없이 저장되므로(11.5) 프레임과 클립을 한곳에서 처리하고, Tier 0 실시간 경로에 부하를 더하지 않는다. 얼굴 영역은 pose keypoint(눈·귀·코)로 잡아 별도 얼굴 모델을 쓰지 않는다. EC2 는 작업 입력의 `face_policy` 를 BLURRED(또는 EXCLUDED)로 둔다. 처리 영역은 눈높이 조금 위부터 턱 아래까지라 이마 위·안전모는 남고, 눈이 보이지 않으면 보이는 점 양옆으로 넓히며, 얼굴 점이 하나도 없는 사람은 사람 상자 위쪽 띠(높이 5\~30%)를 처리한다. BLURRED 는 굵은 모자이크(영역 긴 변 3칸), EXCLUDED 는 같은 영역을 단색으로 칠한다(프레임 전체를 빼지 않는다). 디코드·검출에 실패한 프레임은 VLM 에 넘기지 않고(흐리지 않은 프레임으로 대신하지 않음), 남는 프레임이 없으면 작업이 실패한다. 얼굴 가림이 끝난 뒤에는 VLM 이 테이프로만 표시된 교실 바닥 구역이나 단상 경계를 명확히 인식하도록, 보정 파라미터로 투영한 **위험 구역·작업면 경계선과 대상 인물 표시**를 VLM 입력 이미지 사본 위에 그려 넣는다(원본 이벤트 클립은 수정하지 않음). 또한 VLM 프롬프트에 교실 사물(책상, 40cm 단상, 바닥 테이프)을 건설 현장 사물(비계, 개구부 등)로 이름을 바꾸어 부르라고 지시하지 않는다(관측된 사실과 표시된 위험 구역 기하만 설명하게 하여 거짓말·환각 유도 방지, v1.3 수정 49, `docs/design/tbm-legal-graph.md`). 처리한 이미지는 메모리에서만 쓰고 저장하지 않는다.

## 5.5 PPE 워커 (MVP, M3)

PPE 판정(F-11)은 MVP 다. World ID 별 안전모·조끼 착용 상태를 판정해 관제 화면에 보이고, 안전모 요구 구역의 미착용은 R9(CAUTION) 주의 이벤트로 관제 화면에 안내한다(7.2·7.3, 노트북 로컬 경보·경보음 없음). R9 는 G9 와 G6-R9 를 통과해야 켠다(15.1). 아래 수치는 모두 초기값이며 교실 실측과 시나리오 데이터셋으로 고친다.

- 모델: YOLO26x 검출을 PPE 데이터에 미세조정한 체크포인트 하나를 쓴다(분류는 비교군). 검출이어야 안전모·조끼와 머리·몸통 keypoint의 위치 관계로 착용 여부를 판단할 수 있다. 클래스는 4개다: 안전모 쓴 머리(`helmet_head`), 안전모 없는 머리(`no_helmet_head`), 조끼 입은 몸통(`vest_torso`), 조끼 없는 몸통(`no_vest_torso`). 실행할 때 모델의 클래스 이름이 이 목록과 다르면 시작하지 않는다. 신호수 표식(다른 색 조끼·완장)은 확장이다(부록 C).
- 데이터: 지금 후보는 교실·로비 시연 녹화(사람 그룹을 세션 단위로 나눔), 기계 후보 라벨과 사람 승인 앵커, 배경 합성·좌우 반전으로 학습한다. 공개 데이터(Ultralytics Construction-PPE, AGPL-3.0. SHEL 안전모. SH17 은 라이선스 확인 전에는 쓰지 않음)는 별도 비교군이며 섞어 학습하려면 클래스 마스크가 필요하다. 학습·채택 전에 YOLOE-26 텍스트 프롬프트 무학습 기준선을 같은 평가로 잰다. 같은 장소·탐색 이력이 있는 진단셋 수치는 제품 성능으로 쓰지 않는다(AGENTS 규칙 7).
- 입력: 원본 프레임 전체 화면을 640 으로 줄여 추론하는 것이 기본이다(FP32, confidence 0.5, NMS 0.7). 같은 체크포인트에 문맥을 넓힌 상반신 crop 을 넣으면 검출 성능이 크게 떨어진 기록이 있어 crop 은 비교 후보로만 둔다. 같은 원본·같은 정책으로 미리 정한 기준을 통과하기 전에는 기본 입력을 바꾸지 않는다. 축소 입력에서 교실 안전모 크기가 충분한지는 교실 실측으로 확인한다(아래 크기 항목, 19.1).
- 실행: Tier 0 와 같은 GPU 인스턴스의 별도 PPE 프로세스(GPU 몫 0.05, 3.2)가 Tier 0 의 최신 원본 프레임과 같은 프레임의 관측·local ID → World ID·`identity_revision` 대응을 상한 있는 공유 채널로 받아 1\~2 Hz 로 처리한다. 카메라당 최대 2 Hz(4대 합계 8회/s), 카메라당 대기 1(최신 프레임으로 교체), 동시 추론 1, 대기 150 ms 를 넘으면 버린다. Tier 0 지연을 모르거나 넘으면 새 추론을 멈추고 10초 안정 뒤 재개한다(3.2 접수 규칙). PPE 가 죽거나 메모리가 모자라도 Tier 0 는 계속 돈다.
- 사람과의 연결: 같은 카메라·같은 프레임·같은 촬영 시각의 Tier 0 관측 2D keypoint 만 쓴다(HMR 추정점·가려진 점은 쓰지 않음). 안전모는 머리 영역(눈·귀), 조끼는 어깨\~골반 영역과 일대일로 겹쳐야 착용이다. 한 검출이 두 사람에 걸리거나 같은 장비에서 착용·미착용 클래스가 함께 나오거나 ID 대응이 불확실하면 UNKNOWN 이다. 손에 든 안전모, 의자에 걸린 조끼를 착용으로 세지 않는다. PPE 는 World 위치·ID 를 만들거나 바꾸지 않는다(AGENTS 규칙 1).
- 다시점 비대칭 규칙: 한 대라도 착용을 확실히 보면 WORN 근거, NOT_WORN 은 머리가 선명히 보이는데 명시적 미착용 검출이 있을 때만, 그 외 UNKNOWN. 검출 없음·임계 미달·가림은 미착용 근거가 아니다.
- 상태 전환: 촬영 시각 기준 500 ms 칸으로 모으고(카메라 간 근거 시차 100 ms 이내, 한 칸은 카메라 수와 상관없이 한 표본) 최근 3초(6칸)로 바꾼다. WORN 은 6칸 중 5칸 이상 착용이고 마지막 칸도 착용일 때, NOT_WORN 은 6칸 모두 선명한 미착용이고 착용 근거가 없을 때다. 반대 근거가 나오면 먼저 UNKNOWN 으로 돌린 뒤 창을 다시 쌓는다. 마지막 유효 근거의 촬영 시각 + 10초가 지나면 UNKNOWN 이고, `identity_revision`·World ID 대응이 바뀌면 상태를 바로 초기화한다.
- 원본·crop 은 메모리에서만 쓰고 판정 직후 반환하며 저장하지 않는다. 별도 프로세스는 오류만 격리할 뿐 GPU는 공유하므로, PPE에 GPU 메모리·대기열 길이·초당 추론 수 상한을 두고 GPU가 포화되면 PPE 프레임부터 건너뛴다.
- 크기: 3MP(가로 2304px)·가로 약 105°에서 교실 중앙 안전모는 원본에서 약 36픽셀로 추정되어 기준선(32px)을 조금 넘는다(가로 1920px·98.8° 기준 약 32px에서 해상도·화각 비율로 환산, 화각 실측 후 다시 계산). 전체 화면 640 입력에서는 이보다 작아지고, 약 1.1 Mbps의 강한 압축도 세부를 줄인다. 교실 원본 해상도의 머리·안전모 크기 분포와 640 입력 뒤 유효 크기를 먼저 재고, 실제 스트림 품질로 정확도를 확인한다.
- 결과는 별도 I1 메시지 `ppe_state` 로 EC2 에 보낸다(12.3, 계약은 Lead 승인 뒤 추가, 19.1). R9 판정은 Tier 0 Risk Engine 이 PPE 상태와 구역 요구 조건으로 한다(7.2).

## 5.6 SAM 3D Body 강화 (시연 범위 · EXP-02)

**시연 범위 — EXP-02.** Fast SAM 3D Body로 MHR 리깅 메시·포즈를 복원해 인물별 동적 아바타를 구성하며, 카메라 연속 관측이 쌓일수록 실제 관측 기반 외형·텍스처를 개선한다. 확장 후보·별도 승인이 아니라 시연 범위다(2026-10-23·2026-10-30 사용자 결정). 1단계는 MHR 리깅 메시 + 포즈 스트림(상·하의 대표색), 2단계는 관측 픽셀 UV 텍스처 누적(`SIMAI_AVATAR_APPEARANCE=auto`, CUDA 가 있으면 기본으로 켜고 CPU 에서는 끔, S15P31A101-89)이며, 3DGS는 쓰지 않는다. 상시 스트림 루프(`services/avatar`, S15P31A101-324·-351)는 LIVE 관제 중에도 분석 워커 GPU 상한(0.10) 안에서 돌되, Tier 0 지연 감시(3.2 접수 규칙: 지연 초과·모름은 즉시 멈춤, 큐 대기 초과 프레임은 창당 2건까지 넘김, 재개 10초)에 걸리면 멈추고 뷰어는 0.5 s 뒤 캡슐 아바타로 돌아가며(13.2), 유휴 중에도 I6 WebSocket 끊김(`recv(timeout=0)`·10초 ping)을 즉시 감지해 재연결 시 캐시된 `avatar_asset` 을 다시 알린다(`docs/design/hmr-avatar-loop.md`, `docs/design/hmr-appearance-texture.md`).

- 역할: 삼각측량에서 빠진 관절(책상 뒤 하체 등)을 채우고 체형·손을 더한다.
- 사용: Fast SAM 3D Body 변형, mask 프롬프트(상시 아바타 루프 `SIMAI_AVATAR_SEG=auto` 가 CUDA 에서 왜곡을 편 영상으로 `YOLO26x-seg` 배치 추론을 돌려 bbox IoU ≥ 0.5 일대일 배정한 사람 분할 마스크를 HMR 프롬프트와 원본 좌표 역변환 뒤 UV 텍스처 누적의 전경 가림 마스크에 함께 사용하며, 추론 실패 시 경고 후 bbox 로 폴백, 2026-10-30 사용자 결정, S15P31A101-362, `docs/design/hmr-avatar-loop.md`), keypoint 프롬프트는 몸통·고관절 같은 안정 관절만(손목·손 제외).
- 검출기·입력: 사람 박스·손 영역은 Tier 0와 같은 YOLO26x-pose 로 잡는다. 아바타 포즈 스트림은 body 모드를 기본(사람별 2\~5 Hz 목표, 손가락 관절은 null)으로 하고, 손 포함(full) 모드는 표시용으로 낮은 주기에서만 돌린다(참고: 일본 H100 웹캠 라이브 full 모드 e2e p50 450 ms, EXP-02 6.4). 카메라 K 는 보정(CalibrationProvider) 값을 쓰고, MoGe2 화각 추정은 E-GATE-0 공식 설정 재현에만 쓴다.
- 다시점 집계: 직접 만들기 전에 Fast SAM 3D Body 에 내장된 다시점 융합을 E-GATE-1 에서 먼저 시험한다. 쓸 수 없으면 카메라당 최대 1개 제약 클러스터링 → 대표 포즈의 translation만 다시점 재투영 오차로 보정한다. 최종 root는 5.2를 따른다.
- 품질·성능 검증 기준(E-GATE-1·3, 20.6): G5의 “한 카메라 제외 재투영 오차”와 “책상 뒤 하체 누락률”을 삼각측량 기준선보다 의미 있게 개선. Multi-HMR 2는 비교 기준선이다.
- 표현 계약: 실시간 아바타 스트림(I6 `avatar_pose_batch` → I2 `avatar_frame`, 12.2·12.4)은 `native_pose`(MHR 127관절 부모 기준 축각 라디안 회전과 `root_rotation`, 위치 필드 없음)만 싣고, 공통 관절(COCO17) 위치인 `canonical_motion`은 오프라인 실험 Run 기록(`experiments/human_mesh_output`, G5·한 카메라 제외 재투영 평가용)에만 둔다(실시간 캡슐 아바타의 공통 관절 정본은 Tier 0 `world_state`의 `skeleton`이다). SOMA-X 변환은 확장 후보다(부록 C).

**observed / inferred 구분과 UV 텍스처 누적.** Tier 0 삼각측량 관절은 observed, Tier 1 HMR이 채운 관절은 inferred로 표시한다(`joint_source: "inferred"`). 위험 규칙은 observed이면서 VALID인 관절만 확정 근거로 쓰고, inferred 관절은 표시·보조에만 쓴다(Tier 1 안전 판단 권한 없음). 2단계 관측 픽셀 UV 텍스처 누적(`hmr/appearance.py`·`hmr/raster.py`)은 새 외부 렌더링 의존성 없이 `torch`/`numpy` 원근 보정 z-buffer 래스터화로 사람별 `1024×1024` `albedo.png` 와 `surface_source.png`(코드 `0` 미관측·`1` 보간·`2` 관측, 얼굴 영역 `+128`, `face_ratios`)를 갱신해 `AVATAR_ASSET` 으로 올리고 `avatar_asset` 새 버전을 발행하며, 메시 실루엣 침식·감쇠, 동일 시각 공통 고품질 텍셀의 카메라 간 RGB 채널 이득 EMA 맞춤, 인물 영역 라플라시안 선명도 가중, Tier 0 대 HMR World COCO17 재투영 오차 가중(큰 오차 카메라 배제)을 적용한다(세부 수치는 `docs/design/hmr-appearance-texture.md`, S15P31A101-89·-361). World root 위치·접지 기준의 정본은 계속 Tier 0 `world_state`(5.2)이다.

## 5.7 정적 공간 갱신 (확장)

확장 기능이다. 기준선은 단순 영상·깊이 차분이고, 3DGS 계열(3DGS-U·GS-Pool·GaussianUpdate·CL-Splats)은 확장 후보 묶음으로만 둔다. 흐름과 변화 구역의 임시 형상 정책은 부록 C 에 있다.

## 5.8 Unreal 배경 빌드 (확장)

확장 기능이다(부록 C).

- Unreal은 배경 자산 빌드 도구다. 렌더러는 Three.js 하나다.
- MCP 에이전트는 빌드 레시피(Unreal Python 스크립트 또는 고정 툴 호출 순서)를 작성·수리만 하고, 파이프라인은 검토 후 고정한 레시피를 실행한다.
- 빌드: Scene 커밋 → 레시피 실행(import, 재질, 조명 굽기, LOD) → glTF 출력 → 격자점 왕복·bounding box 검증 → `scene_version` 태그. 실패 시 이전 자산 유지.
- 에디터 MCP는 루프백만 허용하고 툴 범위를 제한한다. Blender 헤드리스를 대안으로 비교한다.
