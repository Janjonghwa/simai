# 7. 위험 규칙과 대응

하나의 Risk Engine이 같은 규칙을 네 가지 입력(실시간, 계획, 리플레이, What-if)에 적용한다. 임계값은 동작 정의용 초기 예시값이며 실제 안전 기준이 아니다. 시나리오 데이터셋으로 조정한다.

## 7.1 규칙 공통 형식

| 항목 | 내용 |
|---|---|
| 입력 | 읽는 상태(World XYZ와 불확실성, 구역, 등록 작업면, 객체 상태 등) |
| 발생·해소 조건 | 발생은 지속 조건(6.4) 충족 시, 히스테리시스용 두 임계값, 해소는 일정 시간 유지 후 |
| 불확실성 처리 | 발생: 불확실성 범위가 조건에 조금이라도 걸리면. 해소: 불확실성 범위까지 완전히 벗어난 상태가 유지되면 |
| 심각도 | CRITICAL / HIGH / CAUTION / INFO |
| 적용 출처 | LIVE / PLANNED / REPLAY / WHAT_IF |
| 근거 조항 | F-02 보고서 RAG 인용과 연결 |
| 버전 | 규칙 ID + 버전, 이벤트에 기록 |

**불확실성 범위.** 수평 위치 공분산의 k=2(약 95%) 타원에 사람 점유 반경 0.3m 를 더한 영역이다. 이 범위가 구역·가장자리 조건에 걸리는지로 발생·해소를 판정한다.

**“확인 필요”의 정의.** 이벤트의 `confidence_reasons[]`가 비어 있지 않은 상태다. 이유 값은 아래와 같고, 여러 개가 함께 붙을 수 있다. 계약 반영(현재 `needs_check`)은 후속 계약 변경으로 한다.

| 값 | 뜻 |
|---|---|
| `Z_UNKNOWN` | 지지 표면·높이를 모름(z_validity UNAVAILABLE) |
| `PREDICTED` | 위치가 관측이 아니라 예측값 |
| `PROVISIONAL_CALIB` | 보정 상태가 PROVISIONAL |
| `SINGLE_VIEW` | 2대 이상 유효 관측이 없음 |
| `JOINT_UNCERTAIN` | 근거 관절이 UNCERTAIN |
| `IDENTITY_UNCERTAIN` | 카메라 간 연결이 애매함 |

## 7.2 규칙 목록

| ID | 규칙 | 발생 / 해소 (예시) | 심각도 | 단계 |
|---|---|---|---|---|
| R1 | 위험 구역 진입 | GROUND_FOOTPRINT 또는 VOLUME_3D 구역 안 진입(8.2). XY는 안인데 Z를 모르면 ‘확인 필요’ / 0.3m 바깥에서 3초 유지 | 구역 유형별 | MVP |
| R2 | 개구부·가장자리 근접 | 등록 작업면 OBB 윗면 둘레(7.5) 중 인접 면과 높이차 2m 이상인 가장자리까지 1.0m 이내 / 1.3m 이상에서 3초 | CRITICAL | MVP |
| R3 | 고소 위치 | 서 있는 면(등록 작업면)과 인접한 낮은 면의 높이 차 2m 이상, 안전 난간 없는 구역(교실은 바닥 기준으로 단순화) | HIGH | MVP |
| R4 | 낙상 의심 | 머리 높이 급하강 후 낮은 자세 유지, 또는 급하강 직후 관측 상실. 관절이 UNCERTAIN이면 “낙상 의심 + 확인 필요” | CRITICAL | MVP(선택) |
| R5 | 진입 예측 | 현재 속도로 1.5\~2초 뒤 R1·R2 구역 진입 | CAUTION | MVP |
| R6 | 위험 구역 내 관측 상실 | 구역 안에서 마지막으로 보인 사람이 UNKNOWN | 원래 규칙 유지 + UNVERIFIABLE | MVP |
| R7 | 구역 감시 능력 저하 | 카메라 장애로 구역의 2대 이상 관측 조건 상실 | CAUTION(시스템) | MVP |
| R8 | 장비 근접 | 이동 장비 반경(방향 반영)까지 기준 거리 이내 | CRITICAL | 확장(부록 C) |
| R9 | PPE 필수 구역 미착용 | 구역이 안전모 요구, PPEState NOT_WORN | HIGH | 확장(부록 C) |
| R10 | 불확실 점유 근접 | 이동(v1.3) → 부록 C | — | 확장(부록 C) |

- R3의 2m는 국내 산업안전 기준에서 추락 방지 조치를 요구하는 높이로 흔히 쓰이는 값이다. 정확한 조항은 RAG 문서 구축 시 확인해 근거 조항에 연결한다.
- R4는 M2에 포함하되 MVP 합격 필수 조건은 아니다. 앉기·물건 줍기·책상 뒤 이동과 영상상 비슷해서, 관절 유효성 게이트(5.2)를 통과한 경우에만 확정 근거로 쓴다.
- R5의 1.5\~2초는 업로드·판정·현장 경보 지연과 사람 반응 시간을 반영한 초기값이다. 선행 시간은 이벤트 생성 시점 기준으로 재고, 채널별 전달 지연은 따로 측정한다. MVP에는 위험에 처한 작업자 본인에게 닿는 채널이 없다(PWA는 반장, 관제 화면은 관리자, 로컬 경보는 현장 소리). R5의 효과는 “진입 전 예측 성공”과 “채널별 실제 전달 성공”으로 나눠 보고, 수신자에게 실제로 전달된 근거가 있을 때만 경고 효과를 주장한다. 확장의 워치가 붙으면 R5 가 워치 알림의 주 경로가 된다(부록 C).
- R7 은 위험이 아니라 시스템 상태 안내라 7.3 표대로 관제 화면 안내로만 보내고 현장 소리(노트북 로컬 경보)·반장 PWA 로 내지 않는다(위험 경보로 오인하지 않게). 저하 구역 안 사람의 위험은 각 규칙과 R6 이 ‘확인 필요’로 다룬다.
- R8 이전에는 정지 장비를 R1 구역으로 등록해 대신한다. R8은 장비 방향(heading) 추정이 전제다.
- R9 UNKNOWN은 경보 등급을 유지하고 “확인 필요”를 붙인다.

## 7.3 심각도 × 신뢰도 → 대응

| 심각도 | 보내는 채널 |
|---|---|
| CRITICAL·HIGH | 노트북 로컬 경보 + 관제 화면 경보 + 반장 PWA |
| CAUTION | 관제 화면 안내 |
| INFO | 기록만 |

신뢰도가 낮으면(“확인 필요”, 7.1) 같은 채널에 “확인 필요”를 붙여 보낸다. 신뢰도가 낮아도 등급은 내려가지 않는다. 이 표가 알림 채널의 정본이며, 다른 절(3.10, 10장)은 이 표를 따른다. 등급별로 소리 패턴과 중복 억제는 달리할 수 있지만 보내는 채널은 이 표로만 정한다. severity(위험 정도), confidence(증거 신뢰도), verification_state(확인 여부), action(대응)은 독립 속성이다. 워치 채널은 확장이다(부록 C).

MVP에서 현장 경보는 노트북 로컬 경보와 관제 화면 경보(3.10)이며, 관리자는 그 관제 화면을 보는 사람이다.

## 7.4 운영 원칙

- **VLM 연결:** R1·R2·R3·R4 이벤트는 이벤트 프레임과 구조화 상태를 VLM에 보내 근거를 붙인다. MVP 에서는 CRITICAL 이벤트에만, 병합된 이벤트당 1회 보낸다(5.4). VLM은 상향 의견만 낸다.
- **역할 예외:** 신호수 등 역할 예외는 PPE 트랙(확장)의 구별 표식 검출로 규칙 기반 부여한다. MVP는 예외 없이 모두에게 적용한다.
- **이벤트 병합:** 같은 사람·같은 규칙은 하나의 이벤트를 갱신하고, 한 사람에게 걸린 여러 규칙은 화면에서 한 묶음으로 보인다. 해소 후 10초 안의 재발생은 기존 이벤트를 재개한다(6.4).
- **출처 분리:** PLANNED·WHAT_IF·REPLAY 위험은 같은 규칙으로 계산하되 보고서·시뮬레이션 화면에만 표시하고, 실제 알림 채널로는 보내지 않는다(DB 제약, 10장).
- **교실 시험:** 높이·낙상 규칙은 40cm 단상과 매트로 시험하고, 시험 때만 높이 임계값을 단상 높이에 맞춘다. 규칙 논리는 같다. 이 시험용 임계값 세트는 별도 `rule_version`(시험 프로파일)으로 두고 화면에 표시한다(부록 E).

## 7.5 작업면 등록과 가장자리

R2·R3 와 ContactEstimator 가 쓰는 높이·가장자리는 관리자가 등록한 작업면에서 온다.

- 관리자는 뷰어에서 단상·책상 같은 작업면을 OBB 로 등록하고 상판 높이를 입력한다(13.4). 등록 작업면은 Operational Geometry 로 구성 묶음에 들어간다(3.2).
- R2·R3 의 가장자리는 등록 작업면 OBB 윗면의 둘레이고, 높이차는 상판 높이와 인접한 낮은 면(바닥 또는 다른 작업면)의 차이다.
- ContactEstimator(5.2)는 등록 작업면의 상판 높이를 지지 표면 후보로 쓴다.
- 정적 3D OBB 에서 책상 상판 후보를 뽑아 관리자가 확인하는 보조 기능은 선택이다. 정적 3D 자체는 R2·R3 판정에 쓰지 않는다.
- 공간이 바뀌면 관리자가 다시 등록하고 새 구성 묶음을 발행한다(6.3).
