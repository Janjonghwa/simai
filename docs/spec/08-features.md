# 8. 기능 명세

MVP는 F-05 → F-06 → F-09의 실시간 루프와 F-02 사전 보고서, F-10 기록·최소 리플레이로 구성한다. 확장 기능은 같은 Risk Engine과 Spatial DB를 재사용하며 부록 C 에 요약한다. 기능 번호는 1.3 을 본다.

## 8.1 F-05 3D 위치 추적 (MVP)

- 5.1·5.2의 출력(World XYZ, 3D 골격, 관측 상태)을 10 Hz로 EC2에 보낸다.
- 위치 정확도는 “m 단위 근사 + 오차 범위 명시”로 표현한다. 밀리미터 정밀도를 주장하지 않는다.
- 고소 작업자는 Z로 직접 표현되어 R2·R3·R4의 입력이 된다.

## 8.2 F-06 입체 Geo-fencing (MVP)

- 관리자는 Three.js 뷰어에서 바닥 다각형을 그리고 최저·최고 높이를 지정해 입체 구역을 만든다(“개구부 위 2m 작업 공간”, “양중 하부 공간”).
- 구역 속성: 유형, 심각도, 유효 시작·종료 시각, 요구 조건(안전모 등, 확장).
- 수정은 덮어쓰지 않고 새 버전을 추가한다. 리플레이 확장은 그 시각에 유효했던 구역을 보여준다(부록 C).
- 판정은 Point-in-Prism + 불확실성 범위(7.1), R1·R5·R6 적용. 판정은 Risk Engine 이 하고 VLM 근거는 첨부만 한다.

**구역 판정 유형.** 구역마다 판정 유형을 지정한다.

| 유형 | 판정 | 쓰임 |
|---|---|---|
| GROUND_FOOTPRINT | position_xy + 수평 불확실성이 바닥 다각형에 걸리는지 | 바닥 출입 통제 구역, 장비 주차 구역 |
| VOLUME_3D | 사람이 차지하는 높이 범위(서 있는 면 Z \~ VALID 관절 중 가장 높은 Z, 없으면 head_z)와 구역 높이 범위가 겹치는지, 3D 불확실성 포함 | 개구부 위 작업 공간, 양중 하부 공간 |

VOLUME_3D 구역에서 XY는 다각형 안인데 Z(서 있는 면 또는 head_z)를 모르면 “진입하지 않았다”고 확정하지 않고, 이벤트를 만들되 “확인 필요”(`Z_UNKNOWN`)로 표시한다.

## 8.3 F-02 TBM 리스크 보고서 (MVP)

- 관리자가 3D 뷰어에 가상 레이아웃(개구부, 가설 비계, 장비 주차 구역)을 배치한다.
- **계획 작업 위치.** 사람 대상 규칙(R1·R2·R3)은 사람이 서 있을 위치가 있어야 판정한다. 기본은 Risk Engine 컨테이너가 레이아웃의 작업면·구역에서 대표 위치를 자동으로 만들고, 관리자가 위치를 직접 줄 수도 있다(그때는 만들지 않는다). 요청에 위치가 없거나 빈 배열이면 ‘사람 없음’이 아니라 ‘컨테이너가 만든다’는 뜻이다. 판정에 쓴 위치는 결과에 출처(요청이 준 위치 REQUESTED, 만든 위치 GENERATED)와 함께 실리고, EC2(Spring)가 결과의 위치 목록을 위험 항목과 함께 `sim.*` 에 저장한다. 계획 위치는 World ID 가 아니다. 생성 규칙: 작업면마다 상판 가운데 1곳(가운데가 R2 발생 거리 밖일 만큼 넓은 면은 가장 긴 변 가운데에서 0.5 m 안쪽 1곳을 더함), 판정 시각에 유효한 개구부 구역(`zone_type` OPENING)마다 가장 긴 변 가운데에서 바깥 0.2 m 의 바닥 1곳(점유 반경 0.3 m 안이라 R1 이 판정한다). 그 밖의 구역 유형에는 만들지 않고, 머리 높이는 주지 않으며(VOLUME_3D 구역에서는 확인 필요 `Z_UNKNOWN`), 같은 레이아웃·판정 시각이면 같은 위치·같은 ID(`gen-<작업면·구역 ID>-<순번>`)다. 수치 근거는 `docs/design/risk-engine-container.md`.
- **평가한 위치 없음.** 만들 작업면·유효한 개구부가 없고 요청도 위치를 주지 않으면 결과의 위치 목록이 비고 위험 항목도 없다. 이것은 사람 대상 규칙을 판정할 위치가 없었다는 뜻이지 ‘위험 없음’이 아니다. 보고서·화면은 ‘평가한 작업 위치 없음’으로 보이고, 필요하면 관리자가 위치를 준다. 계약은 빈 위치 목록을 그 뜻으로 읽고, 선택 표시 `no_evaluated_positions` 로 명시할 수 있다(`risk_plan_result` 1.1.0, 컨테이너가 채우는 것은 19.1).
- Risk Engine이 PLANNED 출처로 규칙을 계산한다(수평 거리와 높이 차 포함). 위험 항목은 확률 대신 등급 + 근거로 표현한다(“추락 리스크 85%” 같은 수치는 쓰지 않는다).
- 계산 요청: 관리자가 `POST /api/reports/tbm`(layoutId)을 부르면 EC2 가 그 안에서 Risk Engine 컨테이너로 PLANNED 계산을 하고(결과는 `sim.*`), pgvector 에서 안전 수칙 조항을 검색해 둘을 `tbm_report` 작업 입력에 담는다. M3 에는 단독 평가 API 가 필요 없다(단독 평가는 부록 C.4). EC2 와 컨테이너 사이 구간은 12.2 를 본다.
- LLM(외부 API, 5.4)이 분석 워커의 `tbm_report` 작업 안에서 계산 결과와 검색된 조항으로 위험성 평가 보고서 초안 문장을 만든다. 보내는 것은 텍스트뿐이다. 인용은 입력에 담긴 조항 ID만 허용한다. 일일 일지도 같은 작업(`report_kind` DAILY, `POST /api/reports/daily`)이다.
- 출력: 보고서(PDF 는 브라우저 인쇄로 만든다, 별도 내보내기 API 없음), 계산 근거 표(`GET /api/reports/tbm/{reportId}`).

## 8.4 F-09 반장 PWA (MVP, M1·M2)

- 반장 휴대폰으로 위험 알림(Web Push)이 오고, 위치·근거·관련 구역을 보여준다(M1).
- CRITICAL·HIGH 이벤트가 생기면 조치 티켓을 “요청” 상태로 자동 생성한다. 관리자도 티켓을 조회해 종료 절차에서 미결을 확인한다(M2).
- 조치 상태: 요청 → 확인 → 조치 중 → 완료. 완료 시 조치 사진을 업로드한다(M2).
- 조치 완료는 사람의 보고이고, RiskEvent 해소는 관측 확인이다. 완료됐는데 관측상 위험이 남아 있으면 불일치를 관리자에게 표시한다(M2, 관리자 전용 토픽 `/topic/admin/events` 의 `action_mismatch`, 12.4).
- MVP 에서 카메라에 잡힌 모든 사람의 위험은 이 경로로 반장에게 전달된다(개인 채널인 워치는 부록 C).

## 8.5 F-10 기록 (MVP) · 최소 리플레이 (M3)

- 기록: 첫날부터 위치·상태·이벤트·조치를 Spatial DB에 저장한다(11장).
- 최소 리플레이(M3): 시각 슬라이더로 시각 T를 고르면 그 시각의 `world_track_state`와 활성 `risk_event`를 불러와 Three.js에 재생한다. EC2 단절 등으로 기록이 없는 구간은 “데이터 없음”으로 표시하고 보간하지 않는다.
- 리플레이 확장(유효 구역·규칙·COMMITTED Scene 버전 재현, 재생 속도, 이벤트 지점 점프)은 이동(v1.3) → 부록 C.
