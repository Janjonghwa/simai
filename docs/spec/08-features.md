# 8. 기능 명세

MVP는 F-05 → F-06 → F-09의 실시간 루프와 F-02 사전 보고서, F-10 기록·최소 리플레이로 구성한다. 확장 기능은 같은 Risk Engine과 Spatial DB를 재사용하며 부록 C 에 요약한다. 기능 번호는 1.3 을 본다.

## 8.1 F-05 3D 위치 추적 (MVP)

- 5.1·5.2의 출력(World XYZ, 3D 골격, 관측 상태)을 10 Hz로 EC2에 보낸다.
- 위치 정확도는 “m 단위 근사 + 오차 범위 명시”로 표현한다. 밀리미터 정밀도를 주장하지 않는다.
- 고소 작업자는 Z로 직접 표현되어 R2·R3·R4의 입력이 된다.
- **관제 화면과 작업 세션 연동 및 “작업 외 진입” 표시(v1.3 수정 52, `docs/design/work-session-flow.md`):**
  - 진행 중인 작업(`work_unit.status = 'IN_PROGRESS'`)이 없을 때 관제 화면은 **“진행 중인 작업 없음 · 관제 대기”** 상태를 표시하고, 현재 작업 이벤트 목록은 비운다(지난 작업의 이벤트는 히스토리/리플레이로 이동).
  - 작업이 시작(`POST /api/work-units/{id}/start`, `IN_PROGRESS`)되면 해당 작업의 대상 구역(`zone_id`), 가상/계획 배치(`layout_id`), 담당 조(`lead_team`), 실제 시작 시각(`actual_started_at`)을 관제 화면에 올리고, 활성 작업 이벤트 목록에는 **그 작업 시작(`actual_started_at`) 이후 발생한 이벤트만** 모아 보여 준다.
  - **경보는 작업 상태로 절대 숨기지 않는다(핵심 안전 원칙):** 진행 중인 작업이 없을 때(관제 대기 중)나 현재 작업의 대상 구역 밖에서 사람이 위험구역에 들어가도 **Tier 0 판정·노트북 로컬 경보·관제 화면 경보는 평소와 100% 똑같이 울린다**(AGENTS.md 규칙 1·5). 관제 화면에는 경보를 즉시 띄우되 **“작업 외 진입”** 배지를 함께 표시해 계획되지 않은 구역 진입임을 알린다.

## 8.2 F-06 입체 Geo-fencing (MVP)

- **별도 구역 편집 페이지 폐지 → 실시간 관제의 관리자 편집 모드(v1.3 수정 52):** 별도의 구역 편집 페이지를 두지 않고, **3D 실시간 관제 화면 안에서 관리자(`ADMIN`)만 편집 모드를 켜** 바닥 다각형과 최저·최고 높이를 지정해 위험구역(`zone`)과 고소 작업면(`static_object`)을 만들고 고친다(13.4, `docs/design/work-session-flow.md`).
- **위험구역 색·심각도 2종(`CRITICAL` 빨강, `HIGH` 주황)과 이벤트 등급 분리:** 구역을 만들거나 고칠 때 선택하는 구역 심각도는 **`CRITICAL`(빨강, 위험)** 과 **`HIGH`(주황, 경고)** 두 가지뿐이다(화면에서 단순 표시용 "작업구역"과 구역 `CAUTION`·`INFO` 선택지는 두지 않음). **구역 심각도와 이벤트 심각도는 별개**이며, R5 진입 예측·R7 감시 저하 등의 이벤트 등급 `CAUTION`(관제 화면 안내만)과 `INFO` 는 그대로 유지한다(7.2).
- **고소 작업면 동시 생성과 시각 표현:** 고소 작업면(단상·가설 비계 등)은 화면에서 `HIGH`(주황) 위험구역과 같은 시각 스타일로 그리되, 내부 데이터는 작업면(`static_object` `WORK_SURFACE` OBB 와 `top_height_m`)을 그대로 유지한다(7.5). 관리자가 편집 모드에서 고소 작업면을 하나 그리면 **작업면(`static_object`)과 둘레 `HIGH` 위험구역(`zone`, 기본 여유 폭 0.30 m)이 함께 만들어져** `zone_id` 로 연결된다.
- **초기 세팅 VLM 위험구역 초안(`vlm_zone_draft`)과 작업 중 새 물체 감지·즉시 구역 발행(v1.3 수정 52):** 최초 설치·초기 세팅 때 정적 3D 배경(GLB/점군)과 보정(`CALIBRATED`), 카메라 대표 프레임에서 추출한 바닥·상판·객체 후보에 VLM(Cosmos3-Nano 16B)이 이름(개구부·가장자리·장비 등), 추천 등급(`CRITICAL`·`HIGH`), 제안 이유를 붙여 **위험구역·작업면 초안**을 채워 둔다(5.4, 12.5). 관제 화면의 관리자 편집 모드에 **"AI 초안"** 으로 표시하며, 사람이 조정한 뒤 **저장·발행(`POST /api/zones/commit`, `config_bundle` 발행)하는 것이 곧 확정**이다(별도 승인 단계 없음). 작업 중 철근·자재 같은 새 물체가 들어와 유지될 때도 사람 지운 배경 비교로 **추정 상자**와 **“새 물체 감지 · 위험 검토 필요”**(`CAUTION`) 안내(및 VLM 이름·이유·둘레 위험구역 초안, 구현 후속)를 띄우며, 관리자가 클릭으로 장애물 등록·위험구역 발행(`POST /api/zones/commit`)하면 진행 중인 작업 판정에 즉시 반영된다(시각적 3D 배경 자체는 관리자가 **“맵 재생성”** 버튼 `POST /api/scenes/regenerate` → I5 `scene_regenerate` 로 전체 재구성 후 `CANDIDATE` 활성화, 5.3·12.5·12.6, S15P31A101-427·-428). **발행 전 초안이나 추정 상자는 Tier 0 위험 판정에 절대 쓰지 않는다**(AGENTS.md 규칙 1·4·7). 확정된 구역은 이어서 작업 관리(8.3)에서 TBM 보고서를 만들 때 그대로 쓴다.
- 구역 속성: 유형(개구부·고소 작업면 둘레·장비 주차·양중 하부 등), 심각도(`CRITICAL`·`HIGH`), 유효 시작·종료 시각, 요구 조건(안전모 등, 확장).
- 수정은 덮어쓰지 않고 새 버전을 추가하며, `POST /api/zones/commit`(`publish: true`, S15P31A101-397·-410) 한 번으로 구역·작업면 새 버전 저장과 Tier 0 `config_bundle` 발행을 처리한다. 리플레이 확장은 그 시각에 유효했던 구역을 보여준다(부록 C).
- 판정은 Point-in-Prism(R1 신규 발생은 확실한 위치의 점 기준, 유지·해소와 R5 는 불확실성 범위 7.1), R1·R5·R6 적용. 판정은 Risk Engine 이 하고 VLM 근거는 첨부만 한다.
- **R1 확실한 위치 발생과 관제 화면 “위치 불확실” 표시:** R1 구역 진입 경보(주의 `HIGH`·위험 `CRITICAL` 모두)는 사람의 위치가 확실하고(관측 `OBSERVED` + 카메라 2대 이상 정합 또는 1대 접지점 확인, `IDENTITY_UNCERTAIN` 아님, `VOLUME_3D` 는 높이까지 확인) 그 위치(점 기준: 검증된 접지점 XY, 없으면 `position_xy`)가 구역 안일 때만 발생시킨다(7.1, 7.2). 불확실성 타원·점유 반경·보정 여유로 넓혀 걸리거나 위치가 불확실하면 이벤트·경보를 만들지 않고, 3D 관제 화면의 사람(아바타) 표시에만 **“위치 불확실”** 을 흐리게 표시한다(13.2, 뷰어 후속). 이미 열린 이벤트의 유지·해소(해소 간격 0.3m·3초 유지, R6 관측 상실 유지)에는 기존 불확실성 범위와 보정 여유를 그대로 써서 불확실 프레임이 열린 경보를 끊지 않는다.

**구역 판정 유형.** 구역마다 판정 유형을 지정한다.

| 유형 | 판정 | 쓰임 |
|---|---|---|
| GROUND_FOOTPRINT | 발생: 확실한 위치의 점 기준(검증된 접지점 XY, 없으면 `position_xy`)이 바닥 다각형 안인지. 유지·해소: `position_xy`(및 접지점 XY) + 수평 불확실성 범위(보정 여유 포함)가 바닥 다각형·해소 간격에 걸리는지 | 바닥 출입 통제 구역, 장비 주차 구역 |
| VOLUME_3D | 발생: 확실한 위치의 수평 점 기준이 다각형 안이고, 확인된 점유 높이 구간(검증된 서 있는 면 Z \~ VALID 관절 중 가장 높은 Z, 없으면 VALID `head_z`)이 구역 높이 범위와 겹치는지. 유지·해소: 수평·3D 불확실성(보정 여유 포함)을 더한 범위가 구역·해소 간격과 겹치는지 | 개구부 위 작업 공간, 양중 하부 공간 |

VOLUME_3D 구역에서 XY는 다각형 안인데 Z(서 있는 면 또는 VALID 관절·VALID `head_z` 위 끝)를 모르면 R1 **신규 발생은 내지 않는다**(높이를 알아야 확실한 위치, 7.1·7.2). 다만 **이미 열린 R1 이벤트의 유지 판정**(또는 PLANNED 계획 위치 평가, 8.3)에서는 Z 를 모른다고 해소를 확정하지 않고, 활성 이벤트를 유지하되 “확인 필요”(`Z_UNKNOWN`)로 표시한다.

## 8.3 F-02 작업 관리 및 TBM 리스크 보고서 (MVP)

- **TBM 페이지 → 작업 관리 페이지로 승격 및 작업 상태(`PLANNED` → `IN_PROGRESS` → `DONE`, v1.3 수정 52):** 기존 TBM 페이지를 **작업 관리 페이지**로 승격하고, TBM 보고서(회의록)는 작업 관리 안의 문서로 둔다(`docs/design/work-session-flow.md`). 각 작업(`work_unit`, `/api/work-units`)은 **`PLANNED`(계획) → `IN_PROGRESS`(진행, “작업 시작” `POST /api/work-units/{id}/start`) → `DONE`(종료, “작업 종료” `POST /api/work-units/{id}/end`)** 상태를 가지며, 예정 시각(`starts_at`·`ends_at`)과 별도로 **실제 시작·종료 시각(`actual_started_at`·`actual_ended_at`)** 을 기록한다(한 시점에 현장당 `IN_PROGRESS` 작업은 최대 1개). 각 작업에 그 작업이 쓰는 대상 구역(`zone_id`), 가상 레이아웃(`layout_plan`, `/api/layouts`, 개구부·가설 비계·장비 주차 구역), 공종(`work_type`, 예: 고소·비계 작업, 개구부 주변 작업, 자재 반입·운반 등)을 연결한다(`work_unit.layout_id`, `work_unit.work_type`, v1.3 수정 49). 같은 작업의 보고서를 다시 만들거나 작업 종료로 마무리를 덧붙일 때는 덮어쓰지 않고 새 버전(`report_version`)을 추가한다.
- **계획 작업 위치.** 사람 대상 규칙(R1·R2·R3)은 사람이 서 있을 위치가 있어야 판정한다. 기본은 Risk Engine 컨테이너가 레이아웃의 작업면·구역에서 대표 위치를 자동으로 만들고, 관리자가 위치를 직접 줄 수도 있다(그때는 만들지 않는다). 요청에 위치가 없거나 빈 배열이면 ‘사람 없음’이 아니라 ‘컨테이너가 만든다’는 뜻이다. 판정에 쓴 위치는 결과에 출처(요청이 준 위치 REQUESTED, 만든 위치 GENERATED)와 함께 실리고, EC2(Spring)가 결과의 위치 목록을 위험 항목과 함께 `sim.*` 에 저장한다. 계획 위치는 World ID 가 아니다. 생성 규칙: 작업면마다 상판 가운데 1곳(가운데가 R2 발생 거리 밖일 만큼 넓은 면은 가장 긴 변 가운데에서 0.5 m 안쪽 1곳을 더함), 판정 시각에 유효한 개구부 구역(`zone_type` OPENING)마다 가장 긴 변 가운데에서 바깥 0.2 m 의 바닥 1곳(계획 위치 생성 규칙의 초기값 0.2 m; LIVE R1 이 점 기준 발생으로 바뀜에 따라 PLANNED 개구부 대표 위치를 구역 안쪽으로 둘지 여부는 구현 티켓 `S15P31A101-431` 에서 정리). 그 밖의 구역 유형에는 만들지 않고, 머리 높이는 주지 않으며(VOLUME_3D 구역에서는 확인 필요 `Z_UNKNOWN`), 같은 레이아웃·판정 시각이면 같은 위치·같은 ID(`gen-<작업면·구역 ID>-<순번>`)다. 수치 근거는 `docs/design/risk-engine-container.md`.
- **평가한 위치 없음.** 만들 작업면·유효한 개구부가 없고 요청도 위치를 주지 않으면 결과의 위치 목록이 비고 위험 항목도 없다. 이것은 사람 대상 규칙을 판정할 위치가 없었다는 뜻이지 ‘위험 없음’이 아니다. 보고서·화면은 ‘평가한 작업 위치 없음’으로 보이고, 필요하면 관리자가 위치를 준다. 계약은 빈 위치 목록을 그 뜻으로 읽고, 선택 표시 `no_evaluated_positions` 로 명시할 수 있다(`risk_plan_result` 1.1.0, 컨테이너가 채우는 것은 19.1).
- Risk Engine이 PLANNED 출처로 규칙을 계산한다(수평 거리와 높이 차 포함). 위험 항목은 확률 대신 등급 + 근거로 표현한다(“추락 리스크 85%” 같은 수치는 쓰지 않는다).
- 계산 요청과 현장 이력 연계: 관리자가 `POST /api/reports/tbm`(작업 ID `workId` 지정, 하위 호환 `layoutId`)을 부르면 EC2 가 그 작업에 연결된 가상 레이아웃으로 Risk Engine Python 컨테이너(`deploy/risk-engine`)에 PLANNED 계산을 요청하고(결과는 `sim.*`), 해당 구역들의 최근 `risk_event` 발생 이력 요약(구역별 건수·최고 등급·대표 규칙, 폐지된 반장 조치 티켓은 제외) 및 개인정보가 아닌 공종(`work_type`)과 함께 같은 Python 컨테이너의 보고서 생성 경로(`POST /v1/report/generate`, 12.2)를 호출한다(GPU·Pod 불필요, I5 `tbm_report` 작업은 폐기 예정, v1.3 수정 49). 작업명·인원·반장/조 이름은 LLM 에 보내지 않고 서버가 보고서 머리말에만 붙인다(5.4). M3 에는 단독 평가 API 가 필요 없다(단독 평가는 부록 C.4).
- 법령 지식 그래프 검색과 4단계 생성·검증: EC2 Python 컨테이너가 PostgreSQL 법령 지식 그래프(`rag_node`·`rag_edge`, `Qwen/Qwen3-Embedding-0.6B` 1024차원)에서 규칙 태그·키워드(`pg_trgm`)·벡터(`pgvector`) 하이브리드 검색과 참조 엣지 1단계 확장으로 후보를 모으고(1단계), 허용 인용 ID 목록을 확정한 뒤(2단계), 외부 LLM(5.4, 텍스트만 전송)으로 초안 JSON 을 1회 작성하고(3단계), 코드 검증으로 허용 목록·본문 미허용 조문 번호·확률 표현·등급 불변성을 검사한다(4단계, 위반 시 최대 1회 재작성). 일일 일지도 같은 컨테이너 경로(`report_kind` DAILY, `POST /api/reports/daily`)로 만든다(`docs/design/tbm-legal-graph.md`).
- 출력과 관제 웹 작업 관리(`/tbm`) 화면 흐름: 보고서(PDF 는 브라우저 인쇄로 만든다, 별도 내보내기 API 없음), 계산 근거 표, 인용된 법령·지침·사례의 관계 서브그래프(`subgraph`: `nodes[]`·`edges[]`) 및 4단계 실행 상태(`steps[]`: 단계별 건수·결과·소요 ms)를 작업별 최신 보고서와 버전 이력으로 조회한다(`GET /api/reports/tbm?workId={workId}`, `GET /api/reports/tbm/{reportId}`). 관제 웹앱 작업 관리(`/tbm`) 화면은 작업 등록·수정·시작·종료(`/api/work-units`, `/api/work-units/{id}/start`, `/api/work-units/{id}/end`, `/api/layouts`)와 보고서 생성·조회·전자서명(`/api/reports/tbm`, `/api/reports/tbm/{reportId}/signatures`)을 연결해 ① 왼쪽 패널의 **위험성 평가 표** ← PLANNED 판정 결과, ② **대책·법령 근거(새 칸)** ← 보고서 문단(`sections`)·인용(`citations`), ③ **법령 그래프 패널·단계 표시** ← `subgraph`·`steps`(시연 Scene 6), ④ 오른쪽 패널의 **A4 회의록** ← 위 값들과 작업 머리말·작업 마무리(`wrap_up_summary`)·참석자 전자서명으로 자동 채움(고정 체크리스트 문구는 유지하고 잠기지 않은 버전은 사람이 편집 모달에서 수정 가능)으로 그린다. 기존 `tbmDemo.ts` 목 데이터는 API 실패 시 대체 화면으로만 쓴다(`docs/design/tbm-legal-graph.md`, `docs/design/work-session-flow.md`).
- **작업 종료 시 TBM 보고서 “작업 마무리” 자동 채움(v1.3 수정 52):** 관리자가 작업 종료(`POST /api/work-units/{id}/end`)를 누르면, 서버가 그 작업의 실제 진행 구간(`[actual_started_at, actual_ended_at]`)과 대상 구역에서 발생한 **실제 LIVE `risk_event` 집계 사실**(등급별·규칙별 건수, 최대 등급, 운영자 확인/종료 건수, 작업 외 진입 건수)을 모으고, EC2 Python 컨테이너(외부 LLM)가 이 집계 사실만으로 TBM 보고서의 **“작업 마무리”** 문단(`wrap_up_summary`)을 작성해 **새 `report_version`** 으로 저장한다(실명·얼굴·영상 미전송, 숫자 불일치·타임아웃 시 결정론적 요약 문장 폴백).
- **참석자 전자서명과 버전 잠금·내용 해시(v1.3 수정 52, NFR-14 예외):** TBM 보고서(회의록)에 참석자 전자서명을 둔다(`POST /api/reports/tbm/{reportId}/signatures`). 서명자 **실명(`signer_name`)과 손글씨 서명 이미지**는 **서버(`report_signature` 표 및 비공개 객체 저장소)에만 저장**하고 관리자(`ADMIN`)만 조회하며, **외부 LLM 에는 절대 보내지 않는다**(NFR-14 개정: 작업명·담당 조·추적 ID 에는 여전히 사람 이름을 넣지 않고 TBM 참석자 전자서명 기록에만 실명 허용, 11.4-5·14장). 첫 서명이 등록되면 해당 보고서 버전(`report_version`)을 **잠그고(`locked_at`)** 보고서 본문 정규화 해시(**`content_sha256`**)를 고정한다. 보고서를 수정하거나 작업 종료로 “작업 마무리”가 추가되면 **새 버전(`report_version + 1`)** 이 만들어지며 재서명을 받는다. 화면과 인쇄본에는 **`"공인 전자서명 아님, 내부 기록용 전자 서명"`** 을 표시한다.

## 8.4 F-09 반장 PWA (MVP, M1·M2)

- 반장 휴대폰으로 위험 알림(Web Push)이 오고, 위치·근거·관련 구역을 보여준다(M1).
- CRITICAL·HIGH 이벤트가 생기면 조치 티켓을 “요청” 상태로 자동 생성한다. 관리자도 티켓을 조회해 종료 절차에서 미결을 확인한다(M2).
- 조치 상태: 요청 → 확인 → 조치 중 → 완료. 완료 시 조치 사진을 업로드한다(M2).
- 조치 완료는 사람의 보고이고, RiskEvent 해소는 관측 확인이다. 조치 완료와 관측의 불일치 알림(`action_mismatch`, 관리자 토픽 `/topic/admin/events`)은 두지 않는다(2026-11-02 취소, S15P31A101-411). 반장 PWA·조치 티켓 자체의 정리(2026-10-31 팀 결정)는 별도 이슈에서 한다.
- MVP 에서 카메라에 잡힌 모든 사람의 위험은 이 경로로 반장에게 전달된다(개인 채널인 워치는 부록 C).
