# S15P31A101-696 작업 1건 안의 실행(run) 여러 번

사용자 결정(2026-11-14, 방식 B): 같은 날 리허설 뒤 본 시연을 한다. 하루 작업 여러 건(A)이나 끝난 작업 다시 열기(reopen, 기록을 지움)
대신 **작업 1건 안의 실행 여러 번**이다. TBM·세팅은 하루 한 번, 「작업 시작 ~ 작업 종료」만 실행 1·2… 로 반복하고 실행마다 시작·종료
시각·이벤트·녹화 구간·다시 보기가 따로 남는다. 보고서는 하루 끝에 한 번 제출한다.

관련 명세: 3.2(구성 묶음·이벤트 소유권), 8.3(작업 시작·종료), 8.5·11.5·12.6(녹화 업로드·다시 보기), 13장(실시간 관제), 18(운영·배포).
앞 설계: -679(작업 시작 = 관제 시작), -692(관제 시작·종료 표시), -693(종료 → 업로드 → 다시 보기), -676·-682(배포 보류).

## 1. 실행 모델

### 1.1 DB (V73 `work_run`, 추가 전용)

| 칸 | 뜻 |
|---|---|
| `work_id`, `run_no` (PK) | 하루 작업과 실행 번호(1부터) |
| `site_id` | 현장(현장당 열린 실행 하나 부분 유일 색인 `work_run_one_open_per_site`) |
| `started_at`·`started_by` | 시작 시각(EC2 시계)·시작한 관리자 |
| `ended_at`·`ended_by` | 종료 시각·종료한 관리자. 진행 중이면 NULL. 종료 때 NULL 인 행만 한 번 채운다 |
| `preflight` (jsonb) | 시작 전 확인 스냅샷: 참석자 서명 수(날짜 작업)·서명이 묶인 보고서 id·판·안전모·조끼 요구 |

- 기존 작업은 마이그레이션이 실행 1 로 채운다(시작한 작업만, 시작·종료한 사람은 비움).
- 뷰 `work_run_window`: 실행 표 + 실행 기록이 없는 시작한 작업(실행 표 밖에서 work_unit 시각만 쓴 경우: 시험 데이터, 옛 복구 경로,
  `seed-mock-history.sh`)의 work_unit 시각을 실행 1 로. 실행 구간을 읽는 곳(작업 응답·녹화·업로드 상태·배포 보류·마무리)은 이 뷰만 쓴다.
- `report.wrap_up_ending`: 서버가 종료 미팅(review.ending)에 마지막으로 채운 글(1.4).

### 1.2 work_unit 은 하루 요약으로 둔다

- `actual_started_at` = **첫 실행 시작**(다시 시작해도 `COALESCE` 로 지킨다), `actual_ended_at` = **마지막 실행 종료**(실행 중이면 NULL).
- `status`: 실행 중 IN_PROGRESS, 끝난 실행만 있으면 DONE. V30 CHECK(`IN_PROGRESS ⇔ 시작 있음·종료 없음`)와
  `work_one_in_progress_per_site` 를 그대로 지킨다.
- 근거: 진행 중 판단(관제 화면·ppe_policy·세팅 차단·레이아웃 구역 잠금·워치 등 status = 'IN_PROGRESS' 를 보는 곳 십여 군데)과 달력·작업 목록
  이벤트 집계(첫 시작 ~ 마지막 종료, 실행 사이에는 Tier 0 가 판정하지 않아 이벤트가 없다)가 바뀌지 않는다. 실행 사이 구간이 필요한 곳만
  실행 표를 읽는다. `actual_ended_at` 은 다시 시작할 때 NULL 로 돌아가지만(파생 값) 실행별 종료는 실행 표에 남는다.

### 1.3 상태 전이(`WorkUnitRepository.startSession/endSession`)

```
PLANNED --시작--> IN_PROGRESS(실행 1) --종료--> DONE --시작(한 번 더)--> IN_PROGRESS(실행 2) --종료--> DONE --제출--> (SUBMITTED, 더 시작 못 함)
```

- 시작: PLANNED 또는 DONE 만. DONE 이면 TBM 보고서를 제출하지 않았어야 한다(409 `WORK_REPORT_SUBMITTED`). 그다음은 기존 검사 그대로
  실행마다 다시 본다: 오늘 날짜(날짜 작업)·세팅 완료·참석자 서명 1명 이상(날짜 작업)·진행 중 작업 없음(409 `WORK_ALREADY_IN_PROGRESS`).
  진행 중이면(같은 작업) 409 `WORK_INVALID_STATE`.
- 동시 시작: `lockSession` 의 현장 행 `FOR UPDATE` 가 같은 현장의 시작·종료·제출을 한 줄로 세운다. 부분 유일 색인 두 개가 마지막 방어다.
  제출(`TbmReportRepository.submit`)도 작업 행을 잠그므로 제출과 다시 시작이 겹치지 않는다.
- 실행 표 밖에서 끝난 작업(work_unit 만 DONE·PLANNED 로 바꾼 경로)의 열린 실행은 시작 때 그 작업 종료 시각으로 닫는다(현장당 하나 색인에 걸리지 않게).
- 실행 기록 없이 시각만 있는 작업을 다시 시작하면 그 시각을 실행 1 로 먼저 남긴다(뷰가 실행 1 을 잃지 않게).
- 종료: 열린 실행 하나를 닫고 work_unit 을 DONE, `actual_ended_at` = 그 종료. 묶음 발행·마무리 준비는 기존과 같다.
- `reopen`(-649, 화면 없음)은 그대로 두었다. 실행 기록은 지우지 않으므로 되돌린 뒤 시작은 다음 실행 번호가 된다.

### 1.4 보고서 마무리(하루 끝 한 번 제출)

- 실행을 끝낼 때마다 기존처럼 마무리 사실을 고정하고 종료 미팅을 만든다. 사실은 첫 시작 ~ 마지막 종료 구간 중 **끝난 실행 구간 안**
  이벤트만 센다(`aggregate`, 실행 사이 이벤트 제외). 계약 `tbm_form_ending_request` 는 바꾸지 않았다(facts 는 닫힌 값 객체).
- 종료 미팅은 비어 있거나 **서버가 지난 실행 종료 때 채운 글 그대로**(`wrap_up_ending` 과 같음)일 때 다시 쓴다. 사람이 고친 글은 둔다.
- 실행이 둘 이상이면 서버가 앞에 실행 요약 한 줄을 붙인다: `실행 2회: 1회 14:00–14:20(위험 0·경고 1), 2회 15:00–15:30(위험 1·경고 0).`
  (현장 시각, 작업 구역 기준 LIVE CRITICAL·HIGH 수, DB 에서 센다. AI 가 쓰지 않는다. 합쳐 2000자를 넘으면 뒤를 자른다.)
- 제출은 DONE 일 때만(기존). 제출하면 다시 시작하지 못한다.

## 3. 화면 흐름

1. 실행 1 종료 → 종료 화면(현장 경보 종료 확인·실행 기록·보고서). 단추 「보고서 제출」·「한 번 더 실행」.
2. 「한 번 더 실행」 → 작업 전 확인(같은 날짜 화면, 서버는 그대로 ENDED). 맨 위 「실행 2 시작 전 확인」과 카메라 재점검 문구,
   끊긴 카메라가 있으면 「카메라 a/b 연결 · 끊긴 카메라를 확인하세요」. 확인창(체크 2개·서명·보호구)을 다시 거친다. 「작업 종료로」 로 돌아간다.
3. 작업 시작 → 실시간 관제(-692 와 같다) → 작업 관리로 돌아오면 작업 종료 단계(실행 2 진행 중).
4. 종료 → 종료 화면(실행 기록 두 줄) → 보고서 제출 → 지난 날짜 화면(실행 선택).

세팅 화면(`features/setup`)은 건드리지 않았다(-689·-690·-691 범위). 재점검은 문구로만 유도한다.

## 5. 버린 대안

| 안 | 버린 이유 |
|---|---|
| 하루 작업 여러 건(A) | 사용자 결정. TBM·세팅·서명이 작업마다 다시 필요하다 |
| 끝난 작업 다시 열기(reopen) | 실행 1 기록(시각·마무리)을 지운다(규칙 6 덮어쓰기) |
| `ppe_policy` 에 run id 추가 | I1 LIVE 계약(config_bundle 구성 요소) 변경이라 Lead 승인이 필요하다. Tier 0 는 종료 묶음의 work_id null 로 이미 실행을 가른다(-679 의 꺼짐 → 켜짐). 실행 사이가 화면 조작이라 종료 묶음을 건너뛸 일이 사실상 없다(남은 위험 1) |
| work_unit 에 실행별 칸을 두거나 시각을 실행마다 덮기 | 지난 실행 시각을 덮는다. 실행 표가 정본이고 work_unit 은 요약이다 |
| V30 CHECK 를 풀어 실행 사이에도 `actual_ended_at` 유지 | IN_PROGRESS 판단·배포 보류 등 기존 소비자 의미가 바뀐다 |
| `recording_upload_progress`·`recording_upload_status` 에 run_no | 계약 두 개·V70 키 변경. 화면 상태는 작업 단위로 충분하고, 조각 등록 수는 작업 단위로 센다 |
| `tbm_form_ending_request.facts` 에 실행 목록 추가 | 닫힌 값 객체라 계약·위험 엔진 컨테이너(숫자 검사·문장)까지 바뀐다. 서버가 DB 사실로 한 줄을 붙이는 편이 작고 결정적이다 |
| 실행 표에 트리거로 추가 전용 강제 | 저장소에 트리거를 쓰는 곳이 없고, 시험·옛 경로가 work_unit 만 바꾸는 경우를 시작 때 바로잡는 편이 운영에 덜 위험하다 |

## 8. 남은 위험

1. Tier 0 가 실행 1 종료 묶음을 적용하기 전에 실행 2 시작 묶음이 오면(실행 사이가 수 초 이내이거나 Tier 0 재시작 중 종료·시작) 같은
   work_id 라 실행 1 의 열린 이벤트가 실행 2 로 이어진다(-679 의 「작업 A→B」 구분은 작업 id 로만 한다). 실행 사이는 화면 조작이라
   시연에서는 생기지 않는다. 필요하면 ppe_policy 에 run id 를 싣는 I1 변경(Lead 승인)이 다음 단계다.
2. 업로드 상태는 작업 단위라, 실행 2 진행 중에는 끝난 실행 1 몫만 보고 COMPLETED 로 보일 수 있고 실행 2 가 끝나면 다시 UPLOADING 이 된다.
3. 한 번 더 실행을 누른 화면 상태는 브라우저 메모리(날짜 화면)다. 새로고침하면 종료 화면으로 돌아간다(서버는 바뀌지 않았다).
4. 카메라가 실행 사이에 옮겨졌는지는 알 수 없다. 끊김만 보이고 나머지는 문구로 유도한다. 세팅 재점검 흐름은 -689·-690·-691 몫이다.
5. 실행 1 종료 미팅 생성(LLM 수 초~수십 초)이 끝나기 전에 실행 2 를 시작·종료하면 늦게 온 실행 1 결과가 실행 2 사실 대신 채워질 수 있다
   (같은 request_id). 실행이 그만큼 짧을 때만이다.
6. reopen 뒤에는 work_unit.actual_started_at(새 시작)과 실행 1 시작이 다르다. reopen 은 이제 쓰지 않는 복구 경로다.
