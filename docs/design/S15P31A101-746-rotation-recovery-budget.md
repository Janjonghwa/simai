# 회전 복구 CPU 예산 이월 끝내기 (S15P31A101-746)

18차(2026-11-15, H100·Xeon 8460Y+, 분리 끔 구간) tier0.log 에 「회전 복구 다음 주기로 이월: CPU 시간 예산 초과(500ms)」가
13:24:41~13:44:53 동안 51회 연속 찍히고 완료는 0회였다. 사람 관절 보정(drift_watch)은 기본 꺼짐이라 관제 중 카메라 틀어짐·쓰러짐
감지 경로가 이 배경 비교 하나뿐인데 20분 동안 멈춰 있었다. 이 티켓은 원인을 재고, 15초 주기마다 판정이 끝나게 고친다.
-738(분리 곁가지 이전)·-744(분리 경로 Re-ID) 위에서 고쳤고 그 둘 뒤에 머지한다.

## 2. 원인

### 2.1 구조(코드·로그로 확정)

옛 작업자는 최근 배경 특징을 서명(세대·창 첫 표본·끝 표본 시각)으로 캐시했다. 관제 표본은 카메라마다 5 s 간격이라 15 s 주기마다
4대 서명이 모두 바뀐다. 그래서

1. 한 주기에 4대를 다 못 뽑고 예산(500 ms)을 넘기면 `BUDGET_DEFERRED` 로 끝나고, 그 주기에 끝낸 카메라의 특징도 다음 주기에는
   서명이 달라 버려진다. 다음 주기는 4대를 처음부터 다시 뽑는다. 한 주기 비용이 예산보다 크면 영원히 끝나지 않는다(이월 51회·완료 0).
2. 계산이 끝난 뒤 서명이 하나라도 바뀌었으면(계산 중 새 표본) 결과를 버리고 `WAITING_NEW_SAMPLES` 를 냈다(로그 없음). 4대가
   제각기 5 s 마다 표본을 넣어 평균 1.25 s 마다 어느 서명이 바뀐다. 20분이면 약 76주기인데 이월 로그는 51회라, 나머지 약 25주기는
   이 경로로 조용히 버려진 것으로 추정한다.
3. 예산 검사가 판정(매칭·추정) 앞에도 있어, 추출을 마친 뒤 판정에서 넘겨도 전부 버렸다.

### 2.2 수치(노트북, 실제 로비 배경 2304x1296 4대, `val01` 배경, 작업자 프로세스 CPU 시간)

Windows `process_time` 해상도가 15.6 ms 라 단계 값은 ±16 ms 다.

| 주기 | reference_read | reference_extract | recent_prepare | recent_extract | matching+estimation | 합 |
|---|---|---|---|---|---|---|
| 첫 주기(기준 4장 PNG 읽기·특징) | 219~312 | 62~141 | 31~94 | 16~62 | 0~16 | 453~531 |
| 다음 주기(새 표본 3장/대) | 0 | 0 | 47~125 | 62~78 | 16~31 | 141~203 |
| 같은 조건 + 사람 5명 가림 흉내 | 0 | 0 | 47~78 | 62~78 | 16~31 | 156~203 |

- 카메라 1대 최근 특징(긴 변 320 px, 단일 스레드 벽시계): 축소 9 ms, 중앙값 합성 13 ms, SIFT 15 ms, 매칭 3 ms, 추정 1~7 ms.
- 요청 크기: 카메라당 최근 10장(960 px)을 매 주기 다 보내 4대 83 MB, 작업자 역직렬화 21 ms(벽시계). 부모 스레드 CPU 도
  18차 `thread_cpu` 에서 `tier0-rotation-recovery` 0.4%(주기당 약 60 ms, 대부분 pickle).
- 기준 특징이 320 px 에서 80개 미만이면 960 px 로 돌아가는데, 이때 카메라당 합성 116~125 + SIFT 88~94 + 매칭 17~30 ms 로 4대 약
  950 ms 다(로비 배경 4장은 320 px 에서 278~331개라 이 경로가 아니다).
- 18차 서버의 단계별 값은 로그에 없었다(이 티켓에서 stage_timing 에 싣는다). 옛 작업자를 CPU 시계 3배(느린 서버 코어 흉내, 같은
  프로세스)로 돌리면 다음 주기가 422~469 ms 이고 실제로는 83 MB 역직렬화(시스템 CPU 포함)가 더해져 500 ms 경계에 걸린다. 한 번이라도
  넘기면 위 1·2 때문에 다시 끝날 수 없다. 서버 코어가 노트북보다 3배 이상 느리면(2.0 GHz 기본·SMT 공유·캐시 경합) 18차 현상과 맞다.

## 3. 고친 방법

### 3.1 카메라 단위 이월(작업자)

- 예산은 카메라 단위 특징 추출(기준 1회, 최근 매 주기)만 끊는다. 카메라를 시작하기 전에 검사하고, 이번 주기에 이미 한 카메라라도
  했으면 멈춘다. 주기마다 최소 1대는 진행한다(역직렬화만으로 넘긴 주기도).
- 끝낸 카메라의 최근 특징은 새 표본이 와도 버리지 않는다. 다음 주기 판정에 이어쓸 수 있는 조건: 같은 세대(카메라 리셋 없음),
  같은 카메라 파라미터·추출 설정, 지금 창 끝 시각과의 차이 `max_feature_age_ms` 이내(= 2 x 주기 = 30 s).
- 다음 주기에는 특징이 없거나 쓸 수 없는 카메라 → 가장 오래된 카메라 순으로 뽑는다. 모든 카메라가 쓸 수 있으면 판정한다.
- 판정(카메라당 매칭 1회·적합, 회전 후보일 때 인접 쌍 검사)은 예산과 무관하게 끝까지 한다. 비용이 묶여 있고(320 px 4대 16~31 ms),
  끊으면 1번의 낭비가 되풀이된다.
- 보고서 `recent_samples_ms` 는 실제로 쓴 특징의 창 끝 시각이다. `observe_drift` 는 카메라별 끝 시각이 늘 때만 세므로 이어쓴 특징이
  확인 횟수를 두 번 세지 않는다. 회전 후보 `observe` 는 최소 끝 시각이 늘어야 센다.
- 기준 배경 특징은 키(폴더·세대·보정 버전·카메라·설정)가 같으면 한 번만 뽑는다(-494 그대로). 벤치·시험에서 다음 주기
  `reference_read`·`reference_extract` 가 0 인 것을 확인한다.

### 3.2 계산 중 새 표본은 결과를 버릴 이유가 아니다(부모)

결과는 그 창에 대한 판정으로 유효하다. 카메라 리셋(서명의 세대가 바뀜)이거나 그 카메라 창이 사라진 때만 버린다. 이어쓴 카메라가
있으면 새 표본이 없어도 다음 주기에 마저 뽑도록 `_last_signatures` 를 남기지 않는다.

### 3.3 새 표본만 보낸다

작업자는 받은 표본(키: 세대·촬영 시각·원본 크기)을 지금 창만큼 보관하고, 응답에 가진 키 목록(`cached_samples`)을 싣는다. 부모는 다음
요청에서 그 키 자리를 `None` 으로 비운다(`omit_rotation_samples`, 원본 스냅샷은 바꾸지 않음). 15 s 주기·5 s 표본이면 10장 중 7장이
비어 83 MB → 약 25 MB 다(벤치: 주기당 40장 → 12장). 수치 경로(960 px 축소 → 작업자 320 px 축소)는 그대로다.

- 작업자가 없는 키를 받으면 `SAMPLE_CACHE_MISS` → 부모가 비운 자리 없이 한 번 더 보낸다(`sample_resyncs`).
- 작업자가 죽었으면(다음 주기 시작 때 `poll`) 받은 키를 비우고 처음부터 다 보낸다.
- 분리 켬: `RemoteCleanBackground.rotation_snapshot(omit_samples=)` 가 `bg_dump_rotation` 명령의 넷째 인자로 키를 보내고, 검출 프로세스의
  `ChildSideWork._dump_rotation` 이 그 자리를 비운 채 파일을 쓴다(파일·판정 쪽 unpickle 도 70% 준다). 넷째 인자가 없으면 지금처럼 다 쓴다.

### 3.4 예산 500 → 1000 ms

카메라 단위 이월만으로도 끝나지만, 4대를 매 주기 새로 뽑아야 감지 지연이 설계(창이 찬 뒤 2주기)대로다. 노트북 다음 주기 141~203 ms 에
서버 3배를 곱하면 420~610 ms 라 500 ms 로는 한두 대가 자주 이어쓰기로 밀린다. 1000 ms 면 4배 느린 코어까지 4대를 매 주기 뽑는다.
작업자는 별도 프로세스·nice 10·스레드 1 이라 Tier 0 검출·판정 스레드와 CPU 를 나누지 않는다. 1000 ms/15 s = 코어 하나의 6.7%
(18차 Tier 0 프로세스는 331%).

| 경우 | 지연 |

| 대안 | 버린 이유 |

| 한 주기에 1~2대씩 고정 순환 | 비용이 충분히 작아도 카메라마다 2~4주기에 한 번만 보므로 쓰러짐 확정이 2주기 → 4~8주기로 늘어난다. 지금은 예산을 넘길 때만 나눈다 |
| 최근 표본을 320 px 로 줄여 넘김(다운샘플) | 2304→320 한 번 축소는 기준 경로(2304→960→320)와 보간이 달라 원본 px 단위 잔차 게이트(3 px = 320 px 의 0.42 px)에 영향을 준다. 새 표본만 보내기로 IPC 를 같은 정도 줄이면서 수치는 그대로 둔다 |
| 예산만 올림 | 더 느린 코어·960 px 경로에서 같은 무한 이월이 다시 난다(근본 원인 1·2 미해결) |
| 이어쓰기 나이 제한 없음 | 오래된 특징이 쓰러짐을 가릴 수 있다. 30 s 로 묶었다 |
| 판정 단계도 예산으로 끊기 | 추출을 끝낸 뒤 판정에서 끊기면 다음 주기에 새 표본으로 추출부터 다시 해 같은 낭비가 난다 |

## 9. 남은 일·잔여 위험

- 18차 서버의 실제 단계·카메라별 CPU 는 아직 모른다. 다음 GPU 세션에서 `stage_timing.rotation_recovery`(`cpu_ms_by_camera`,
  `carried`, `consecutive_deferrals`)와 「회전 복구 완료」 줄을 확인한다.
- 첫 주기의 기준 PNG 4장 읽기(노트북 219~312 ms)는 한 번뿐이지만 느린 코어에서는 두 주기에 걸칠 수 있다.
- 960 px 경로(희박 장면)는 서버 3배면 카메라당 약 700 ms 라 한 주기 2대씩 번갈아 뽑는다(이어쓰기 15 s, 판정은 매 주기).
- `camera-fall-drift-detection.md` 5절의 `interval_ms = 60_000`·`cpu_budget_ms = 500` 서술과 -738 설계의 「회전 복구 입력 4대 약 80 MB」는
  이 문서로 갱신된다(명세 정리 MR 에서 반영).
