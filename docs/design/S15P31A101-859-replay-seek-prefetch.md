# 지난 작업 다시 보기: 위험 이벤트 조각 미리 받기·이동 중 앞 화면 유지

S15P31A101-859. 지난 작업 다시 보기(`features/history`, 화면은 `work/past`)에서 이벤트 줄·타임라인 표식을 눌러 다른 30초 조각으로 넘어갈 때
4칸 영상이 잠깐 멈추던 것(2026-11-23 사용자 보고)을 줄인다. 관련: 668 설계 1.9 화면(`docs/design/S15P31A101-668-recording-s3-playback.md`),
명세 12.6(서명 주소)·14장(조회 기록). 서버 변경 없음.

## 1. 원인

- 운영 녹화는 카메라마다 약 30초 조각, 약 4 MB, 1.1 Mbps, 25 fps, mp4 faststart.
- 칸은 지금·다음 조각만 `<video>` 로 그린다(`useSegmentSwap`). 조각 밖으로 뛰면 4칸 모두 서명 주소 요청(EC2) → S3 받기 → 디코딩·이동을 처음부터 했다.
- 서명 주소 쿼리가 `gcTime: 0` 이라 이미 본 시각으로 돌아가도 주소·영상을 다시 받았다.
- 떼어 낸 `<video>` 를 비우지 않아 GC 전까지 받기·디코더를 쥐고 있었다(측정 중 발견: 뛰어넘을 때마다 쌓이면 새 칸 첫 화면이 1.7 s 대로 늦었다).

## 2. 사용자 결정(2026-11-23, 바꾸지 않는다)

| 항목 | 결정 |
|---|---|
| 마우스 올리기 미리 받기 | **하지 않는다**(hover·focus·pointerdown 모두). 처음 지시였으나 사용자가 방향을 바꿨다 |
| 미리 받을 것 | 시연에서는 위험(CRITICAL) 이벤트 부분만 영상으로 확인하므로, 이 작업 구간의 **위험 이벤트 시각마다 그 시각을 덮는 4칸 조각** |
| 시작 때 | 화면에 들어와 지금 보이는 4칸이 모두 첫 화면(loadeddata)을 낸 뒤 |
| 받는 방식 | 서명 주소로 조각 전체를 `fetch` 해 Blob 으로 보관하고, 그 조각이 칸에 올라오면 **blob 주소로 재생**(새 `<video>` 가 HTTP 캐시를 다시 쓰는지에 기대지 않는다). 서명 주소 만료와 무관 |
| 순서·상한 | 위험 이벤트 시각순, 동시 받기 4개 이하, 위험 이벤트 최대 6개(조각 최대 24개 ≈ 100 MB). 같은 조각은 한 번만 |
| 해제 | 화면을 떠나면(작업 구간이 바뀌어도) 받는 중인 것을 끊고 blob 을 모두 해제(`URL.revokeObjectURL`) |
| 나머지 이벤트 | 주의(CAUTION)·경고 등은 지금처럼 눌렀을 때 받는다 |
| 함께 유지 | 서명 주소 약 4분 보관, 넘어가는 동안 「불러오는 중」 표시 |

## 3. 설계

### 3.1 위험 이벤트 조각 고르기(`segmentPrefetch.ts` `criticalPrefetchSegments`)

- 이벤트를 누르면 옮겨 가는 시각 = `eventJumpAt(raisedAt, from)` = max(작업 구간 시작, 발생 − 3 s). 지난 날짜 화면(`PastDayPage.pickEvent`)도 같은 함수를 쓴다(값을 한 곳에 둠).
- 위험 이벤트를 발생 시각순으로 보며, 옮겨 갈 시각을 덮는 카메라별 조각(`activeSegments`, 칸이 쓰는 규칙 그대로)을 모은다.
  이미 고른 조각만 덮는 이벤트(같은 30초 안의 위험 여러 개)는 세지 않는다. 이벤트 6개까지.

### 3.2 blob 보관소(`createSegmentBlobCache`, `fetchSegmentBlob`)

- 줄 세운 순서대로 동시에 4개까지 받는다. 받은 조각 id 를 기억해 같은 조각은 다시 줄 세우지 않고, 24개(`PREFETCH_MAX_EVENTS × 4`)를 넘게 받지 않는다.
- 받기: 서명 주소는 칸과 같은 쿼리(`videoUrlQuery`, `queryClient.fetchQuery`)로 받아 4분 보관을 함께 쓴다 → `fetch(url, { credentials: 'omit' })` → Blob → `createObjectURL`.
  `h264-annexb` 조각(Tier 0 상시 조각, 지금 운영 경로 아님)은 클립과 같은 `loadPlayableClip` 으로 mp4 로 감싼 blob 이다.
- 실패한 조각은 다시 받지 않는다. 칸은 그 조각을 서명 주소로 튼다(지금과 같음).
- `dispose`: `AbortController` 로 받는 중인 것을 끊고, 받아 둔 blob 과 dispose 뒤에 끝난 것을 모두 해제한다. 그 뒤 `prefetch` 는 아무것도 하지 않는다.
- 수명: `useSegmentBlobCache(range.from)` 가 effect 에서 만들고 정리한다(StrictMode 두 번 실행에도 하나). 작업 구간이 바뀌면 새로 만든다.

### 3.3 시작 시점(`ReplayStage` `ReplayCctv`)

- `ReplayVideoWall` 이 칸마다 보이는 영상이 있는지(`shownId`)를 모아, 영상 칸이 모두 첫 화면을 내면 `onFirstFrames` 를 한 번 부른다. 그 뒤 `blobs.prefetch(...)`.
  지금 보이는 칸의 받기와 다투지 않게 하려는 것이다. 작업 구간마다 다시 기다린다.
- 지금 시각에 영상 칸이 하나도 없으면(목 화면) 다툴 받기가 없으므로 기록을 다 받은 뒤(`!pending`) 바로 시작한다.

### 3.4 칸에서 blob 쓰기(`ReplayVideoWall` `SegmentVideo`)

- 칸이 붙을 때 한 번 `blobs.get(id)` 를 본다. 있으면 그 blob 주소로 틀고 서명 주소 쿼리는 돌리지 않는다(`enabled: false`).
  재생 중에 blob 이 다 받아져도 주소를 바꾸지 않는다(바꾸면 처음부터 다시 읽어 멈춘다).
- blob 을 읽지 못하면(`onError`) 서명 주소로 다시 튼다. 그 뒤 만료 오류는 기존 경로(한 번 `refetch`, 또 실패하면 조각 빼기) 그대로다.

### 3.5 서명 주소 4분 보관

- `videoUrlQuery`: 키 `['history', 'video-url', id]`, `gcTime` = `staleTime` = 4분(`VIDEO_URL_CACHE_MS`), 서버 서명 5분보다 1분 짧다.
- 칸은 붙을 때(`mountedAt`) 4분보다 오래된 주소는 쓰지 않는다. 그런 주소는 stale 이라 붙을 때 다시 받고, 새 주소가 오면 그것으로 시작한다(만료 직전 주소로 시작해 곧 오류가 나지 않게).
  붙어 있는 동안에는 주소가 4분을 넘어도 그대로 쓴다(만료 오류가 나면 기존 재요청 경로).
- 보관해 둔 실패(4xx 등)는 칸이 붙을 때 다시 받으므로, 받는 중에는 실패로 보지 않는다(`isError && !isFetching`). 「영상 다시 확인」이 계속 실패로 남지 않는다.
- blob 해제 시점: 예전에는 한 쿼리가 서명 주소 받기와 annexb 감싸기(blob)를 같이 해 `gcTime` 을 늘리면 칸이 사라질 때 해제한 blob 을 보관 데이터가 가리킬 수 있었다.
  그래서 쿼리를 나눴다. 서명 주소(JSON)만 4분 보관하고, 감싼 blob 은 `['history', 'video-wrap', id, url]`, `gcTime: 0`, 칸이 사라지면 해제(지금과 같음). mp4 는 감싸지 않는다.
  미리 받은 blob 은 쿼리 밖 보관소가 들고 화면을 떠날 때만 해제한다.

### 3.6 넘어가는 동안

- 다른 조각으로 넘어가면 새 조각이 첫 화면을 낼 때까지 마지막으로 보이던 조각을 멈춘 채 보인다(`useSegmentSwap` 의 held, 지금과 같음).
  그 위 왼쪽 아래에 작은 「불러오는 중」(점 셋)을 띄운다. 같은 조각 안에서 옮기는 동안(`seeking`)에도 띄운다. 빈 칸·검은 화면은 없다.
- 칸에서 빠진 `<video>` 는 `src` 를 지우고 `load()` 해 받기·디코더를 바로 놓는다. 문서에 아직 붙어 있으면(StrictMode 의 effect 두 번 실행) 건드리지 않는다.

## 4. 측정(로컬, 목업 개발 서버 + Playwright, 2026-11-23)

조건: `VITE_API_MOCK` 개발 서버, 측정용으로만 녹화 mock 을 고쳐(커밋 안 함) 조각 30초·재생 주소 응답 120 ms 지연, 영상은 운영과 같은 형식의 시험 mp4
(2304×1296, 25 fps, 1.1 Mbps, GOP 2 s, faststart, 30 s, 약 4 MB, 카메라 4개)를 로컬 서버가 첫 바이트 60 ms·응답당 25 Mbps 로 준다(S3 흉내, CORS 허용).
headless Chrome(채널 chrome), 지난 날짜 화면에서 위험 이벤트 줄을 마우스로 누른 순간(pointerdown)부터 4칸 모두 새 조각이 옮겨 간 시각(발생 − 3 s)에서 재생을 시작할 때까지.

| 경우 | 수정 전 | 수정 후 |
|---|---|---|
| 위험 이벤트로 조각 밖 이동(5회 중앙값) | 2,602 ms | 392 ms |
| 이미 본 위험 이벤트로 돌아가기(3회 중앙값) | 2,591 ms | 360 ms |
| 같은 조각 안의 다른 이벤트(첫 이벤트, 조각 이동 없음) | 225 ms | 224 ms |

- 수정 전에 조각 앞쪽(1 s)으로 가는 이벤트는 약 760 ms, 7 s 로 가는 위험 이벤트는 약 2.6 s 였다(옮겨 갈 자리까지 받아야 해서).
- 남은 약 0.35~0.4 s 는 새 `<video>` 의 디코딩·이동이다(받기 없음). 측정 PC 의 headless Chrome 소프트웨어 디코딩이라 실제 화면은 다를 수 있다.
- 첫 측정에서 수정 후가 1.7 s 와 0.4 s 로 번갈아 나왔다. 떼어 낸 `<video>` 가 디코더를 쥔 탓이라 3.6 의 비우기를 더하고 고르게 0.4 s 가 됐다.
- 측정 서버에 CORS 를 열기 전에는 `fetch` 가 막혀 미리 받기가 모두 실패했고, 칸은 서명 주소로 지금처럼 틀었다(대체 경로 확인).

| 값 | 정한 것 | 근거 |

| 시작 신호 | 영상 칸이 모두 첫 화면(loadeddata) | 사용자 결정. 지금 보이는 칸의 받기를 먼저 |

## 6. 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 마우스 올리기(hover·focus·pointerdown) 때 그 시각 조각 미리 받기 | 사용자 결정으로 하지 않음. 줄을 훑기만 해도 서명 주소 요청(조회 기록)이 쌓이고, 올린 뒤 누르기까지 짧으면 이득이 작다 |
| 작업 구간의 모든 조각 미리 받기 | 8시간 × 4대면 수 GB. 메모리·대역이 감당되지 않는다 |
| 숨긴 `<video preload="auto">` 로 미리 받고 새 칸이 브라우저 캐시를 다시 쓰기를 기대 | 서명 주소가 같아야 하고, Chrome 미디어 캐시 공유·HTTP 캐시 재사용이 보장되지 않는다(사용자 결정: blob 으로 확실히) |
| 다음 조각 준비(standby) 칸에 미리 받을 조각을 얹기 | 칸 하나에 `<video>` 가 늘어 디코더를 더 쥐고, 위험 이벤트 6개를 다 들 수 없다 |
| 서명 주소 쿼리 하나에 blob 까지 담고 gcTime 만 늘리기 | 칸이 사라질 때 해제한 blob 을 보관 데이터가 가리킨다(3.5) |

## 7. 남은 위험

- **버킷 CORS**: blob 받기는 브라우저 `fetch` 라 S3 버킷 CORS 가 화면 출처의 GET 을 허용해야 한다(`exec/02_외부서비스.md` 의 CORS 에 GET 이 있다).
  버킷을 서울로 옮기며 CORS 를 빠뜨렸다면 미리 받기가 모두 실패하고 지금처럼 서명 주소로 튼다(멈춤은 그대로). 시연 전 운영 화면에서 개발자 도구로 `fetch` 오류가 없는지 확인할 것.
- **조회 기록**: 미리 받기도 `GET /api/videos/{id}` 를 불러 조회 기록(14장)이 위험 이벤트 조각마다(최대 24개) 남는다. 관리자가 실제로 보지 않은 조각도 기록된다.
- **메모리**: blob 최대 약 100 MB 를 화면을 떠날 때까지 든다. 실제 조각이 커지면(조각 길이·비트레이트 변경) 그만큼 는다(상한은 조각 수로만 건다).
- **첫 화면 신호**: 지금 시각의 칸 하나가 끝내 첫 화면을 못 내면(받기 실패로 빠지기 전까지) 미리 받기가 시작되지 않는다. 실패한 조각은 칸에서 빠지므로 그 뒤 남은 칸이 모두 보이면 시작한다.
- 위험 이벤트가 6개를 넘으면 7번째부터는 지금처럼 눌렀을 때 받는다. 이벤트를 누른 뒤 재생이 다음 조각으로 넘어가는 경계는 기존 다음 조각 준비(5 s 앞)가 맡는다.
- 측정은 로컬 흉내(지연 60 ms, 25 Mbps)다. 운영 S3(서울)·SSAFY 망에서의 값은 다음 GPU 세션이나 운영 화면에서 다시 잰다.
