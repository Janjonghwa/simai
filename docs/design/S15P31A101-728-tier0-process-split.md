# Tier 0 검출·판정 프로세스 분리 (S15P31A101-728)

17차 GPU 세션에서 판정 스레드의 벽시계 시간이 스레드 CPU 시간의 1.45~1.66배였다(틱당 20~50 ms 를 CPU 를 쓰지 않고 기다림). 같은
프로세스 안에서 스레드 CPU 는 검출 49%·판정 48%·영상 수신 31% 였다. 판정 스레드가 GIL 을 다른 두 묶음과 나눠 쓰는 대기가 판정 지연의
상당 부분이라는 뜻이다. 2026-11-15 사용자 결정으로 Tier 0 를 **검출 프로세스**와 **판정 프로세스** 둘로 나누는 경로를 설정
스위치(기본 끔) 뒤에 만들고, 판정 중심 최적화(-726)와 함께 다음 라이브에서 A/B 로 재서 기본값을 정한다.

이 문서는 1차 MR 의 설계와 구현 범위, 그리고 기본값을 켜기 전에 끝내야 할 일(9절)을 적는다.

## 1. 고른 경계: 2D 관측(Observation2DFrame)

| 프로세스 | 하는 일 | 스레드 |
|---|---|---|
| 검출(자식, spawn) | I0 영상 포트(TLS 수신) 또는 녹화 메시지 수신 → 디코딩(PyAV/NVDEC) → 최신성 대기열(`I0Ingest`) → TensorRT 검출·포즈 → `ResultGate` → 카메라별 Local Tracker(`DetectorFeed.detect_once`, 지금 코드 그대로) → 관측 송신. GPU 선확보, 아바타 입력 공유 쓰기(그림이 여기 있다) | `i0-video-conn-*`, `tier0-detect`, `tier0-detect-status`, 명령 수신(주 스레드) |
| 판정(부모, 지금 Tier 0 프로세스) | 관측 수거 → 보간·ROI·교차 시점 삼각측량 → World Track → 접지 → 위험 판정·생명주기 → 저널·체크포인트 → I1·I0 제어 채널(시계 교환·현장 경보) → world_state·이벤트, health, 표시 파일, 보정 감시·후보 보정·카메라 확인 탭 | `tier0-judge`, `tier0-housekeeping`, `i1-*`, `event-journal-writer`, `tier0-checkpointer`, `tier0-detect-ipc`(관측 받기) |

경계를 지나는 자료는 `Observation2DFrame`(카메라 ID, stream_epoch, frame_sequence, 추정 촬영 시각·출처·불확실성, 로컬 트랙 ID·bbox·
17×3 keypoint) 묶음뿐이다. 5명 4대 한 묶음이 pickle 로 수 KB, 20 Hz 면 초당 100 KB 남짓이라 공유 메모리가 필요 없다. 원본 프레임
(2304×1296 BGR 4장 약 36 MB)은 넘기지 않는다.

### 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 영상 수신·디코딩만 분리 | 넘길 것이 디코딩된 프레임이라 25 fps × 4대 × 9 MB ≈ 0.9 GB/s 를 공유 메모리로 복사해야 하고, 정작 검출(49%)과 판정(48%)이 한 프로세스에 남아 GIL 대기가 그대로다(외부 검토 두 건 모두 같은 결론) |
| 판정(R1~R11)만 분리 | 교차 시점·World Track(판정 tick 의 대부분, 약 50 ms)이 검출과 같은 프로세스에 남는다. 효과가 작다 |
| 검출을 부모, 판정을 자식으로 | 저널·체크포인트·I1·I0 제어·표시 파일·bootstrap 감시(PID·종료 코드·재시작 규칙)가 모두 지금 Tier 0 프로세스에 묶여 있다. 판정을 자식으로 보내면 이것들을 전부 옮기거나 중계해야 하고, 판정이 죽었을 때 부모가 무엇을 해야 하는지(복구는 저널이 하는데 저널 소유자가 자식) 규칙이 복잡해진다 |
| 공유 메모리 링 버퍼로 관측 전달 | 관측은 작고 개수가 가변이다. 유계 `multiprocessing.Queue`(pickle)로 충분하고 고정 칸 크기·SIGBUS 함정(-563)이 없다 |
| 스레드 대신 asyncio·GIL 없는 Python | 판정 중심이 순수 Python 이라 같은 프로세스 안에서는 GIL 다툼이 없어지지 않는다. free-threaded 빌드는 torch·ultralytics·PyAV 휠이 없다 |

## 3. 경계 큐: 순서·역순·중복·지연·드롭

- 검출 → 판정: 유계 `multiprocessing.Queue`(256건). 검출 루프는 `put_nowait` 만 한다. 차면 그 묶음을 버리고 `ipc_dropped` 로 센다
  (판정 프로세스의 받기 스레드가 멈췄을 때 검출이 막히지 않게).
- 판정 쪽 받기 스레드(`tier0-detect-ipc`)는 묶음을 카메라별 유계 deque(깊이 = `detect_queue_depth`, 기본 8)에 넣는다. 지금
  `DetectorFeed` 의 카메라별 대기열과 같은 깊이·같은 정책(넘치면 가장 오래된 관측을 버리고 `dropped_observations`)이다.
  **카메라별 최신 1건만 남기지 않는다**: 판정 tick(10 Hz) 사이에 카메라당 2~3장이 오고, 보간은 공통 시각 t 앞뒤 관측이 모두 있어야
  한다(외삽 금지). 최신 1건만 두면 t 이후 관측만 남아 보간이 `NO_FRAME_BEFORE` 로 빠진다.
- 카메라별 촬영 시각이 직전에 받은 값보다 늘지 않은 관측(중복·역순)은 버리고 `out_of_order` 로 센다. 정상 경로에서는 검출 쪽
  `ResultGate` 가 이미 같은 규칙을 지켜 0 이다. 재시작한 검출 프로세스가 같은 시각을 다시 내도 판정에는 들어가지 않는다.
- 판정 루프는 지금처럼 tick 마다 쌓인 관측을 모두 꺼내 (촬영 시각, 카메라 순, frame_sequence) 로 정렬해 `LocalTrackletBuffer` 에
  넣는다. 늦게 도착한 카메라는 지금과 같은 시간 모델(`fusion_max_lag_ms` 150, `camera_stall_ms` 500, -219)이 다룬다. 경계 전달
  지연은 파이프 한 번(1 ms 미만)이라 이 문턱에 비해 작다.
- 판정 → 검출: 같은 유계 큐로 명령(영상 포트 열기·멈춤·아바타 요청·녹화 재생 메시지). 아바타 요청은 `put_nowait`(차면 버림·계수,
  최신성만 의미가 있다). 녹화 재생 메시지는 버리면 결과가 달라지므로 기다려 넣는다(제한 시간을 넘기면 재생 실패).

### 녹화 재생(file 입력)·같은 결과

file 입력은 lockstep 이다. 판정 스레드가 재생 시계를 옮기고 지난 I0 메시지를 명령 큐로 보낸 뒤(`RemoteIngest.receive`), 판정
tick 의 관측 수거(`SplitDetectorFeed.poll`)가 `step` 을 보내고 답을 기다린다. 검출 프로세스는 명령을 받은 순서대로 처리하므로 `step`
을 받을 때 디코더·대기열 상태가 단일 프로세스와 같고, 지금 판정 tick 과 같은 순서(`detect_once` → `poll`)로 관측을 만든다. 재생
시계는 판정 프로세스만 갖고, 명령마다 그때의 판정 시계 값(now_ms)을 실어 보내 검출 프로세스의 `I0Ingest` 가 그 값을 쓴다. 그래서
최대 속도 재생은 단일 프로세스와 같은 world_state·이벤트 전이를 낸다(시험 5절 a).

LIVE 는 비동기다. 검출 루프가 지금 `tier0-detect` 와 같은 주기(`detect_tick_ms` 50)로 돌며 묶음마다 관측을 보낸다.

## 4. 시계

- Tier 0 코드는 시계를 직접 읽지 않는다(ai/CONVENTION.md). 검출 프로세스의 시계는 진입점(`_detector_child_main`, 조립 지점)이
  만든다. LIVE 는 판정 프로세스의 기본값과 같은 OS 시계(`time.monotonic_ns`·`time.time_ns`)로 자기 `DecisionClock` 을 만든다. file
  입력은 판정 프로세스가 명령에 실어 보낸 판정 시계 값만 쓴다(`_MirrorClock`).
- 검출 프로세스의 시계는 최신성 정책(대기 상한·frame_age)에만 쓴다. **관측의 시각은 프레임 헤더의 추정 촬영 시각(노트북 시계,
  3.9) 그대로**이고, 판정 프로세스가 시계 교환(I0 제어 채널)으로 구한 시계 차이로 해소 확인을 한다(지금과 같다).
- 검출 프로세스의 시계 값을 판정에 쓰지 않는다. 받기 시각·하트비트 신선도는 판정 프로세스의 단조 시계로 잰다.

status 의 `process_split.disabled` 에 꺼진 곁가지를 싣는다. 그래서 다음 라이브 A/B 는 두 칸 모두 같은 곁가지를 끄고 잰다(8절).

## 6. 종료·재시작·재시작 복구

| 상황 | 동작 | 근거 |
|---|---|---|
| 기동 중 검출 프로세스 실패 | 자식이 지금과 같은 종료 코드 규칙으로 실패를 알리고(검출기·디코더·포트 열기 실패 4, 영상 포트 설정 오류 2) 판정 프로세스가 같은 코드로 `Tier0StartError` | bootstrap 규칙이 지금과 같게 작동(2 는 다시 띄우지 않음, 4 는 다시 띄움) |
| LIVE 중 검출 프로세스 죽음(종료 코드·신호)·응답 없음 | 그 순간부터 모든 카메라를 연결 아님으로 본다(health NO_SIGNAL, R7 입력). 이미 받은 관측은 실제 관측이라 그대로 쓰고, 새 관측은 지어내지 않는다(World Track 은 시간 모델대로 PREDICTED·OCCLUDED·소멸). 1초부터 두 배(최대 5초) 백오프로 새 세대를 띄운다. 새 세대의 로컬 트랙 ID 는 `-g<세대>` 를 붙여(`cam_A-t1-g1`) 옛 ID 와 겹치지 않는다(옛 World Track 에 다른 사람이 붙지 않게). 노트북 게이트웨이는 영상 연결이 끊긴 것을 보고 다시 붙는다 | 판정 상태·저널·I1 연결을 잃지 않는다. 전체 재시작(저널 복구, 활성 이벤트 UNVERIFIABLE)보다 피해가 작다 |
| 60초 안에 검출 프로세스가 3번 넘게 죽음 | 판정 프로세스가 표시 파일을 쓴 채 정상 종료 절차(저널 비우기·마지막 체크포인트)를 밟고 **종료 코드 4** 로 끝난다 | bootstrap 은 4 를 다시 띄운다(TIER0_NO_RESTART = 0·2·3·5 밖). 다시 띄운 Tier 0 는 지금과 같은 재시작 복구(-652, 저널·체크포인트)를 한다 |
| file 입력 중 검출 프로세스 죽음 | 다시 띄우지 않고 재생 실패로 끝낸다(종료 코드 4) | 재생은 결정론이 목적이다. 새 디코더는 다음 세그먼트 코덱 정보까지 디코딩하지 못해 결과가 달라진다 |
| 판정 프로세스 죽음 | 검출 프로세스는 1초마다 부모를 확인하고(`parent_process().is_alive()`) 부모가 없으면 끝난다. bootstrap 은 Tier 0 프로세스 그룹 전체를 SIGKILL 로 정리하므로(spawn 자식은 같은 그룹) 고아가 남지 않는다. 그다음은 지금과 같은 Tier 0 전체 재시작·재시작 복구 | 판정 정본이 없는 검출은 의미가 없다 |
| 정상 종료 | 영상 포트를 닫을 차례(지금 `i0_video` 단계)에 `stop` 을 보내고 자식을 기다린다(제한 시간 넘으면 kill, 실패 이름을 종료 실패 목록에 남김) | 지금 종료 순서와 같은 자리 |

## 7. CPU 고정(-662)과 포트

- bootstrap 이 Tier 0 를 앞쪽 코어(`SIMAI_TIER0_CPUS`)에 묶으면 spawn 자식도 그 묶음을 물려받는다. 그래서 기본은 두 프로세스가
  Tier 0 몫 코어를 함께 쓴다(OS 가 나눔).
- 새 설정 `detect_cpus`(환경 `SIMAI_TIER0_DETECT_CPUS`): `none`(기본, 물려받음) | `auto`(물려받은 묶음의 앞쪽 절반, 최소 1개) | 목록
  (`0-5`). 검출 프로세스만 그 코어로 좁힌다(Linux `sched_setaffinity`, 다른 OS 는 무시). 판정 프로세스는 바꾸지 않는다(이미 뜬
  스레드의 묶음을 바꾸는 것은 스레드마다 해야 해서 1차에서 하지 않는다). A/B 칸 B2 에서 잰다.
- I0 영상 포트(TLS 수신)는 검출 프로세스가 연다. I0 제어 채널(시계 교환·현장 경보·하트비트)은 판정 프로세스에 남는다(현장 경보
  송신 순서와 판정 lock 이 묶여 있다). 영상 포트를 다시 열 때는 기존 `SO_REUSEADDR` 로 바로 다시 묶는다.

## 11. 잔여 위험

- IPC 비용: 관측 pickle·받기 스레드의 GIL 은 판정 프로세스에 남는다(묶음당 0.1 ms 수준 추정, 라이브에서 `thread_cpu` 의 `tier0-detect-ipc` 로 확인).
- 두 프로세스의 CUDA 문맥: 판정 프로세스는 torch 를 불러오지 않는다. 다만 다른 곁가지(9절)를 옮길 때 판정 쪽에서 torch 를 불러오지 않는지 다시 본다.
- 검출 프로세스 재시작 동안 health 프레임 누계가 0 부터 다시 센다(증가분은 음수를 0 으로 둔다).
- 아바타 문서의 그림은 요청 받은 때의 최신 그림이라 단일 경로와 한두 묶음 다를 수 있다(판정 결과와 무관).
