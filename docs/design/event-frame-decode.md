# CRITICAL 이벤트 사진의 중복 디코딩 제거

S15P31A101-378. 관련 명세 §5.1·5.4·6.6·12.3, `event_frame_ready` 계약은 변경하지 않는다. 리뷰 생략(사용자 지시).

## 문제와 선택

9차 조사(`.agy/ref/findings-tier0-control-drops.md`)에서 이벤트마다 카메라별 키프레임부터 130~170개 패킷을 다시 디코딩해 2~3초가 걸렸다. JPEG·서명·PUT도 순차 실행했다. -377 조사(`tier0-perception-profile.md`)의 디코딩+JPEG 동시 부하는 합성 5명 CPU 융합 중앙값을 약 25.5% 늘렸다. 이 수치를 GIL 단독 원인이나 이번 변경의 LIVE 개선율로 해석하지 않는다.

| 대안 | 메모리·GIL/CPU | 지연·제약 | 결정 |
|---|---|---|---|
| (a) 추론 프레임 재사용 | 원본 BGR 참조를 제한 개수 보관. 판정에서는 짧은 Python 목록 작업만 수행. 복사·JPEG 없음 | 이벤트의 재디코딩 0회. 수신/추론에서 이미 버린 프레임은 복구하지 않음 | 선택 |
| (b) 별도 프로세스 디코딩 | Python GIL은 분리하나 H.264 CPU 비용은 유지. 프로세스별 디코더 메모리, 패킷 전송/IPC·종료 관리 필요 | 130~170패킷 의존 디코딩·2~3초 자체가 없어지지 않음 | 제외 |
| (c) 키프레임 간격·탐색 | 카메라 GOP 설정 변경 필요. 참조 P/B 프레임은 임의로 건너뛸 수 없음 | 짧은 GOP는 압축률·I0 대역폭에 영향. 키프레임 그림만 쓰면 0~500ms 현재 창을 보장할 수 없음 | 제외 |

별도 디코딩은 완전히 제거한다. JPEG/native OpenCV와 HTTPS I/O는 최대 4개 스레드에서 실행한다. 네트워크 대기 중 겹칠 수 있지만 JPEG의 native CPU 경합이 완전히 없어지는 것은 아니며, LIVE 판정 p95 개선은 후속 실측 대상이다.

## 경로와 상한

`DetectorFeed.poll`의 기존 `observe_decoded`를 연결한다. 디코더 FrameKey와 검출 결과가 일치하고 최신성 게이트를 통과한 입력만 받는다. 기존 배경 수집도 그대로 호출하며 한 콜백의 실패가 다른 콜백의 호출을 막지 않는다. 이미지를 수정하지 않는 배경·아바타 경로의 기존 소유권 규칙을 따른다.

- 카메라별 과거 표본: 최소 1,000ms 간격, 최근 5,000ms, 최대 6장. 3~5초 창의 최근 표본을 택한다. 과거 시각 선택은 기존 전 프레임 검색보다 최대 약 1초 성기다.
- 현재 표본: 최근 500ms, 최대 6장. 10Hz 판정 입력에서 빠른 카메라의 최신 그림이 융합 시각보다 미래인 경우에도 그 이전 그림을 선택한다. 더 빠른 호출에서는 개수 상한을 우선한다.
- 새 epoch면 해당 카메라 링을 비우며 역행 epoch·중복/역행 시각·알 수 없는 카메라·10MiB 초과/빈 이미지는 받지 않는다. 재연결 epoch가 같으면 기존 촬영 시각 창으로만 판단한다.
- `on_transitions`는 대상 관측 카메라 순서로, 사용 가능한 최대 2대×2시점 이미지 참조를 불변 요청으로 고정한다. 미래·너무 오래된 그림은 대체하지 않는다. 큐에서 기다려도 링 갱신과 섞이지 않는다.
- 요청 큐는 기존 8개, 소비자는 1개, JPEG·서명·PUT 풀은 최대 4개다. 풀 대기 작업도 이벤트당 최대 4개로 제한한다. 서로 다른 카메라·두 시점 모두 병렬 처리하고 결과 목록은 선택 순서를 유지한다.
- 판정 lock 안에서는 참조 보관·선택·`put_nowait`만 한다. JPEG·SHA256·계약 검증·서명·PUT·I1 재시도는 판정 lock 밖이다. 사진 경로는 새 디코더를 만들지 않는다.
- 큐 포화·사진별 실패·사진 없음·종료 전 I1 전달 실패 로그와 I1 큐 포화 재시도를 유지한다. I1 재시도 중 객체를 다시 업로드하지 않는다. 업로드 일부 실패 시 성공한 사진만 보내며, 제3 카메라를 추가 선택하지 않는다.
- 종료 시 대기 요청·링 참조를 해제한다. 실행 중인 PUT을 강제 취소하지 않고 종료 시간 초과는 `False`로 보고한다. HTTP 서명/PUT의 기존 2초 timeout은 유지한다(네트워크의 절대 총 실행 시간 보장은 아님).

**BGR 보관 상한**: 카메라 C개, 요청 큐 Q개이면 `(12C + 4(Q+1)) × 10MiB` 이하. 4대/Q=8이면 840MiB다. 2304×1296 BGR 한 장은 8,957,952바이트(8.543MiB)이므로 같은 계산은 약 718MiB다. 링 단독은 약 410MiB이며 이력/현재/요청 사이 중복 참조는 실제로 추가 할당하지 않는다. 이는 보수적인 이미지 보관 상한이고 전체 프로세스 RSS 상한이 아니다. JPEG 인코더 native 작업 공간·동시 JPEG 최대 4개·기존 추론/클립 버퍼·Python 객체 비용은 별도다. 4K 등 10MiB 초과 입력은 사진 캐시에서 거부한다. 작은 합성 배열로 상한과 참조 동일성을 시험했으며 LIVE RSS는 측정하지 않았다.

## 사진 크기와 VLM

원본 해상도와 기존 JPEG 품질 85를 유지한다. VLM 클라이언트(`ai/src/simai_ai/vlm/client.py`)는 모델에 보내기 전 폭을 1280 이하로 줄이고 품질 90으로 인코딩하지만, 그 전에 워커가 원본 사진에서 pose 기반 얼굴 영역을 검출·흐림 처리한다(§5.4). Tier 0에서 미리 줄이면 원거리 사람의 얼굴 점 검출에 영향을 줄 수 있다. 이번 이슈에서는 입력을 줄이지 않고 재디코딩 제거와 업로드 병렬화로 개선한다. 얼굴 정책·외부 LLM 텍스트 전용·I1 스키마는 그대로다.

## 검증과 남은 일

`ai/tests/services/tier0/test_event_frames.py`에서 합성 H.264를 기존 PyAV 디코더로 한 번 디코딩해 입력 캐시를 만든다. 실제 I1 신뢰 큐·스키마·JPEG 그림 번호와 촬영 메타데이터 결합, LIVE/CRITICAL/최초 RAISED 조건, 큐 포화에도 판정 반환, I1 재시도·부분 실패·종료·캐시 상한·epoch 전환·미래 프레임 제외·배경 콜백 공존을 검증한다.

느린 PUT 150ms×4 시험은 변경 전 동시성 1로 실패했다. 변경 후 동시성 4, 이벤트 제출부터 준비 통지까지 171ms로 통과했다(PUT만 순차 실행하면 600ms). 같은 시험에서 PyAV `decode`/`flush`를 실패하도록 바꿔 이벤트 경로의 추가 디코딩이 없음을 확인한다. 상한은 합성 시험 500ms이며 인터넷·GPU·실제 2304×1296 JPEG CPU 비용을 측정한 수치가 아니다.

남은 위험은 원본 BGR 상주 메모리, 업로드 4개의 순간 CPU/네트워크 경합, 추론이 멎으면 현재 사진을 제공하지 못함, 실패한 두 카메라를 제3 카메라로 대체하지 않음이다. 실제 시연 GPU에서 이벤트→사진→VLM 완료 지연·판정 p95·RSS를 함께 재측정해야 한다. S3 리전/다운로드 지연과 워커의 사진 순차 다운로드는 이번 범위 밖이며 G7 5초 달성은 아직 보장하지 않는다.
