4 프로세스로 약 38분(1회), 재생은 실험 하나에 CPU 약 4분이다.

**녹화 재생의 한계.** 녹화 헤더의 촬영 시각·수신 시각을 그대로 쓰므로 실시간의 도착 흔들림·중계 지연·카메라별 시계
차이 변동이 없다. 늦은 카메라 제외는 녹화 전체에서 0.2% 이하였다. 그래서 T* 실험(보간 불확실도·늦은 카메라 문턱)의 효과는
작게 나오는 것이 당연하고, 실시간의 시각 정렬 문제를 여기서 판정할 수 없다(대신 촬영 시각을 일부러 옮긴 T3~T5 와 카메라 하나를
늦게 도착시킨 T6 으로 민감도만 본다).

입력: `rec-20261029-015512z-lobby-railing-pose`(4대, 약 9분), 보정 `cal-fastrot-20261030-011907-266z`(10차 시작 보정, 9차
relay 재생 위 실행 중 보정으로 나온 회전만 다시 맞춘 보정). 이 녹화는 **1인 구간이 없다**: 검출 수로 세면 5~415 s 내내 2인,

## 3. 재현과 기준선

녹화 재생(정확한 헤더 시각)으로도 폭증이 재현된다: **9분에 ID 149개(16.6/분, 시간당 약 1,000)**, 2인 구간 새 ID 8.7/사람·분,
Track 수가 사람 수와 맞는 tick 62%(많음 23%, 적음 15%), 구역 근사 중복 18(진입 ID 28 / 점유 10). 수명 중앙값 2.2 s, 75% 가
6 s 미만. 9차와 같은 규모다.

계측이 보여 준 기전(기존 분석의 분기·분포 해석이며, 아래 실험 표는 `final/summary.md` 기준):

- 분기 계측의 `reconnect_skip.holder_updated_now` 는 새 Track 이 될 수 있는 클러스터의 로컬 트랙 주인이 **같은 시각에 이미
  위치를 갱신한 Track** 임을 뜻한다. 즉 한 사람이 카메라 2+2(또는 3+1, 1대 클러스터는 기준점이 없어 Track 을 못 만든다)로 갈라져
  남은 쪽이 새 ID 가 된다. 그 뒤 46개는 TENTATIVE 로 죽고, 61개는 병합(ID 교정)으로 사라진다(병합도 R1 새 이벤트·키 갈이를 부른다).
- 클러스터 `IDENTITY_UNCERTAIN` 사유 중 `MARGINAL_RESIDUAL` 이 많다(쌍 잔차 8~12 px 이면 병합을 막는다).
  쌍 잔차 중앙값이 카메라 C 가 든 쌍에서 크고(B/C·C/D 의 최빈 구간 6~10 px), B/C·C/D 쌍은 에피폴라 거부가 통과의 2~4배다.
  당시 한쪽 카메라 view 기준 최근접 상대 에피폴라 거리도 B/C·C/D 에서 20~50 px 에 큰 덩어리가 있다 → 이 보정(266z)의 카메라 C 쪽 기하가 약하다.
- **카메라를 하나만 빼도(어느 것이든) ID 가 149 → 18~29 로 준다**(X_no*). 3대로는 2+2 분할이 생기지 않기 때문이다.
  나쁜 카메라 하나가 원인이 아니라 4대 기하가 조금씩 어긋나 완전 연결이 갈라지는 것이 원인이다.
- 같은 녹화 1단계 걷기로 만든 회차 보정(699z, 459z)으로 바꾸면 149 → 71~77, 4대 융합 12% → 45~56%, 사람 수 일치 62% → 87~90%.
  266z 는 9차 relay 재생(아래 4절: 카메라 사이 내용 시각이 최대 약 440 ms 어긋남) 위에서 실행 중 보정이 회전만 다시 맞춘 것이라
  시각 오차를 보정이 떠안았을 가능성이 크다.
- 시각 정렬 문턱(T1 불확실도 50 ms, T2 늦은 카메라 300 ms)은 재생에서 효과가 없다(위 한계). 보간 탈락은 `TIMESTAMP_UNCERTAIN`
  이 카메라당 150~190(녹화의 불확실도 45 ms 프레임 약 1%) 수준이다.

## 5. 해석

1. **가장 효과가 큰 것은 보정 품질과 "분할 나머지로 새 ID 를 만들지 않기"다.** 보정 교체(K3·K4)는 ID 를 절반으로, 분할
   나머지 억제(S3)는 1/5 로, 둘을 합치면(S5·S11) 9분 12~13개(2인 구간 새 ID 0.22~0.44/사람·분, 사람 수 일치 92.7~93.7%, 많음 0~0.2%)로
   줄인다. 여기에는 3번째 사람의 출입과 녹화 끝 퇴장이 포함된다.
2. **Cross-view 문턱 완화는 ID 를 줄이지 않는다.** 잔차 경계 8 → 12 px(C1)·10 px(C5)는 4대 융합을 12% → 26~32% 로 늘리지만
   ID 는 오히려 늘었다(149 → 167~180). 큰 클러스터가 시각마다 다르게 묶여 기준점이 흔들리고 나머지 분할이 여전히 새 ID 가
   되기 때문이다. 에피폴라 20 → 30 px(C3)만 149 → 115 로 줄였다. 애매함 여유(C4) 영향 없음.
3. **생명주기 완화는 보조 효과다.** TENTATIVE 공백 300 → 1000 ms(W1) 134, 확정 3 → 2회(W2) 131, 게이트 상한 1.5 → 2.5 m(W3)
   127, 셋을 함께(M1) 112, 에피폴라 30 과 함께(M2) 94. 원인(분할)을 없애지 않고 짧은 ID 를 줄일 뿐이다.
4. **2D 추적 문턱(L1·L2)은 영향이 없다.** 로컬 ID 는 카메라당 40~56개 발급되지만 World 연결은 3D 위치 게이트가 주도한다.
5. **촬영 시각 오차 민감도(T3~T5).** 카메라 B 를 50·100·200 ms 옮기면 4대 융합이 12% → 11·8·5% 로, swap 이 211 → 231·246·288
   로 나빠지지만 ID 수는 155~167 로 크게 늘지 않는다(분할 나머지 억제를 켠 S12 에서도 100 ms 이동은 32 → 38). 이 녹화·보정에서는
   시각 오차보다 기하(보정)가 먼저다.
6. **부작용.** 분할 억제(S3)는 2인 구간에서 사람 수보다 적은 tick 비율을 늘리지 않았고(15.2% → 11.8%), 3인 구간도 같았다
   (35% → 34%). 기준선과 S3의 bad bone 은 약 1.1%로 비슷하다(두 사람 합침 신호 없음). 다만 정답(사람별 GT)이 없는 근사 지표다.

## 6. 실시간(10차)에만 있는 문제에 대한 판단

- 10차 상태 파일(`state/tier0.live`, `calibration.live_candidate.last_comparison.holdout`)에서 **쌍 통과율이 A/D 0.87, 나머지 쌍
  모두 0.0, 카메라 B·C 의 재투영 관측 0개**였다. 같은 시각 4대 모두 카메라당 약 11.9 fps 로 추론됐다(`live_input.cameras.*.inferred`).

  → **실시간 "동시 관측 2대 상한"은 시각 정렬(25 ms·150 ms 문턱)보다 B·C 의 보정이 11/02 실제 자세와 맞지 않는 것(거치대
  이동·회전)이 가장 유력하다.** 다른 가능성은 B·C 프레임의 불확실도가 25 ms 를 넘어 보간에서 전부 빠지는 경우(PTS 없음 45 ms)다.

  오히려 ID 가 준다(3대에서는 2+2 분할이 없다). 늦은 카메라 제외가 ID 폭증의 원인일 가능성은 낮다.
- **9차의 "녹화로도 폭증 재현"은 relay 파일 재생의 시각 정렬이 섞인 값이다.** relay 파일 모드는 카메라마다 프레임을 25 fps
  로 일정하게 내보내고 그 송신 시각을 촬영 시각으로 쓴다(`relay-file-capture-time.md`). 녹화의 실제 촬영 간격과의 차이가
  카메라마다 달라 첫 회전 안에서도 카메라 사이 내용 시각이 25% 지점 약 50 ms, 50% 지점 약 200 ms, 끝 약 440 ms 어긋나고(카메라
  A −554 ms 대 B −991 ms), `loop = true` 로 돌면 프레임 수 차이(13,478~13,488)만큼 더 벌어진다. 이 재생 위에서 만든 266z 도 영향을
  받았을 수 있다. 녹화 재생은 이 도구처럼 헤더 시각으로 해야 한다.

## 9. 분할 억제 운영 반영과 비교 준비 (S15P31A101-458)

사용자 결정 **2026-11-04**: 분할 나머지 억제는 운영에 넣고, 더 정확한 조합은 실험으로 고른다. 관련 명세는 §5.2이며
§6.1 관측 상태와 R1 확실한 진입 조건은 그대로다. **현재 실험을 실행하지 않았으며 아래는 구현·실행 계획이다.**

### 구현과 수치

- `tracking/world_track.py`: 새 ID 발급 직전에 같은 시각 실제 골반 측정이 있는 Track 과 확실한 나머지 클러스터를 비교한다.
  수평 거리 **0.6 m 이하**, 카메라 비중복이면 발급을 억제하고 기존 Track 에 `CROSS_VIEW_UNCERTAIN`을 남긴다.
  **후보 로컬 키 하나 이상이 최근 그 Track 에 속했던 나머지에만 적용한다.** 첫 등장한 주인 없는 묶음은 새 ID 를 만든다.
  소유 이력은 tick 시작 때 고정하므로 같은 tick 의 새 ID 발급·키 이동·1대 검출 이력 갱신으로 조건을 만들지 않는다.
  `split_suppression_owner_ttl_ms=1000`(경계 포함)은 별도 설정이며 일반 `key_ttl_ms=2000`이나 늦은 재연결 창과 다르다.
  키 보관 기간은 이 설정도 포함한 최댓값으로 잡으므로 10초보다 긴 비교 창도 검사 전에 이력이 지워지지 않는다.
  측정·관절·로컬 트랙 소유권은 기존 Track 에 더하지 않는다. 카메라 중복·반경 밖·예측 위치뿐인 Track 은 억제 근거가 아니다.
  반경 근거는 -413 S3 및 S6·S7 민감도이며 1초는 3차 지시의 초기 후보값으로 아직 실측 선택하지 않았다.
  운영 기본은 `split_suppression_enabled=true`, `split_suppression_radius_m=0.6`, `split_suppress_ownerless=false`다.
  true 는 최근 소유 이력 조건을 생략하는 1차 동작 비교용이며 반증 예외는 유지한다.
  `split_suppression_require_owner=false`는 별개로 유지한다. true 는 -413 S1·S2의 모든 옛 주인 일치 제약이다.
  `plan_413.json`은 `split_suppress_ownerless=true`를 명시하여 기존 S* 비교 의미를 보존한다. 등록 횟수 `confirm_hits=3` 유지.
  **반증 예외:** 후보의 옛 로컬 트랙 주인과 억제 근거 Track 이 기존 `_distinct` 쌍이면 억제하지 않는다.
  병합 시 `_distinct`의 사라진 ID 를 남는 ID 로 바꾸는 기존 상속 규칙을 그대로 사용한다. 이번 tick 같은 카메라의
  서로 다른 두 검출도 억제 반증이다. 억제 근거 Track 의 실제 갱신 클러스터뿐 아니라 그 Track 의 옛 로컬 키로
  이번 tick 에 보인 1대 클러스터까지 확인한다(위치 갱신 없이도 반증). 반증이 있는 Track 을 억제 근거에서 뺀다.
- 짧은 재연결은 기존 **`lost_after_ms`**·1:1 배정·거리 게이트를 재사용한다. 같은 기능의 초 단위 별도 설정은 만들지 않았다.
  현행 **3000 ms**를 기준으로 **1000·2000 ms** 후보를 비교한다. 3초 동안도 이미 기존 ID 를 유지하므로 별도 위치 추정을
  더할 이유가 없다. 빈 tick 없이 입력이 다시 와도 마지막 유효 측정 시각으로 만료를 적용하도록 비용 게이트를 보완했다.
  짧은 창 이후에는 위치만으로 이어 붙이지 않고 기존 2대 옛 로컬 이력 기반 늦은 재연결을 쓴다(`reconnect_window_ms=10000`).
  `tentative_max_gap_ms=300`, `gate_max_m=1.5`도 재사용하며 W1·W3 완화를 기본값으로 넣지 않았다.

  따라서 ID 는 OCCLUDED 로 유지하되 관측 상태는 200 ms까지 OBSERVED, 500 ms까지 PREDICTED, 이후 UNKNOWN 이다.

  창 기본값의 1초/2초 선택은 Lead 실행 결과를 보고 하는 후속 결정이다.
- `tracking/cross_view.py`: 에피폴라 문턱 **20 → 30 px**(-413 C3·S8). 잔차 경계 8 px·잔차 게이트·완전 연결은 유지한다.
- `experiments/track_replay/replay_tracking.py`는 운영 Manager만 쓴다. 기존 실험 전용 subclass·관절을 비워 발급을 막는 우회는
  제거했다. `plan_413.json`도 같은 운영 설정으로 옮기고 기준선의 억제 OFF·에피폴라 20을 명시했다.

## 버린 대안

- **relay `--send` 로 녹화를 다시 실시간 재생해 실험.** 카메라 사이 내용 시각이 수백 ms 어긋나(6절) 원인을 섞는다. 검출도 매번 다시 해야 한다.
- **`services.tier0` 파일 입력(-215)으로 실험마다 전체 재생.** 디코딩·검출을 매번 해야 하고 최대 속도에서는 판정 tick 마다 카메라당
  한 장(10 Hz)만 써 실시간 검출 주기(약 12 fps)와 다르다. 캐시 + 운영 Perception 조립을 택했다.
- **오프라인 전용 추적·삼각측량 구현.** CONVENTION("오프라인용 삼각측량·추적을 따로 만들지 않는다") 위반이고 운영과 결과가 달라진다.
- **분할 억제를 운영 코드에 꺼진 설정으로 넣기.** 명세 결정 전이라 실험 코드(`SplitSuppressingManager`)로만 두었다.
