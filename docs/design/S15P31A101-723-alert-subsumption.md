# S15P31A101-723 같은 사람 동시 경보는 하나로 울리고, VLM 근거는 같은 사건에 한 번

17차 GPU 세션(2026-11-15) 작업 4분에 실제 2~3명인데 R2(CRITICAL) 27건·R3(HIGH) 27건·R5(CAUTION) 21건이 열렸고(전체 96건),
VLM 근거 작업도 R2 27건 나갔다. 원인 분석은 `S15P31A101-716-world-id-churn.md` 에 있다: R2 27건은 **World ID 25개**에 걸쳐 있고,
27/27 이 발생 때 `Z_UNKNOWN`, 21/27 이 `PREDICTED`, 20/27 이 `SINGLE_VIEW` 였다. ID 갈라짐 자체는 -716 이 보고, 이 티켓은 Tier 0 추적·판정
코드를 건드리지 않는다.

관련 명세: 3.10(현장 경보: 소리는 확인까지 반복), 7.1(불확실성 처리·확인 필요), 7.2(R2·R3 접지 모름 정책), 7.3(채널 정본, "등급별로 소리 패턴과
중복 억제는 달리할 수 있지만 보내는 채널은 이 표로만 정한다"), 7.4(이벤트 병합: 한 사람에게 걸린 여러 규칙은 화면에서 한 묶음, VLM 은
CRITICAL 병합 이벤트당 1회), 5.4(VLM 빠른 경로·권한), 부록 C.6(워치). AGENTS 규칙 1·4·5·6.

## 1. 같은 사람 동시 경보 — 명세 대조

**허용된다.** 7.3 이 채널별 중복 억제를 명시적으로 허용하고(보내는 채널은 그대로), 7.4 가 한 사람의 여러 규칙을 한 묶음으로 보이라고 한다.
이벤트 기록(Tier 0 정본, 추가만)·등급·확인 대상은 바꾸지 않는다. 경보를 끄는 것이 아니라 같은 사람에게 이미 울리는 같거나 높은 등급이
있을 때 하위의 **소리·진동만** 하나로 모은다. 3.10 의 "소리는 확인까지 반복"은 이미 -497(사용자 결정 2026-11-05)의 Tier 0 `sound_mode`
결정으로 하위 경보를 SILENT 로 보내는 것과 같은 범위다(새 차이 없음).

### 채널별 현재 상태와 이번 변경

| 채널 | 이전 | 이번 |
|---|---|---|
| 노트북 현장 소리 (Tier 0 `SoundLadder`, -497) | 같은 World ID 에 열린 같거나 높은 등급이 있으면 하위를 `SILENT`. 노트북은 울리는 경보 중 최상위 패턴 하나만 낸다 | 바꾸지 않음(Tier 0 판정 코드 범위 밖) |
| 노트북 현장 화면 (`gateway/site_alert/display.py`) | 경보마다 한 줄, `SILENT` 인데도 "소리 반복 중" 으로 표시 | 같은 사람(world_id 겹침) 하위 경보를 최상위 아래 "└ 같은 사람" 줄로 묶음. `SILENT`·`ONCE` 문구를 실제 소리대로 |
| 관제 화면 소리 (`front/.../alarmPolicy.ts`) | Tier 0 와 같은 규칙(같은 사람 상위가 울리면 하위 무음) | 바꾸지 않음 |
| 워치 진동 (`WatchAlertService`) | 이벤트마다 진동. R2+R3+R5 가 한 사람에게 열리면 세 번 | 같은 워치에 **아직 열린** 다른 이벤트로 같거나 높은 등급 진동을 보냈고 지우지 않았으면 넣지 않음. 위 이벤트가 해소되면(지움 통지 직후) `resync` 로 남은 열린 이벤트 중 최상위를 보냄. `resync` 순서를 등급 높은 것부터로 |
| Web Push (`NotificationQueue`) | 넣는 쪽(생산자)이 없다. 반장 PWA·Web Push 폐기(10.1) | 바꾸지 않음(죽은 경로) |

묶음 기준은 **같은 사람(World ID 겹침)** 이고 구역은 보지 않는다. Tier 0 `SoundLadder`·관제 `alarmPolicy` 가 이미 같은 사람·구역 무관으로
활성 상위가 하위를 누르므로 세 채널을 같은 규칙으로 맞췄다(구역까지 같아야 묶으면 R2·R3 는 구역이 없고 R1·R5 는 구역이 있어 한 사람의
R1+R2 가 따로 울린다). "짧은 창"은 상위 이벤트가 **열려 있는 동안**으로 정했다(새 수치 없음).

워치 상세:
- 묶는 쪽은 `origin = EVENT` 알림만이다. 수동 알림(`MANUAL`, -475)은 묶지도 묶이지도 않는다.
- 보내지 못한 알림(`SEND_FAILED`), 지운 알림(`cleared_at`), 해소됐거나 재개 전 회차(`resume_count` 다름)·감사 전용 이벤트의 알림은 묶는 쪽이 될 수 없다.
- 상향은 묶이지 않는다: 하위가 CRITICAL 로 오르면 다른 열린 알림이 HIGH 이하이므로 바로 울린다.
- 격상(NO_ACK)은 실제로 보낸 알림만 대상이라 묶인 하위는 격상하지 않는다. 상위 알림의 격상은 그대로다.

### 17차에는 얼마나 듣나 (한계)

R2 27건이 World ID 25개라 같은 사람 묶음으로는 거의 줄지 않는다(같은 ID 의 R2+R3 짝만 이미 Tier 0 가 하나로 울렸다). 현장 소리는 원래
패턴 하나라 소리 겹침은 없었고, 실제 부담은 **확인해야 할 경보 줄 수**다. 이 줄 수를 ID 를 넘어 줄이려면(예: 같은 구역·같은 규칙이면 짧은
창 안에서 다른 ID 라도 묶음) 진짜 두 번째 사람의 경보를 확인 없이 무음으로 둘 수 있어 3.10 "소리는 확인까지 반복"과 부딪힌다. 코드로
하지 않고 Lead 결정 요청으로 남긴다(아래 결정 요청 1).

## 2. VLM 근거 작업 상한

`VlmRationaleIngestor` 가 작업을 등록하기 전에, 같은 Tier 0·같은 구역(구역 없는 R2·R3 는 '구역 없음'끼리) 안에서

- 같은 사람(World ID 겹침, 규칙 무관) **또는** 같은 규칙(ID 무관)인 이벤트의
- 근거 작업이 대기·대여·성공(`QUEUED`·`LEASED`·`SUCCEEDED`) 상태로
- 관측 시각 ±30 s 안에 있으면

새로 요청하지 않는다(`DUPLICATE`, INFO 로그에 앞선 이벤트 ID). 앞 작업이 실패·시간 초과·취소면 다음 이벤트가 다시 요청한다. 서로 다른
이벤트 통지가 동시에 와도 한 번만 요청하도록 Tier 0 별 트랜잭션 권고 잠금(`simai.vlm_rationale:<gateway>`)을 잡는다(기존
`CalibrationService`·`MediaClipIngestor` 와 같은 방식).

- **30 s 근거**: 명세에 없는 값. 17차 R2 의 흡수 마감(`IDENTITY_MERGED`)이 발생 뒤 최대 10.29 s(중앙 3.5 s), 재개 창이 10 s(6.4), 현장
  확인 뒤 같은 사람 소리 억제가 30 s(-497 `ACK_QUIET_MS`)라 같은 사건의 ID 재발생을 덮는 가장 짧은 기존 값을 썼다. 17차 R2 27건(221 s)은
  이 규칙이면 구역 없는 R2 끼리 30 s 마다 1건 이하, 최대 8건이다. 상수 `SAME_INCIDENT_WINDOW_MS`.
- **같은 규칙(ID 무관)도 묶는 이유**: 같은 사람만 묶으면 ID 25개에 걸친 17차는 27 → 약 25 로 거의 줄지 않는다. 근거는 설명뿐이고(5.4 권한:
  설명·상향 의견만) 등급·경보·이벤트 기록은 그대로라, ID 를 넘어 묶어도 안전 판단에 영향이 없다(AGENTS 4).
- **참조**: 생략한 이벤트에 앞선 근거를 이어 붙이는 것은 하지 않았다. `risk_event.rationale` 은 그 이벤트 VLM 결과의 투영이라 다른 이벤트
  문장을 넣으면 G7 측정·감사가 섞이고, 별도 연결 칸은 마이그레이션이 필요하다(넘긴 일 2).

**명세와 다른 점(명세 정리 때 반영 필요)**: 5.4·7.4 "CRITICAL 병합 이벤트당 1회"에 "같은 Tier 0·같은 구역에서 같은 사람 또는 같은 규칙의
근거가 관측 30 s 안에 이미 요청됐으면 생략(앞 작업 실패 시 다시 요청)"을 더한다.

## 3. 접지 모름 + 예측 위치만으로 R2·R3 새 발생 (코드 변경 없음, 7.1·7.2 변경 사안)

17차 수치: R2 27건 모두 발생 때 `Z_UNKNOWN`, 그중 21건 `PREDICTED`, 20건 `SINGLE_VIEW`. R3 는 R2 와 같은 시각·같은 ID 로 함께 열렸다.
높이차 0.40 m 교실 작업면. 7.2 접지 모름 정책은 "불확실성 범위가 작업면에 조금이라도 걸치면 그 위에 있을 수 있다"로 판정하고, 7.1 은
R2~R5 발생을 범위가 조금이라도 걸리면 내도록 한다. 그래서 접지가 안 나오는 새 ID 가 단상 근처를 지날 때마다 R2+R3 가 났다.

| 선택지 | 내용 | 17차 효과(추정) | 위험 |
|---|---|---|---|
| A. 그대로 | 현행 7.1·7.2 | 0 | 오경보 지속, 확인 피로 |
| B. 새 발생에 '관측 위치' 요구 | R2·R3 신규 발생은 `PREDICTED` 가 아닐 때만(유지·해소는 현행). R1 신규 발생이 11차에 '확실한 위치'만으로 바뀐 것과 같은 방향 | 발생 순간 기준 최대 21/27 차단(지속 조건 중 관측 프레임이 오면 늦게 날 수 있음) | 가려진 채 가장자리로 가는 실제 위험을 관측이 돌아올 때까지 늦게 냄 |
| C. 새 발생에 `Z_UNKNOWN` 과 `PREDICTED` 동시면 막음 | B 보다 좁게, 둘 다일 때만 | 최대 21/27 | B 와 같으나 접지는 모르는데 위치는 관측인 경우는 그대로 남음(6건) |
| D. CONFIRMED 트랙에서만 발생 | -716 제안 2(R5 처럼) | 흡수된 11건 일부 | 5.2 생명주기·위험 판단 분리 원칙 변경 |
| E. 낮은 신뢰 발생은 CAUTION 으로 | `Z_UNKNOWN`+`PREDICTED` 면 등급 낮춤 | 소리·진동 0(화면 안내) | 7.3 "신뢰도가 낮아도 등급은 내려가지 않는다"와 정면 충돌 |
| F. 낮은 신뢰 발생의 지속 조건 연장 | 예: 3프레임 중 2 → 1 s 연속 | ID 갈라짐이 짧은 경우만 | 수치 근거 없음, 지연 증가 |

추천은 C(가장 좁고 R1 선례와 같은 방향, "모르면 비운다"와 정합)이고 다음은 B 다. 둘 다 안전 규칙 발생 조건 변경이라 Lead 결정과 명세
7.1·7.2 개정이 먼저다. -716 의 재생 입력 시각 어긋남(188~342 ms)이 접지를 거의 못 내게 한 주원인이라, 라이브 RTSP 로 다시 잰 뒤 정하는
것도 방법이다.

## Lead 결정 요청

1. **ID 를 넘는 현장 경보 묶음**: 같은 구역·같은 규칙이면 짧은 창(예: 10 s) 안 다른 World ID 의 새 경보도 소리·진동을 묶을지. 현장 소리는
   어차피 패턴 하나라 이득은 '확인할 줄 수'다. 진짜 두 번째 사람의 경보가 확인 없이 무음이 될 수 있어 3.10 과 부딪힌다. 이번에는 하지 않았다.
2. **R2·R3 낮은 신뢰 새 발생**: 위 3절 선택지(추천 C).
3. **명세 정리**: 2절의 5.4·7.4 문장 추가, 1절의 워치 묶음을 부록 C.6 에 한 줄(같은 사람 열린 상위 진동이 있으면 하위는 진동하지 않고, 상위
   해소 뒤 남은 최상위를 보낸다).

## 버린 대안

- **노트북이 스스로 하위 소리를 끔**: 소리 결정은 Tier 0 `sound_mode` 하나로 정해져 있다(-497). 노트북이 따로 판단하면 Tier 0·관제와 어긋난다.
- **Web Push 대기열(`NotificationQueue`)에 묶음 추가**: 생산자가 없는 폐기 경로라 고쳐도 효과가 없다.
- **VLM 을 같은 사람만 묶음**: 17차(ID 25개)에 거의 효과가 없다.
- **생략한 이벤트에 앞선 근거 문장 복사**: 위 2절 '참조'.

## 잔여 위험

1. 같은 구역·같은 규칙에서 30 s 안에 진짜 다른 사람의 CRITICAL 이 나면 그 이벤트는 VLM 근거가 없다(경보·등급은 그대로). R2·R3 는 구역이
   없어 현장 전체가 한 묶음이다.
2. 워치: 상위 이벤트가 열린 채 오래 남으면(관측 없음으로 해소 안 됨, 6.4) 같은 사람의 새 하위 이벤트는 그동안 진동하지 않는다. 상위 진동은
   이미 받았고 하위가 상향되면 울린다.
3. 노트북 화면 묶음은 world_id 를 아는 경보만이다. 재동기화 목록으로만 안 경보(놓친 `local_alert`)는 world_id 가 없어 따로 보인다.
