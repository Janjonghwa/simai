# S15P31A101-769 PPE: ID 불확실한 사람의 local ID 차지는 다툼으로 둔다

관련 명세: 5.5 상태 전환(World ID 대응 변경 때 초기화). 선행: -653(ID 불확실 칸 건너뛰기·3초 초과 초기화), -661(순수 병합 승계), -766(칸 결합, ppe-policy-0.7.0).
명세 반영: 같은 MR 에서 5.5 상태 전환 문구와 개정 이력(v1.3 수정 83)을 고친다. 계약 변경 없음.

## 바꾼 것

`ai/src/simai_ai/ppe/state.py` `PpeJudge._claim`(새 메서드): local ID 주인 판정을 이곳으로 옮기고 다툼(contested)을 더했다.

| 상황 | 0.7.0 까지 | 0.8.0 |
|---|---|---|
| ID 불확실한 사람이 2초 안에 다른 ID 가 쓰던 local ID 를 가져감 | 두 ID 초기화, 주인 기록을 가져간 쪽으로 | 아무도 초기화하지 않고 다툼으로 기록. 주인 기록은 원래 주인 그대로 |
| 원래 주인이 그 local ID 를 되찾음 | (가져간 쪽에서 다시 주인 변경 → 또 초기화) | 다툼만 지움 |
| 가져간 ID 가 원래 주인에게 순수 병합됨 | 원래 주인은 이미 초기화돼 있음 | 다툼만 지움 |
| 가져간 ID 가 쥔 채로 확실해짐 | — | 두 ID 초기화(진짜 주인 변경) |
| 가져간 ID 가 다른 ID 에 병합됨 | — | 그 ID 와 원래 주인을 초기화하고 주인 기록을 옮김 |
| 가져간 ID 가 병합 없이 사라짐(보존 30초 경과) | — | 다툼을 지움 |
| 확실한 사람이 가져감 | 두 ID 초기화 | 같음 |

- 불확실한 사람의 표본은 원래 창에도 근거에도 넣지 않는다(-653). 그래서 다툼 중인 local ID 의 표본은 어느 쪽에도 들어가지 않는다. 원래 주인은 다른 카메라 근거로 계속 갱신되고, 없으면 10초 만료가 상태를 정리한다.
- `ai/src/simai_ai/ppe/config.py`: `uncertain_claim_contests = True` 를 추가하고 `POLICY_VERSION` 을 `ppe-policy-0.8.0` 으로 올렸다. False 면 0.7.0 동작이다.
- 계측 `identity_events` 에 `mapping_contested`(다툼 시작)와 `mapping_contest_cleared`(초기화 없이 정리)를 더했다. PPE 서비스 상태 보고(`identity`)에 그대로 실린다.

## 왜 하나 (실측)

2026-11-16 로비 라이브(work 58 run 1, 13:39~14:07 KST, EC2 `ppe_state`·`world_track_state`·`person_world_merge_log`).

- 노랑 조끼 작업자(w-mwiqipf2-0044)는 PPE 판단 자체는 안정적이었다(클립 재분석 미착용 오검출 0%). 그런데도 착용 상태가 ID 문제로 22번 초기화됐다.
  - `IDENTITY_MAPPING_CHANGED` 14번
  - `IDENTITY_UNCERTAIN` 3초 초과 8번
- `IDENTITY_MAPPING_CHANGED` 14번 중 13번은 ±1초 안에 새 임시 ID 가 생긴 때였다.
  - 그중 7번은 그 임시 ID 가 1~9초 뒤 0044 로 다시 병합됐다.
  - 1번(0062)은 0050 에 병합됐다. 이 경우는 진짜 사람 사이 local ID 이동이다.
- 이 구간 임시 ID 는 51개였다.
  - 51개 중 38개는 끝까지 한 번도 확실해지지 않았다(평균 2.9초 생존, 24개는 원래 ID 로 병합).
  - 확실해진 13개 중 6개만 1초 안에 확실해졌다. 나머지 7개는 평균 7.4초 동안 불확실했다.
  - 51개 중 29개가 다른 ID 로 병합됐고, 22개는 병합 없이 사라졌다.
- 착용이 다시 확정되기까지 대개 15~27초가 걸렸다. 0044 의 대응 변경 UNKNOWN 구간 합계는 약 468초로, 작업 시간의 약 28% 였다.
- 원인은 0.7.0 의 주인 검사였다. 불확실한 사람에게도 그대로 적용됐고, 그 사람이 주인 기록까지 덮어썼다. 근거로도 쓰지 않는 사람 때문에 확실한 작업자의 상태가 지워졌다.

어느 카메라의 local ID 가 넘어갔는지는 DB 에 없다. 위 연결은 시각 일치로 한 추정이다.

## 버린 대안

- **병합되면 초기화 전 상태를 되살리기**: 구현은 단순하다. 그러나 임시 ID 가 사는 동안(최대 약 9초)은 여전히 UNKNOWN 이고, 병합 없이 사라진 임시 ID(51개 중 22개)는 구제하지 못한다.
- **불확실 3초 초과 초기화 완화(2안)**: 나머지 8번을 줄이지만 -653 D2 결정을 바꾼다. 이번 범위에서 뺐다(사용자 결정 2026-11-16).
- **Tier 0 임시 ID 남발 자체를 줄이기**: 근본 원인이다. 그러나 시연(11-18)까지 시간이 없고 위험이 크다. 별도 과제로 둔다.

## 불변 조건

- 확실한 사람의 주인 변경 판정은 그대로다.
- 순수 병합 승계(-661)도 그대로다. 흡수된 ID 의 local ID 를 남는 ID 가 이어받는 것은 주인 변경이 아니다.
- 다툼은 원래 주인의 확정 상태를 유지할 뿐이다. 새 근거는 더하지 않으므로 10초 만료는 그대로 동작한다.
- 새 stream_epoch 이 오면 그 카메라의 다툼도 지운다.

## 잔여 위험

- 임시 ID 가 실제로는 다른 사람이고, 끝까지 불확실한 채 사라질 수 있다. 이때 그 사이 원래 주인의 상태는 원래 주인의 다른 카메라 근거로만 갱신된다. 잘못된 사람의 표본은 원래부터 쓰지 않으므로 상태가 섞이지는 않는다.
- 원래 주인 자신이 같은 때 불확실하면 3초 초과 초기화(-653)는 그대로 일어난다(0044 의 나머지 8번).
- 효과 수치(초기화 감소량, UNKNOWN 감소)는 추정이다. 다음 현장 라이브에서 `identity_events` 의 `mapping_contested`·`mapping_contest_cleared`·`mapping_reset` 과 0044 형 작업자의 UNKNOWN 비율로 잰다.
