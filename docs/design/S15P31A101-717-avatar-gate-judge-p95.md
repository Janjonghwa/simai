# 아바타 접수 문의 판정 처리 p95 기준 재검토 (S15P31A101-717)

17차 GPU 세션(H100 SXM, 14차 녹화 재생, 사람 2~3명)에서 상시 아바타가 `AdmissionGate 차단: Tier 0 judge 처리 p95 179.3ms > 100ms`
로 막혀 작업 4분 동안 자세 묶음 49개·외형 20개만 나갔다. 아바타는 시연 필수다. 17차 로그로 판정 p95 를 단계별로 나누고, 아바타 문이
쓰는 판정 처리 p95 의 정의와 기준이 명세 3.2 의 의도(Tier 0 지연이 목표를 넘거나 모르면 멈춤)에 맞는지 보고, 기준을 고쳤다.
**판정 처리 기준을 100 → 200 ms 로 바꾼 것은 Lead 확인이 필요하다.**

## 관련 명세 절

| 절 | 내용 | 이 문서에서 |
|---|---|---|
| 3.2 | Tier 0 지연이 목표를 넘거나 모르면 분석 워커·상시 아바타 추론을 멈춘다. 지연 초과·모름이면 즉시, 뷰어는 0.5 s 뒤 캡슐 | 모름·극단값(1 s)·표시 파일 만료는 그대로 즉시 멈춤. 판정 처리 기준만 6.6 목표에서 다시 끌어냄 |
| 6.6 | capture_to_risk **p95 목표** 600 ms(상한 아님, 끝에서 끝까지 직접 잼), 기하 단계 목표(5명 p95 25 ms) | 판정 처리 몫 = 600 − 150 − 150 − 100 = 200 ms 는 목표를 나눈 배분이지 끝단 600 ms 를 보장하는 식이 아니다(3절, S15P31A101-727 정정). 기하 단계 목표 미달은 아래 "명세와 다른 점" |
| 5.1 | 추론 대기 상한 `queue_wait_ms` 150 ms | 검출 처리 기준 150 ms 는 그대로 |

`docs/design/tier0-gpu-priority.md` 의 -498(아바타는 처리 부하 기준, 2026-11-05 사용자 승인)·-547(p95 연속 10 s 차단·10 s 재개)
규칙 위에서 기준값 하나와 사유 문구만 바꾼다.

## 2. 아바타 문의 "판정 처리 p95" 정의와 명세 의도

정의(코드): Tier 0 `_run_judge` 가 `ProcessingWindow.run(judge.tick)` 으로 틱 한 번의 벽시계(판정 lock 대기·GIL 대기 포함)를 재고,
표시 파일을 쓸 때(5 s)마다 그 사이 표본(약 50개, 진행 중 경과 포함)의 p95 를 `gpu_priority.processing.judge.lag_ms_p95` 로 남긴다.
아바타 문은 이 값이 예산을 **연속 10 s**(창 2개) 넘으면 막고, 예산 이하가 10 s 이어지면 연다. 모름·창 최댓값 ≥ 1000 ms·표시 파일
만료·GPU 예약 실패는 즉시 막는다. 검출 쪽은 `detect_once`(대기열·TRT·2D 추적·Re-ID 제출) 한 번을 같은 방식으로 150 ms 와 비교한다.

100 ms 의 원래 근거(-547)는 "판정 주기 10 Hz = 100 ms, 11-08 에서 3명 p95 97 ms·4명 233 ms 라 정상과 과부하의 경계"였다. 17차 증거:

| 증거 | 값 | 뜻 |
|---|---|---|
| 아바타를 멈춘 동안의 판정 p95 | 아바타 로그 1분 상태 줄 5개 연속: 108.3·104.3·118.4·197.6·179.3 ms. 그동안 `infer` 누계 12,837 ms·`appearance` 820 ms 그대로(HMR·외형 0회), `pose_batches=0` | 판정 초과는 아바타 때문이 아니다. 아바타를 막아도 판정이 줄지 않으니 막는 것이 Tier 0 를 지키지 못한다 |
| 분석 워커 끝단 문(capture_to_risk 창 최댓값 600 ms·큐 대기 규칙) | 07:14:40 `받음 (Tier 0 지연 271ms ≤ 예산 600ms)` 뒤 끝까지 바뀌지 않음(바뀔 때만 남김), VLM 작업 27건 실행 | 명세 3.2·6.6 의 기준으로 Tier 0 는 목표 안이었다 |
| 결합 경로 | 아바타는 별도 프로세스, 사이드카 코어(`SIMAI_SIDECAR_CPUS=auto`)에 묶임. Tier 0 안 아바타 몫은 `avatar_share` p95 0.1 ms·`avatar-ipc` 스레드 CPU 3.7% | 아바타가 판정 시간에 닿는 길은 작다. GPU 를 나눠 쓰는 길은 검출 시간에 나타난다(검출 150 ms 가 그 몫) |

결론: 100 ms 는 "판정 주기를 한 번이라도 넘김"이지 "판정 지연이 위험함"이 아니다. 지금 Tier 0 는 2~3명에서 아바타와 상관없이 이 선을
넘으므로, 문이 시연 필수 기능만 끄고 Tier 0 에는 이득이 없다. 명세 3.2 의 의도(Tier 0 지연이 목표를 넘을 때 멈춤)에 맞추려면 판정 처리
기준을 6.6 목표에서 끌어내야 한다.

## 3. 고친 것 (Lead 확인 필요)

판정 처리 p95 예산 = capture_to_risk p95 목표 600 ms − 융합 허용 지연 150 ms(`fusion_max_lag_ms`, 늦은 카메라 기준) − 검출 처리 예산
150 ms − 판정 주기 대기 100 ms(`tick_ms`) = **200 ms**(판정 주기 2개). 이것은 600 ms p95 목표 안에서 판정 처리에 나눠 준 **몫(배분)**
이다. 각 구간이 자기 몫 안이라고 촬영 → 판정 p95 가 600 ms 안이라는 보장은 없다.

(S15P31A101-727 정정) 처음에 "이 안이면 촬영 → 판정이 600 ms 를 넘지 않는다(구간 p95 를 더한 값은 전체 p95 보다 크므로 보수적이다)"
라고 적었는데 틀렸다.

- 구간 p95 의 합은 전체 p95 의 상한이 아니다(분위수는 더하기에 대해 준가법이 아니다). 예: 독립인 두 구간이 각각 96% 확률로 0 ms,
  4% 확률로 100 ms 면 구간 p95 는 둘 다 0 이라 합이 0 이지만, 합이 0 보다 클 확률은 1 − 0.96² = 7.84% > 5% 라 전체 p95 는 100 ms 다.
  명세 6.6 도 "구간별 p95의 합을 전체 p95로 해석하지 않고 각 구간을 끝에서 끝까지 잰다"고 쓴다.
- 600 ms 는 상한이 아니라 p95 **목표**다(6.6 "초기 목표"). 5% 는 넘어도 목표 안이고, 판정은 끝단 직접 측정으로 한다.
- 식의 항은 끝단 경로를 빠짐없이 나눈 구간이 아니다. 노트북 → Pod 업로드·디코딩·추론 대기(상한 150 ms)·I1 송신이 없고,
  `fusion_max_lag_ms` 는 구간 시간이 아니라 카메라 간 촬영 시각 차 허용 한도다. 판정 200 ms 도 p95 라 5% 는 넘는다.

그래서 이 몫이 맞는지는 끝단 직접 측정으로 본다. 17차 작업 중 분석 워커 문의 끝단 지연(capture_to_risk 근사, 창 최댓값)은
271 ms ≤ 600 ms 로 열려 있었다(2절 표). 아바타를 켠 상태의 끝단 값은 "다음 GPU 세션에서 잴 것" 3번이다.

- 2~3명 17차 창(104~198 ms)은 통과한다. 4명 이상 지속 과부하(11-08 p95 233·333·422 ms)는 지금처럼 10 s 뒤 막는다.
- 검출 150 ms·극단값 1000 ms·모름 즉시 차단·10 s 연속 차단/재개는 그대로다.
- 자체 감속은 차단 예산이 아니라 기준선(판정 100 ms = 판정 주기 초과 시작점, 검출 150 ms) 대비 0.70·0.85·1.0 단계로 그대로 둔다.
  판정 70 ms 부터 400 ms 주기, 85 ms 부터 600 ms, 100 ms 를 넘으면(차단 전 100~200 ms 구간) 800 ms 주기로 물러난다. 주입한 판정
  예산이 100 ms 보다 작으면 기준선도 그 값이다(감속이 차단보다 먼저 오게).
- 차단·통과 사유에 `judge p95 x/200ms·detect p95 y/150ms` 를 함께 남긴다. 17차에는 판정 사유만 보여 검출 쪽 여유를 몰랐다.
- `SIMAI_AVATAR_JUDGE_BUDGET_MS`·`SIMAI_AVATAR_DETECT_BUDGET_MS` 로 GPU 세션에서 재빌드 없이 바꿀 수 있다(아바타 프로세스만 읽는다).
  100 을 주면 이전 동작이다. 값이 양수 유한값이 아니면 경고를 남기고 기본값으로 시작한다(예외로 끝내면 감시 프로세스가 아바타를 계속 다시 띄운다).
- 3.2 의 "지연 초과·모름이면 멈추고 뷰어는 캡슐로 돌아간다"는 그대로다. 문이 닫히면 포즈가 끊기고 뷰어 정지 기준으로 캡슐이 된다.

## 4. 판정 처리 시간을 줄이는 일 (이 티켓에서 코드는 안 바꿈)

## 버린 대안

- **100 ms 유지 + 판정 최적화만**: 시연 전에 판정 p95 를 2~3명에서 100 ms 아래로 확실히 내릴 길이 없다(-716 과 겹침, 재생 묶음 없음).
  그동안 아바타가 꺼진다.
- **판정 처리를 스레드 CPU 시간으로 재기**: GIL·코어 대기도 실제 판정 지연이다. 지연을 지키는 문이 지연의 일부를 빼고 보면 안 된다.
- **아바타 문에 끝단 지연(600 ms)을 다시 넣기**: 11-05 사용자 결정(-498)이 망 지연 때문에 뺀 것이다. 분석 워커 문은 그대로 끝단 지연을 본다.
- **"아바타가 원인일 때만" 막기(켜고 끈 차이로 판정)**: 원인을 가리려면 아바타를 일부러 꺼 봐야 해서 시연 중 깜빡임이 생기고 규칙이 복잡하다.
- **-650 의 "100 → 200~250 완화 기각"을 그대로 따르기**: 그때 근거는 아바타가 Tier 0 를 느리게 한다는 것(14차 L40S, 판정 경로 동기 크롭 쓰기·
  4대 seg)이었다. -650·-662 로 그 결합을 뺐고 17차에서 아바타를 멈춰도 판정이 그대로였다. 근거가 바뀌었다.

## 남은 위험

- **14차 선례**: 아바타 예산을 150 ms 로 풀자 Tier 0 지연이 600 ms 를 넘었다(-662 문서). 결합을 뺀 뒤라 다를 것으로 보지만 아바타를
  켠 상태의 판정·검출 p95 는 아직 재지 못했다. 검출 150 ms·극단값 1 s·모름 즉시 차단과 분석 워커의 끝단 600 ms 문이 남아 있다.
- **검출이 다음 차단 사유가 될 수 있다**: 아바타를 멈춘 상태에서도 2~3명 `detect_trt` p95 89~135 ms 였다. `detect_once` 전체 p95 는
  로그에 없어 모르지만 150 ms 에 가까울 수 있다. 아바타 GPU 몫이 더해지면 검출로 막힐 수 있다.
- **판정 창 p95 가 200 ms 근처**: 17차 창 197.6 ms. 단발은 10 s 연속 규칙이 흡수하지만 부하가 조금 늘면 다시 막힌다. 4절 최적화가 필요하다.
- 아바타 로그 1분 상태 줄에는 시각이 없어 차단 구간을 tier0 로그 시각과 초 단위로 맞추지 못했다(줄 순서와 누계로만 판단).
