# Git 협업 규칙

코드 규칙(포맷터, 이름 규칙 등)은 파트별로 `front/`, `server/`, `ai/` 의 `CONVENTION.md` 에 둔다.

## 규칙 문서 위치

| 문서 | 내용 |
| --- | --- |
| `docs/git-convention.md` | 브랜치·커밋·MR 규칙과 Jira 연동 (이 문서) |
| `docs/jira-convention.md` | Jira 에픽·작업 작성, 라벨, 상태 규칙 |
| `front/`, `server/`, `ai/` 의 `CONVENTION.md` | 파트별 코드 규칙 |
| `AGENTS.md` | AI 코딩 도구 공통 지침. `CLAUDE.md` 는 `AGENTS.md` 를 불러오기만 한다 |

사람과 AI 도구가 같은 규칙을 보도록 규칙은 위 문서에만 쓴다. AI 도구용 지침에 규칙을 따로 복사하지 않고 이 문서들을 가리킨다.

## 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `master` | 배포. `dev` 에서 MR 로만 올린다. |
| `dev` | 개발 통합 (GitLab 기본 브랜치). 작업 브랜치에서 MR 로만 올린다. |
| 작업 브랜치 | `dev` 에서 따서 작업하고 `dev` 로 MR 을 올린다. merge 후 삭제한다. |

작업 브랜치 이름은 `{Jira 키}-{기능 설명}` 이다.

```
S15P31A101-12-login-api
S15P31A101-34-alert-duplicate
```

- Jira 키는 이슈 번호를 그대로 쓴다. Jira 이슈가 먼저 있어야 한다.
- 기능 설명은 영어 소문자와 `-` 로 짧게 쓴다.
- 원칙은 이슈 하나에 브랜치 하나, MR 하나다. 큰 일은 Jira 에서 스토리를 나눈다(`docs/jira-convention.md`).
- 예외: 이슈를 끝내기 전에 중간 결과를 먼저 `dev` 에 넣어야 할 때만, 같은 키에 기능 설명을 바꿔 브랜치를 하나 더 만든다. 예: `S15P31A101-40-exp01-baseline`, `S15P31A101-40-exp01-report`

## 커밋 메시지

```
[S15P31A101-12] 로그인 API 에 JWT 발급을 추가한다
```

- 맨 앞에 `[Jira 키]` 를 붙인다. 이 키로 Jira 이슈에 커밋이 연결된다.
- 설명은 한국어로, 무엇을 바꿨는지 한 줄로 쓴다.
- 커밋 하나에는 한 가지 변경만 담는다.

## 커밋하지 않는 것

- 영상·사진·녹화 파일: 사람이 찍혀 있어 개인정보다. 객체 저장소나 RunPod Network Volume 에 두고, 저장소에는 경로와 해시만 남긴다.
- 모델 가중치·데이터셋·대형 3D 산출물: 같은 방식으로 경로와 해시만 남긴다.
- 비밀 값(API 키, 토큰, 카메라 RTSP 계정): `.env` 에만 두고 `.env.example` 에 이름만 적는다.

`.gitignore` 가 대부분 막지만, 새 형식의 파일을 추가할 때는 커밋 전에 `git status` 로 확인한다. 실수로 올렸으면 바로 알린다. 이력에 남으므로 비밀 값은 즉시 폐기하고 다시 발급한다.

## MR 라벨

MR 에는 변경 성격에 맞는 라벨을 하나 붙인다. 여러 성격이 섞이면 가장 주된 것을 고른다.

| 라벨 | 쓰는 경우 |
| --- | --- |
| ✨ feat | 새로운 기능 추가 |
| 🐛 fix | 버그 수정 |
| 📝 docs | 문서 수정 |
| 🎨 style | 코드 포맷팅, UI 스타일 등 |
| ♻️ refactor | 기능 변경 없는 코드 개선 |
| ⚡ perf | 성능 개선 |
| ✅ test | 테스트 추가/수정 |
| 🔧 config | 설정 파일, 환경 설정 변경 |
| 🔥 remove | 코드/파일 삭제 |
| 🚀 deploy | 배포 관련 변경 |
| 👷 ci | CI/CD 관련 변경 |

## MR

- 대상 브랜치는 `dev` 다. 배포 MR 만 `dev` → `master` 로 올린다.
- 제목은 커밋 메시지와 같은 형식이다: `[S15P31A101-12] 로그인 API 에 JWT 발급을 추가한다`
- 본문은 `.gitlab/merge_request_templates/default.md` 양식을 쓴다.
  - **To People**: 작업 내용, As-Is, To-Be. 사람이 읽고 바로 이해할 수 있게 쓴다.
  - **To AI**: 의도와 근거, 관련 명세, 가정, 영향 범위, 검증, 리뷰 중점. diff 에 없는 정보만 쓴다.
- 본문 맨 아래에 Jira 키를 남긴다.
  - 이 MR 로 이슈가 끝나면 `Closes S15P31A101-12`. `dev` 에 merge 되면 Jira 이슈가 완료로 바뀐다.
  - 위 예외로 같은 키의 MR 이 더 남았으면 `Refs S15P31A101-12`. 이슈에 연결만 되고 상태는 바뀌지 않는다.
- [MR 라벨](#mr-라벨) 중 하나를 붙인다.
- Claude Code 를 쓰면 `/mr` 스킬로 위 규칙대로 MR 을 올릴 수 있다.

## 리뷰와 merge

- 리뷰 댓글(스레드)이 모두 해결돼야 merge 할 수 있다.
- merge 는 squash 로 한다. MR 제목이 `dev` 에 남는 커밋 메시지가 된다.
- merge 후 작업 브랜치는 자동 삭제된다.

## Jira 연동

GitLab 과 Jira(`ssafy.atlassian.net`, 키 `S15P31A101`)가 연결돼 있다.

| 하는 일 | Jira 에 생기는 일 |
| --- | --- |
| 커밋 메시지·MR 제목/본문에 Jira 키를 쓴다 | 이슈의 웹 링크에 커밋·MR 이 연결된다 |
| `Closes 키` 가 있는 MR 을 `dev` 에 merge 한다 | 이슈가 완료로 바뀐다 |

연동은 브랜치 이름이 아니라 커밋 메시지와 MR 에 적힌 키로 동작한다. 커밋 메시지의 `[Jira 키]` 를 빠뜨리지 않는다.
