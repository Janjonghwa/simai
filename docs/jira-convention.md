# Jira 규칙

Jira(`ssafy.atlassian.net`, 프로젝트 키 `S15P31A101`)에서 일을 나누고 추적하는 규칙이다. 브랜치·커밋·MR 은 `docs/git-convention.md` 를 따른다.

## 구조

| 단위 | 쓰는 것 | 예 |
| --- | --- | --- |
| 에픽 | 기능·결과물 묶음. 팀 전체가 공유한다 | 실시간 추적·World 상태 |
| 스토리 | 한 사람이 한 주 안에 끝내는 결과 하나. 브랜치 하나, MR 하나, 스토리 포인트의 단위 | Tapo C110 RTSP 수신 측정 도구를 만든다 |
| 버그 | 이미 merge 된 기능의 잘못된 동작 | R1 경보가 구역 밖에서 울린다 |
| 라벨 | 파트와 실험 | `ai`, `exp-01` |
| 버전 | 통합 단계(마일스톤) | `M1` |

- 개발·실험·문서·발표 작업을 모두 스토리로 만든다. 작업(Task) 유형은 쓰지 않는다.
- 하위 작업은 쓰지 않는다. 스토리 안의 세부 단계는 본문의 할 일 목록으로 관리한다.
- 큰 일은 스토리를 크게 만들지 않고, 결과 단위로 스토리를 여러 개 만들어 같은 에픽에 둔다.

## 에픽

| 관제 플랫폼 기반 | 인증·권한, DB 구성, 공통 API 구조, 앱 뼈대·공통 UI, EC2 배포·HTTPS·객체 저장소·모니터링 | — |

- 모든 스토리는 에픽 하나 아래에 둔다. 기능에 묶인 작업은 파트와 관계없이 그 기능의 에픽으로 보낸다(예: 이벤트 API 는 관제 백엔드·알림, 뷰어의 경보 표시는 3D 관제 뷰어).
- 파트별로 보려면 보드에서 라벨로 거른다.
- 새 에픽은 팀에 알린 뒤 만든다. 확장 기능(PPE, 워치, 리플레이)은 착수할 때 추가한다.

## 스토리 쓰는 법

**요약**: 무엇을 하는지 한국어 한 줄로, 커밋 메시지처럼 쓴다. 이 요약이 MR 제목이 된다.

```
Tapo C110 RTSP 수신 측정 도구를 만든다
EXP-01 E-GATE-0: MapAnything Native 를 A40 에서 재현한다
최종 발표 시연 영상을 촬영하고 편집한다
```

- 실험 스토리는 요약 앞에 실험 ID 와 게이트를 붙인다.
- `[AI]` 같은 파트 표시는 요약에 쓰지 않는다(라벨로 한다).

**본문**: 아래 양식을 쓴다.

```
## 배경
왜 하는지. 관련 기획서 절(예: 기획서 §12.7), 요구사항 ID.

## 작업
- [ ] 할 일 1
- [ ] 할 일 2

## 완료 조건
- 무엇을 확인하면 끝인지. 테스트 통과, 측정값, 산출물, 판정 기록.
```

- 완료 조건은 다른 사람이 확인할 수 있게 쓴다. "잘 동작한다" 대신 "4대 동시 수신 30분, 프레임 손실 1% 이하 기록"처럼 쓴다.
- 실험·조사처럼 결과가 불확실한 스토리는 완료 조건에 "판정 기록(채택/보류/기각과 근거)"을 넣는다. 실패한 결과도 기록하면 완료다.

**필드**

| 필드 | 규칙 |
| --- | --- |
| 담당자 | 한 명. 작업을 시작할 때 지정한다 |
| 상위 항목(에픽) | 필수 |
| 스토리 포인트 | 0, 1, 2, 3, 5, 8 중 하나. 아래 기준을 따른다 |
| 우선순위 | 기본값(Low)으로 둔다. 급하거나 다른 일을 막고 있을 때만 올린다 |
| 라벨 | 파트 라벨 하나 이상: `ai`, `server`, `front`, `deploy`, `docs`, `pm`(기획·발표·운영). 실험은 `exp-01`, `exp-02`, `int-01` 을 더한다 |
| 버전 | 해당하는 통합 단계: `M1`, `M2`, `M3`. 기반·실험·발표 스토리처럼 단계에 묶이지 않으면 비운다 |
| 스프린트 | 이번 스프린트에 할 스토리만 넣는다 |
| 연결 | 다른 스토리가 끝나야 시작할 수 있으면 "blocks / is blocked by" 로 연결한다 |

## 스토리 크기 (권장)

- 한 주 안에 혼자 끝내고 MR 하나로 올릴 수 있는 결과 하나가 기준이다.
- 8 포인트를 넘을 것 같으면 결과 단위로 나눈다. 예: "4대 동시 수신"과 "NTP 시각 동기화"
- 완료 조건이 "설정 한 줄 바꿈" 정도로 작으면 따로 만들지 않고, 관련 스토리의 할 일 목록에 넣어 같은 브랜치에서 처리한다.
- 어느 스토리에도 속하지 않는 작은 일(의존성 업데이트, 오타 수정)만 0~1 포인트 스토리로 만든다.

## 스토리 포인트

상대적인 크기로 매긴다. 시간 약속이 아니다.

| 포인트 | 크기 |
| --- | --- |
| 0 | 설정 하나 바꾸기처럼 거의 일이 없는 것 |
| 1 | 작고 할 일이 분명한 것 |
| 2 | 작지만 확인할 것이 몇 가지 있는 것 |
| 3 | 보통 크기 |
| 5 | 크거나 모르는 부분이 있는 것 |
| 8 | 한 스프린트 안에 혼자 끝낼 수 있는 최대 크기 |

- 스프린트가 끝나도 못 끝낸 스토리는 다음 스프린트로 옮기고, 포인트는 남은 일 기준으로 다시 매긴다.

## 개발 외 스토리

기획·발표 에픽의 스토리(발표 자료, 영상, 동의서 등)는 브랜치와 MR 이 없다.

- 산출물 링크(PPT, 영상, 문서)를 댓글이나 첨부로 남긴 뒤 담당자가 완료로 옮긴다.
- 라벨은 `pm` 을 쓰고, 스토리 포인트도 매겨 그 주의 개발 계획에 반영한다.

## 상태

| 상태 | 언제 |
| --- | --- |
| 해야 할 일 | 만든 직후 |
| 진행 중 | 담당자가 브랜치를 만들고(개발 외 스토리는 작업을 시작하고) 직접 옮긴다 |
| 완료 | `Closes 키` 가 있는 MR 이 `dev` 에 merge 되면 자동으로 바뀐다. 코드가 없는 스토리는 완료 조건을 확인한 뒤 담당자가 직접 옮기고, 결과를 댓글로 남긴다 |

- 막혀서 진행할 수 없으면 상태는 그대로 두고 댓글에 막힌 이유와 필요한 것을 쓴다.

## 스프린트

- 1주 단위로, 월요일에 시작해 금요일에 끝낸다.
- 첫 스프린트 "MVP 완성"만 예외로 2026-10-16(금) ~ 10-30(금) 2주다. 목표는 핵심 루프(카메라 4대 → 노트북 중계 → Tier 0 추적·World 상태 → R1 판정 → 현장 경보 → EC2 저장 → Three.js 표시)가 처음부터 끝까지 도는 데모다. 장애 복구·자동 보정·M2·M3 기능은 이후 스프린트에서 한다.
- 월요일에 이번 주에 할 스토리를 스프린트에 넣고 포인트를 매긴다. 금요일에 완료하지 못한 스토리를 확인하고 다음 스프린트로 옮긴다.
